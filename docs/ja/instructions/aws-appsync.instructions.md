# AWS AppSync イベント API の手順

`APPSYNC_JS` ランタイムを使用して AWS AppSync **Event API** ハンドラー (`onPublish`、`onSubscribe`) を実装する場合は、次の手順を使用してください。

## 範囲と契約

- チャネル名前空間フローに関するハンドラーを設計します。`onPublish` はブロードキャスト前に実行され、`onSubscribe` はサブスクリプション試行時に実行されます。
- イベント契約を明示的かつ安定的に保ちます。チャネルパスとペイロードの形状を API コントラクトとして扱います。
- ペイロードフィールドの追加的な変更を優先し、既存のサブスクライバーを壊すことを避けてください。

## データソース マップ (イベント API)

イベントワークフローのニーズに基づいてデータソースを意図的に使用します。

- Lambda: カスタムコンピューティング、変換、オーケストレーション、外部 AWS/サービス統合。
- DynamoDB: 低レイテンシーのイベント/状態の永続性とキーベースの読み取り/書き込み。
- RDS (Aurora): リレーショナルチェック、結合、およびより強力なリレーショナル整合性の使用例。
- EventBridge: イベントをより広範なイベント駆動型アーキテクチャにルーティングします。
- OpenSearch: イベントデータの検索と分析。
- HTTP エンドポイント: HTTP 経由の外部 API または AWS サービス API。
- 基盤: イベントパイプラインでのモデル推論と AI エンリッチメント。

各ホップに明確な理由 (認証、永続性、エンリッチメント、ルーティング) がある場合にのみ、複数のデータソースを組み合わせることをお勧めします。

## データソースのセットアップと IAM (必須)

- イベント API レベルでデータソースを作成し、それらを名前空間統合としてアタッチします。
- サービスロールを使用する場合は、必要なアクションのみを付与します (最小権限)。
- 信頼ポリシープリンシパルは、`appsync.amazonaws.com` が役割を引き受けることを許可する必要があります。
- 可能であれば、条件付きで信頼を制限します。
  - `aws:SourceAccount` をあなたのアカウントに送信してください。
  - `aws:SourceArn` を特定の AppSync API ARN (または範囲が狭いパターン) に変換します。
- AppSync データソース アクセスに広範なサービス間 IAM ロールを再利用しないでください。

## 実行時の制限事項 (従う必要があります)

`APPSYNC_JS` ランタイムは、制約付きの JavaScript サブセットです。完全な Node.js ではなく、この環境用のコードを作成します。

- 非同期パターン (約束なし、`async/await`、またはバックグラウンドの非同期ワークフロー) は使用しないでください。
- サポートされていないステートメント/演算子: `try/catch/finally`、`throw`、`while`、C スタイル `for(;;)`、`continue`、ラベル、サポートされていない単項演算子は使用しないでください。
- ランタイムコードからのネットワークまたはファイルシステムへのアクセスに依存しないでください。 I/O には AppSync データソースを使用します。
- 再帰を使用したり、関数を関数の引数として渡したりしないでください。
- 文書化されたサポート以外のクラスや高度なランタイム機能に依存しないでください。
- 反復が必要な場合は、`for-of` / `for-in` ループを優先します。

## ハンドラーのフローパターン

- データソース統合のないハンドラーの場合は、変換された `ctx.events` を直接返します。
- データソースを含むハンドラーの場合は、`request(ctx)` および `response(ctx)` を含むオブジェクトフォームを使用します。
- ビジネスロジックがデータソースの呼び出しと応答マッピングをスキップすることを決定した場合は、`runtime.earlyReturn(...)` を使用します。
- `ctx.info.channel.path`、`ctx.info.channel.segments`、`ctx.info.channelNamespace.name`、および `ctx.info.operation` を使用してルーティングロジックを駆動します。
- データソース統合のある `onPublish` の場合、`response(ctx)` からブロードキャストするイベントリストを返します。
- データソース統合を伴う `onSubscribe` の場合、`response(ctx)` 関数を含めます (フォローアップマッピングが必要ない場合は空にすることができます)。

### `ctx.prev.result` 対 `ctx.stash` (パイプラインガイダンス)

- リゾルバー/関数がステップバイステップで実行され、次のステップが前のステップの出力に依存する場合は、`ctx.prev.result` を使用します。
- 連続するパイプライン関数間のデフォルトのデータ受け渡しメカニズムとして `ctx.prev.result` を使用します。
- 直前の結果だけではなく、複数のパイプラインステージにわたって共有データが必要な場合は、`ctx.stash` を使用します。
- `ctx.stash` には、大きなペイロードのコピーではなく、小さな意図的なメタデータ (フラグ、ID、相関コンテキストなど) のみを保存します。
- `ctx.prev.result` がすでに必要な値を提供している場合は、以前の結果全体を `ctx.stash` に複製しないでください。

## エラーと認証の流れ

- ハンドラでは `throw` を使用しないでください。 AppSync ランタイムでサポートされている `util.error(...)` パターンと `util.appendError(...)` パターンを使用します。
- パブリッシュが失敗した場合は、安全なメッセージ (内部メッセージなし) を含む明示的なランタイムエラーを返します。
- ハンドラーレベルでビジネスレベルの承認を拒否するには、ハンドラーコードで文書化された無許可ユーティリティを使用します。
- エラーペイロードを機密にしないでください。シークレット、生のスタックトレース、内部識別子は決して公開しないでください。

## 組み込みユーティリティ

ランタイムセーフなヘルパーには `util` を使用します。

- エンコードユーティリティ:
  - `util.urlEncode`、`util.urlDecode`
  - `util.base64Encode`、`util.base64Decode`
- ランタイムユーティリティ:
  - `runtime.earlyReturn(obj)` は、現在のハンドラーの実行を停止し、データソースと応答の評価をスキップします。

## 内蔵モジュール

`@aws-appsync/utils` の公式モジュールを使用し、コードは宣言的にしてください。

- DynamoDB モジュールのインポート:
  - `import * as ddb from '@aws-appsync/utils/dynamodb'`
- RDS モジュールのインポート:
  - `import { ... } from '@aws-appsync/utils/rds'`

### DynamoDB の使用法

可能な場合は、手書きのリクエストオブジェクトよりもモジュールヘルパーを優先します。

- コアヘルパーには、`get`、`put`、`remove`、`update`、`query`、`scan`、`sync` が含まれます。
- バッチヘルパー: `batchGet`、`batchPut`、`batchDelete`。
- トランザクションヘルパー: `transactGet`、`transactWrite`。
- `update` の場合は、安全なパッチ形式の変更のために、increment/append/add/remove などの操作ヘルパーを優先します。
- クエリファーストアクセスのキーとインデックスをモデル化します。正当な理由がない限り、`scan` は避けてください。
- 必要に応じて、正確性とオプティミスティック同時実行性のための条件を使用します。
- バースト性の高いパブリッシュフローの場合は、多くの単一項目操作よりも `batchPut`/`batchDelete` (または原子性が必要な場合は `transactWrite`) を優先します。
- DynamoDB のバッチサイズをサービス/API の制限内に保ち、チャンク入力を決定的に維持します。

### ラムダの使用法

Event API Lambda データソース リクエストの場合は、以下を使用します。

- `operation: 'Invoke'`
- オプション `invocationType: 'RequestResponse' | 'Event'`
- `payload` は Lambda コントラクト用に明示的に形成されています

ガイダンス：

- ハンドラーフローが Lambda 出力に依存する場合は `RequestResponse` を使用します。
- `Event` は、ファイアアンドフォーゲットの副作用にのみ使用してください。
- `response(ctx)` の `ctx.result` を検証し、正確な送信イベントの形状にマッピングします。
- イベント API ハンドラーでは、Lambda オペレーションのサポートは `Invoke` です。ここでは GraphQL スタイルの `BatchInvoke` に依存しないでください。
- イベント API フローで Lambda を使用したバッチ処理が必要な場合は、配列ペイロードを 1 つの `Invoke` で送信し、Lambda 内で項目レベルの集計/部分的な失敗の処理を実装します。

### Lambda の直接統合 (ハンドラーコードなし)

`onPublish`/`onSubscribe` コードを記述する代わりに、直接 Lambda 統合 (`Behavior: DIRECT`) を使用して名前空間ハンドラーを設定できます。

- `REQUEST_RESPONSE` モード:
  - `onPublish` ラムダは `{ events?: OutgoingEvent[], error?: string }` を返します。
  - `onSubscribe` Lambda は、成功の場合は `null` を、拒否の場合は `{ error: string }` を返します。
- `EVENT` モード:
  - 呼び出しは非同期です。 AppSync は Lambda 応答を待ちません。
  - パブリッシュの場合、イベントは通常どおりブロードキャストを続けます。
- Lambda がリクエスト/レスポンスモードで `error` を返した場合、ログが有効になっているときにログに記録され、詳細な内部エラーペイロードとしては送り返されません。

名前空間の動作全体を Lambda で一元管理でき、APPSYNC_JS リクエスト/レスポンスマッピング ロジックが必要ない場合は、Lambda の直接統合をお勧めします。

### HTTP/イベントブリッジ/RDS/OpenSearch/Bedrock

非 DynamoDB データソースを使用する場合:

- HTTP: `resourcePath`、`method`、オプションの `params` (`headers`、`query`、`body`) を返します。 `ctx.result.statusCode`、`ctx.result.body`、`ctx.error` を確認してください。
- EventBridge: `operation: 'PutEvents'` を使用し、`ctx.events` から確定的なイベントエントリを構築します。
- RDS: SQL ヘルパーと `createPgStatement`/`createMySQLStatement` を優先します。安全でない SQL を挿入しないでください。
- OpenSearch: リクエストのパス/パラメータを明示的に保ち、`ctx.result` からの必須フィールドのみをマップします。
- Bedrock: `operation` (`InvokeModel` または `Converse`) を明示的に定義し、プロンプト挿入の保護手段を含めます。

## バッチ操作 (必要なガイダンス)

- ターゲットデータ ソースがネイティブにサポートし、イベントセマンティクスでグループ化が可能な場合は、バッチ処理を優先します。
- ダイナモDB:
  - 非アトミックな一括操作には `batchGet`、`batchPut`、`batchDelete` を使用します。
  - アトミックな全か無かの動作が必要な場合は、`transactGet`、`transactWrite` を使用します。
  - リクエストごとのアイテム数を検証して制限します。大きなバッチをチャンクします。
- ラムダ：
  - イベント API JS ハンドラーリクエストでは `operation: 'Invoke'` とオプションの `invocationType` が使用されます。
  - ハンドラーリクエスト オブジェクトには Event API `BatchInvoke` オペレーションはありません。
  - 疑似バッチ Lambda パターンの場合、リストペイロードを 1 つの呼び出しに送信し、決定的な項目ごとの結果構造を返します。
- 順序を維持することで、明示的な保証が行われます。下流の消費者が順序に依存する場合、順序キーを保存して文書化します。

## セキュリティとデータの安全性

- `ctx.identity`、ヘッダー、およびペイロードフィールドを信頼できない入力として扱います。
- データソースごとに最小権限の IAM を適用します。
- 書き込み操作の前、および変換されたイベントの転送前に検証を追加します。
- ハンドラーコードにシークレットをハードコーディングしないでください。
- 公共で使用する場合は、デフォルトを控えめにしてください (無効な状態では拒否/無許可)。

## ツール、TypeScript、ビルド

- `@aws-appsync/eslint-plugin` (少なくとも `plugin:@aws-appsync/base`) を使用してください。
- TypeScript ツールが構成されている場合は、`plugin:@aws-appsync/recommended` を使用します。
- TypeScript は AppSync ランタイムによって直接実行されません。デプロイメントの前に、サポートされている JavaScript にトランスパイルします。
- 外部化された `@aws-appsync/utils` インポートとデバッグ用のソースマップをバンドルします。

## 可観測性と操作

- ハンドラーとデータソース統合の CloudWatch ロギングを有効にします。
- 構造化されたカーディナリティの低いフィールド (チャネル名前空間/パス、操作、リクエスト ID) を含むログ。
- 警告可能なシグナルを追加します: ハンドラーエラー、データソースエラー、レイテンシー回帰。
- 応答変換を決定論的に保ち、マルチイベントペイロードを使用してテストします。

## 最低限の品質チェックリスト

- [ ] APPSYNC_JS でサポートされるランタイム機能のみを使用します。
- [ ] `throw`、非同期/プロミスの使用、サポートされていないループ/制御構造はありません。
- [ ] エラーフローはランタイムでサポートされるユーティリティを使用し、機密性のないメッセージを返します。
- [ ] `onPublish` および `onSubscribe` の動作は明示的であり、テストされています。
- [ ] データソースのリクエスト/レスポンスマッピングは決定的であり、スキーマセーフです。
- [ ] Lambda/DynamoDB コントラクトが文書化され、検証されています。
- [ ] `@aws-appsync/eslint-plugin` によるリンティングが有効になっています。
