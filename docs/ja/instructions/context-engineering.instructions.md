# コンテキストエンジニアリング

GitHub Copilot がコードベースを理解し、より適切な提案を提供できるようにするための原則。

## プロジェクトの構造

- **わかりやすいファイルパスを使用してください**: `src/auth/middleware.ts` > `src/utils/m.ts`。 Copilot はパスを使用して意図を推測します。
- **関連コードを同じ場所に配置**: コンポーネント、テスト、タイプ、フックをまとめて配置します。 1 つの検索パターンで、関連するすべてのものが見つかるはずです。
- **インデックスファイルからパブリック API をエクスポート**: エクスポートされるのはコントラクトです。そうでないものは内部にあります。これは、コパイロットが境界を理解するのに役立ちます。

## コードパターン

- **推論よりも明示的な型を優先します**: 型の注釈はコンテキストです。 `function getUser(id: string): Promise<User>` は、`function getUser(id)` よりも多くのことを Copilot に伝えます。
- **セマンティック名を使用**: `activeAdultUsers` > `x`。自己文書化コードは、AI が読み取り可能なコードです。
- **定数を定義**: `MAX_RETRY_ATTEMPTS = 3` > マジックナンバー `3`。名前付きの値には意味があります。

## 副操縦士との連携

- **関連するファイルをタブで開いたままにする**: Copilot は、開いているタブをコンテキスト信号として使用します。認証に取り組んでいますか?認証関連のファイルを開きます。
- **意図的にカーソルを配置する**: Copilot はカーソル近くのコードを優先します。コンテキストが重要な場所にカーソルを置きます。
- **複雑なタスクには Copilot Chat を使用します**: インライン入力には最小限のコンテキストが含まれます。チャットモードではより多くのファイルが表示されます。

## コンテキストヒント

- **COPILOT.md ファイルを追加します**: Copilot が従うべきアーキテクチャの決定、パターン、規則を文書化します。
- **戦略的なコメントを使用する**: 複雑なモジュールの先頭に、フローまたは目的を簡単に説明します。
- **パターンを明示的に参照**: 「`src/api/users.ts` と同​​じパターンに従う」は、Copilot に具体的な例を示します。

## 複数ファイルの変更

- **最初にスコープを説明してください**: 変更を要求する前に、関連するすべてのファイルを Copilot に伝えます。 「ユーザーモデル、API エンドポイント、テストを更新する必要があります。」
- **段階的に作業**: 一度に 1 つのファイルを作成し、各変更を確認します。一度にすべてを求めないでください。
- **理解度の確認**: 「どのファイルを見る必要がありますか?」と尋ねます。複雑なリファクタリングの前に。

## 副操縦士が悩んでいるとき

- **コンテキストが欠落しています**: 関連するファイルをタブで開くか、コードスニペットを明示的に貼り付けます。
- **古い提案**: コパイロットには最近の変更が表示されない可能性があります。ファイルを再度開くか、セッションを再起動します。
- **一般的な回答**: より具体的にしてください。制約を追加し、フレームワークについて言及し、既存のコードを参照します。
