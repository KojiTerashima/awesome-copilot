## 1. 最新の Terraform とプロバイダーを使う
常に最新の安定版 Terraform と Azure プロバイダーを対象にします。コード内では、必須の Terraform とプロバイダーのバージョンを明示してこれを強制してください。新機能や修正を取り込むため、プロバイダーのバージョンは更新を保ちます。

## 2. コードを整理して構成する
Terraform の設定は、論理的にファイルを分けて構成します。

- リソースには `main.tf` を使う
- 入力には `variables.tf` を使う
- 出力には `outputs.tf` を使う
- 一貫した命名規則とフォーマット (`terraform fmt`) に従う

これにより、コードの見通しと保守性が向上します。

## 3. モジュールにカプセル化する

再利用可能なインフラコンポーネント群は Terraform モジュールでまとめます。複数の文脈で使うリソース群については、次のようにします。

- 独自の variables/outputs を持つモジュールを作成する
- コードを複製せず、そのモジュールを参照する
- これにより再利用性と一貫性を高める

## 4. 変数と出力を活用する

- 型と説明を付けた変数で、設定可能な値をすべて **パラメーター化** する
- 任意変数には適切な場合に **既定値を設定** する
- 他のモジュールや利用者が参照できるよう、主要なリソース属性を公開する **outputs を使う**
- 秘密情報を保護するため、**機微な値には sensitive を設定する**

## 5. プロバイダー選定 (AzureRM と AzAPI)

- 大半のケースでは **`azurerm` プロバイダーを使う**。安定性が高く、多くの Azure サービスをカバーできます
- 次のような場合に限って **`azapi` プロバイダーを使う**
  - ごく新しい Azure 機能が必要な場合
  - `azurerm` がまだ対応していないリソースが必要な場合
- **選定理由を** コードコメントで説明する
- 必要なら両方のプロバイダーを併用できますが、迷う場合は `azurerm` を優先します

## 6. 依存関係は最小限にする

- プロジェクトの範囲を超える追加プロバイダーやモジュールは、確認なしに **導入しない**
- 特殊なプロバイダー (`random`, `tls` など) や外部モジュールが必要な場合は、次を行う
  - 説明用のコメントを追加する
  - ユーザーの承認を得る
- インフラ構成はスリムに保ち、不必要な複雑さを避ける

## 7. 冪等性を確保する

- 同じ結果になるように繰り返し適用できる設定を書く
- **冪等でない操作を避ける**
  - apply のたびに実行されるスクリプト
  - 二重作成で競合し得るリソース
- **`terraform apply` を複数回実行して確認し**、2 回目が変更 0 件になることを確かめる
- ドリフトや外部変更は、リソースの lifecycle 設定や条件式で適切に扱う

## 8. ステート管理

- Terraform の state は、**リモート バックエンド** (state locking 付き Azure Storage など) を使って安全に保存する
- チームでの共同作業を可能にする
- **state ファイルは絶対に** ソース管理へコミットしない
- これにより競合を防ぎ、インフラの状態を一貫して保てます

## 9. ドキュメントと図を更新する

- **最新のドキュメントを維持する**
- コード変更時には、変数、出力、利用方法を反映して **README.md を更新する**
- 自動化には `terraform-docs` などのツール利用を検討する
- 重要な更新のたびに、インフラ変更を反映して **アーキテクチャ図を更新する**
- ドキュメントと図が整っていれば、チーム全体がインフラを理解しやすくなります

## 10. 変更を検証・テストする

- 変更適用前に **`terraform validate` を実行し**、`terraform plan` の出力を確認する
- エラーや意図しない変更を早期に検出する
- **自動チェックの導入を検討する**
  - CI パイプライン
  - pre-commit フック
  - フォーマット、lint、基本検証の強制
