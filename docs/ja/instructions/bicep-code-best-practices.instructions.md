## 命名規則

-   Bicep コードを記述するときは、すべての名前 (変数、パラメーター、リソース) に lowerCamelCase を使用してください。
-   リソースタイプを説明するシンボル名を使用します (例: 「storageAccountName」ではなく「storageAccount」)
-   「name」はリソースの名前ではなくリソースを表すため、シンボリック名での使用は避けてください。
-   接尾辞を使用して変数とパラメータを区別しないようにします。

## 構造と宣言

-   常に @description デコレータを使用してファイルの先頭でパラメータを宣言します
-   すべてのリソースに最新の安定した API バージョンを使用する
-   すべてのパラメータに説明的な @description デコレータを使用する
-   パラメータに名前を付けるための最小文字長と最大文字長を指定する

## パラメータ

-   テスト環境にとって安全なデフォルト値を設定します (低コストの価格帯を使用します)。
-   有効なデプロイメントをブロックしないように、@allowed デコレータは慎重に使用してください。
-   導入間で変更される設定にはパラメータを使用する

## 変数

-   変数は解決された値から自動的に型を推測します
-   複雑な式を含めるには、変数をリソースプロパティに直接埋め込むのではなく、変数を使用します。

## リソース参照

-   リソース参照には、reference() 関数や resourceId() 関数の代わりにシンボリック名を使用します。
-   明示的な dependOn ではなく、シンボリック名 (resourceA.id) を使用してリソースの依存関係を作成する
-   他のリソースからプロパティにアクセスするには、出力を通じて値を渡す代わりに「existing」キーワードを使用します。

## リソース名

-   uniqueString() でテンプレート式を使用して、意味のある一意のリソース名を作成します
-   一部のリソースでは数字で始まる名前が許可されないため、 uniqueString() の結果にプレフィックスを追加します。

## 子リソース

-   子リソースの過度のネストを避ける
-   子リソースのリソース名を構築する代わりに、親プロパティまたはネストを使用する

## 安全

-   出力にシークレットやキーを決して含めないでください
-   出力でリソースプロパティを直接使用する (例: storageAccount.properties.primaryEndpoints)

## ドキュメント

-   読みやすさを向上させるために、役に立つ // コメントを Bicep ファイル内に含めます
