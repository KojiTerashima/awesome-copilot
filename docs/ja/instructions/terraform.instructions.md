# Terraform 規約

## 一般的な指示

- インフラストラクチャーのプロビジョニングと管理には Terraform を使う。
- Terraform 設定はバージョン管理を使って管理する。

## セキュリティ

- Terraform とその provider は常に最新の安定版を使う。
  - セキュリティパッチや改善を取り込むため、Terraform 設定は定期的に更新する。
- 機密情報は、AWS Secrets Manager や SSM Parameter Store などを使って安全に保管する。
  - 資格情報やシークレットは定期的にローテーションする。
  - 可能な箇所ではシークレットローテーションを自動化する。
- AWS Secrets Manager や SSM Parameter Store に保存した値を参照するには AWS 環境変数を使う。
  - これにより、機密値を Terraform state file から排除できる。
- AWS 資格情報、API キー、パスワード、証明書、Terraform state などの機密情報をバージョン管理にコミットしてはならない。
  - 機密情報を含むファイルは `.gitignore` を使ってバージョン管理から除外する。
- Terraform 設定内の機密変数には常に `sensitive = true` を設定する。
  - これにより、Terraform の plan や apply の出力に機密値が表示されないようにできる。
- IAM role と policy を使ってリソースへのアクセスを制御する。
  - 権限割り当てでは最小権限の原則に従う。
- リソースへのネットワークアクセス制御には security group と network ACL を使う。
- 可能な限り、リソースは private subnet に配置する。
  - load balancer や NAT gateway のように直接インターネットアクセスが必要なリソースに限って public subnet を使う。
- 保存時および転送時の機密データには暗号化を使う。
  - EBS volume、S3 bucket、RDS instance では暗号化を有効にする。
  - サービス間通信には TLS を使う。
- Terraform 設定にセキュリティ脆弱性がないか、定期的にレビューし監査する。
  - `trivy`、`tfsec`、`checkov` のようなツールで Terraform 設定のセキュリティ問題をスキャンする。

## モジュール化

- インフラの主要コンポーネントごとに個別プロジェクトを使う。これにより:
  - 複雑さを下げられる
  - 設定の管理と保守が容易になる
  - `plan` と `apply` の実行が高速になる
  - コンポーネントごとに独立した開発とデプロイが可能になる
  - 関連のないリソースへの accidental change のリスクを減らせる
- 設定の重複を避けるため module を使う。
  - 関連するリソースと設定をカプセル化するために module を使う。
  - 複雑な設定を単純化し、可読性を高めるために module を使う。
  - module 間の循環依存を避ける。
  - 不要な抽象化レイヤーは避け、価値がある場合にのみ module を使う。
    - 単一リソースのためには module を使わず、関連するリソース群に対してのみ使う。
    - module の過度なネストは避け、階層は浅く保つ。
- インフラの重要情報を公開するには `output` ブロックを使う。
  - 出力は、他の module や設定利用者に有用な情報を提供するために使う。
  - 機密情報を output で公開するのは避け、含まれる場合は `sensitive = true` を設定する。

## 保守性

- 可読性、明確さ、保守性を優先する。
- 複雑な設定や、特定の設計判断を行った理由を説明するコメントを使う。
- 理解しやすい、簡潔で効率的、かつ Terraform らしい設定を書く。
- ハードコード値は避け、代わりに変数を使う。
  - 適切な場合は変数にデフォルト値を設定する。
- 既存リソースの情報取得には手動設定を要求するのではなく data source を使う。
  - これにより、エラーリスクを減らし、設定が常に最新であることを担保し、異なる環境へ適応しやすくなる。
  - 同一設定内で作成するリソースには data source を使わず、代わりに output を使う。
  - 不要な data source は避けるか削除する。`plan` と `apply` を遅くするためである。
- 複数箇所で使う値には `locals` を使い、一貫性を保つ。

## スタイルと書式

- リソース命名や構成には Terraform のベストプラクティスに従う。
  - リソース、変数、output には説明的な名前を使う。
  - すべての設定で一貫した命名規則を使う。
- 書式は **Terraform Style Guide** に従う。
  - インデントは一貫して使う (各レベル 2 スペース)。
- 関連するリソースは同じファイルにまとめる。
  - リソース群のファイル名には一貫した命名規則を使う (例: `providers.tf`、`variables.tf`、`network.tf`、`ecs.tf`、`mariadb.tf`)。
- 依存関係が明確になるよう、`depends_on` ブロックはリソース定義の先頭に置く。
  - 循環依存を避けるため、`depends_on` は必要な場合にのみ使う。
- リソースの生成ロジックを明確にするため、`for_each` と `count` ブロックもリソース定義の先頭に置く。
  - コレクションには `for_each`、数値反復には `count` を使う。
  - `depends_on` がある場合はその後に置く。
- `lifecycle` ブロックはリソース定義の末尾に置く。
- file 内の provider、変数、data source、resource、output は、移動しやすいようにアルファベット順に並べる。
- ブロック内では関連属性をまとめる。
  - 必須属性を任意属性より先に置き、各セクションには必要に応じてコメントを付ける。
  - 可読性向上のため、属性セクションの間は空行で区切る。
  - 各セクション内の属性は移動しやすいようにアルファベット順に並べる。
- 設定の論理セクションは空行で区切る。
- `terraform fmt` を使って設定を自動整形する。
- `terraform validate` を使って構文エラーを確認し、設定の妥当性を確保する。
- `tflint` を使ってスタイル違反を検出し、設定がベストプラクティスに従っていることを確認する。
  - 開発初期にスタイル問題を見つけるため、`tflint` は定期的に実行する。

## ドキュメント

- 変数と output には常に `description` と `type` 属性を含める。
  - 各変数と output の目的がわかるよう、明確で簡潔な説明を書く。
  - 変数には適切な型 (`string`、`number`、`bool`、`list`、`map`) を使う。
- Terraform 設定は適切な箇所でコメントによって文書化する。
  - コメントはリソースや変数の目的を説明するために使う。
  - 複雑な設定や判断を説明するためにコメントを使う。
  - 冗長なコメントは避け、価値と明確さを加えるものだけにする。
- 各プロジェクトには、概要と構成を示す `README.md` を含める。
  - 設定のセットアップ方法と利用方法の説明も含める。
- `terraform-docs` を使って設定のドキュメントを自動生成する。

## テスト

- Terraform 設定の機能を検証するテストを書く。
  - テストファイルには `.tftest.hcl` 拡張子を使う。
  - 正常系と異常系の両方をカバーするテストを書く。
  - テストは冪等にし、副作用なく何度でも実行できるようにする。
