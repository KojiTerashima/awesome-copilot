# エンタープライズオンボーディング

契約から価値実現までエンタープライズ顧客をオンボーディングするための4フェーズフレームワーク。目標は単なる本番稼働ではなく、Week 12で崖落ちしない持続的な活用です。

## 使うタイミング

**トリガー:**
- 「このエンタープライズ顧客をどうオンボーディングすればいい？」
- 「本番稼働はしたが活用が弱い」
- 「本番稼働の3か月後に顧客を失い続けている」
- 「POCから本番への移行」
- 「Week 4のゴースティングをどう防ぐ？」
- 「カスタマーサクセスのオンボーディングフレームワーク」

**コンテキスト:**
- エンタープライズまたはミッドマーケット案件
- 複雑な技術要件
- 複数ステークホルダーの関与
- 30〜90日の導入タイムライン
- 初年度チャーンのリスク

---

## コアフレームワーク

### 1. Week 4ゴースティング問題（とその防ぎ方）

**パターン:**

Week 1: キックオフコールは大成功。全員が前向き。  
Week 2-3: 技術ディスカバリー、要件収集。まだ順調。  
Week 4: 顧客から返信が来なくなる。会議がキャンセルされる。「忙しすぎる」。

**何が起きたのか？**

顧客側の社内アラインメントが取れる前にオンボーディングを始めてしまった。

**このプロジェクトを社内で誰が持っているのか？**
- 営業担当？（すでに次の案件へ）
- テクニカルチャンピオン？（本業が優先される）
- エグゼクティブスポンサー？（委任はするが推進しない）
- 誰もいない？（**ゴースティングの原因はこれ**）

**フレームワーク: 社内オーナー検証**

キックオフコール前に、次に答える:

**顧客側で次を担うのは誰か:**
- 週次プロジェクト会議に参加するか？（「招待済み」ではなく実際に出席する）
- 調達/法務/セキュリティの課題を解消できるか？（権限がある）
- エンドユーザーへの活用浸透を推進できるか？（影響力がある）
- 停滞時にエスカレーションできるか？（経営層へのアクセスがある）

**各項目で具体的な個人名を挙げられないなら、プロジェクトオーナーはいません。契約はあっても、推進する人がいない状態です。**

**どう修正するか:**

**営業 → CS引き継ぎ時（顧客キックオフ前）:**

営業担当は次を特定する:
- 主担当プロジェクトオーナー（役職ではなく名前）
- その人の稼働余力（専任か副業務か）
- その人の権限（障害を解消できるか）
- その人の動機（本人にとってのメリットは何か）

**明確なオーナーがいない場合:**

まだオンボーディングを開始しない。営業からエコノミックバイヤーへの紹介を依頼する:

「実装キックオフの前に、御社側で適切なプロジェクトオーナーがいることを確認したいです。経験上、毎週の推進を担う方がいると導入は成功しやすくなります。御社チームでどなたと連携するのが最適でしょうか？」

**よくあるミス:**

誰かが持つだろうと想定してしまうこと。明示的に確認する。名前が出てこないなら、その案件はリスクが高い。

### 2. 活用の崖（Week 12問題）

**パターン:**

Week 6で本番稼働。利用は急増。祝う。

Week 8: 利用が横ばい。  
Week 10: 利用が減少。  
Week 12: ピーク比で利用が50%減。

**なぜ起きるのか:**

本番稼働をゴールとして扱ったから。**本番稼働はスタートラインです。**

**持続的活用を生むもの:**

**違う:** 機能の網羅性、技術統合、トレーニング実施  
**正しい:** 継続的な価値提示、ユーザー成功事例、ユースケース拡張

**フレームワーク: 本番稼働後の活用ステージ**

**Week 1-6（実装）:** 動く状態にする  
- 指標: 技術セットアップ完了率（%）  
- オーナー: テクニカルリード

**Week 6-12（初期活用）:** 人に使ってもらう  
- 指標: アクティブユーザー数、利用頻度  
- オーナー: Enablement / DevRel

**Week 12-26（持続活用）:** 継続価値を証明する  
- 指標: ユースケース拡張、チーム内浸透  
- オーナー: カスタマーサクセス

**Week 26+（拡張）:** アカウント内で拡大する  
- 指標: 新規チーム、新規ユースケース、アップグレードトリガー  
- オーナー: アカウントエグゼクティブ + CS

**多くのチームが見落とす引き継ぎ:**

Week 6（本番稼働）→ Week 12（持続活用）

多くのCSチームは本番稼働を祝って次の顧客へ移る。**チャーンの種はこの時に植えられる。**

**Week 6-12でやること:**

**Week 7:** 初回価値レポート  
「初週にチームが達成した内容はこれです: [具体的指標]。Week 12の理想状態はこれです: [目標値]。」

**Week 9:** ユーザー成功事例  
「[チーム名]の[ユーザー名]は今週、[X時間削減/Yエラー削減]を達成しました。活用方法はこうです。」

**Week 11:** ユースケース拡張の会話  
「現在は[主要ユースケース]でご利用中です。同様のチームでは[隣接ユースケース]にも活用しています。検討してみますか？」

**よくあるミス:**

「本番稼働完了」を測って「持続的なアクティブ利用」を測らないこと。本番稼働は成功ではない。Week 26時点で活用が維持されていることが成功。

### 3. プレオンボーディング: 成功は最初の顧客コール前に作られる

**パターン:**

オンボーディング失敗の多くは、キックオフ前の抜け漏れに起因する。

**見落とされること:**

**営業からCSへのブリーフ不足:**
- 案件ドライバーが不明
- ステークホルダー構図が不明瞭
- 技術要件が推測のまま

**社内プロジェクトオーナー未特定:**
- CSが連絡しても誰も返答しない
- 会議が不適切な相手で設定される
- 意思決定が定着しない

**顧客のタイムラインが非現実的:**
- 2週間で本番稼働したい
- 技術セットアップは最低6週間必要
- Day 1から期待値がずれる

**フレームワーク: キックオフ前チェックリスト**

キックオフコールを設定する前に、次を検証する:

**アカウントインテリジェンス:**
- [ ] 営業引き継ぎ完了（案件ドライバー、ステークホルダー、技術要件）
- [ ] 過去のやり取り確認済み（デモメモ、提案書、メール）
- [ ] 組織構造をマッピング済み（チーム規模、レポートライン）
- [ ] ユースケース文書化済み（現在 + 将来）

**社内準備:**
- [ ] 社内Slackチャンネル作成済み（#account-[customer-name]）
- [ ] CRMのアカウントプラン更新済み
- [ ] プロジェクトプランテンプレート準備済み
- [ ] 役割アサイン済み（CSMリード、テクニカルリード、エグゼクティブスポンサー）

**顧客準備状況:**
- [ ] プロジェクトオーナーを実名で特定済み（「相手のDevRelチーム」ではない）
- [ ] 双方のエグゼクティブスポンサー確認済み
- [ ] タイムラインが現実的（相手目標 vs 自社標準タイムライン）
- [ ] 既知ブロッカーを文書化済み（調達、セキュリティ、法務）

**タイムライン検証:**
- [ ] 顧客の本番稼働希望日は技術要件を踏まえて現実的
- [ ] 社内キャパシティ確保済み（過剰アサインなし）
- [ ] 依存関係を特定済み（SSO、連携、データ移行）

**意思決定基準:**

4セクションすべてを検証できた時のみキックオフを設定。ギャップがある場合は、顧客対応前に営業またはエグゼクティブスポンサーへ共有する。

**よくあるミス:**

社内の明確化なしでオンボーディングを始めること。これが混乱、納期遅延、顧客信頼の低下を招く。

### 4. 4フェーズのオンボーディングフロー

**フェーズ1: キックオフ（Week 1）**

**目標:** 目的、タイムライン、成功指標を揃える

**参加者:** エグゼクティブスポンサー + プロジェクトリード + テクニカルリード

**アジェンダ:**
1. 自己紹介と役割（5分）
2. 戦略目標に関する経営レベルのアラインメント（5分）
3. 成功定義: 「3/6/12か月後の成功状態は？」（10分）
4. タイムラインとマイルストーン（5分）
5. 会議頻度（週次プロジェクトチーム、月次エグゼクティブレビュー）（5分）
6. 次アクション（技術ディスカバリーコール、サクセスプランレビュー）（5分）

**成果物:** 24時間以内にキックオフ要約を送付（成功指標、タイムライン、次回会議を記載）

**フェーズ2: ディスカバリー & 計画（Week 2-3）**

**目標:** 技術環境の把握、ユースケース整理、ロールアウト計画

**3つの並行ワークストリーム:**

**ワークストリーム1: 技術ディスカバリー**
- 現在のインフラ（オンプレ、クラウド、ハイブリッド）
- 既存ツールと連携
- セキュリティ/コンプライアンス要件
- タイムライン制約

**ワークストリーム2: サクセス計画**
- ユースケース優先順位付け（高価値から開始）
- 成功指標定義（活用をどう測るか）
- トレーニング要件特定（誰に何が必要か）

**ワークストリーム3: 技術セットアップ**
- SSO/ID設定
- 必要な連携
- データ移行（必要な場合）
- パイロットグループ特定

**成果物:** ユースケース、指標、タイムライン、マイルストーンを含むCustomer Success Planドキュメント

**フェーズ3: 実装（Week 4-6）**

**目標:** パイロットグループへ展開し、ユースケースを検証し、広範囲ロールアウトに備える

**3つの並行トラック:**

**トラック1: 管理・設定**
- SSO設定完了
- 連携稼働
- データ移行完了（必要な場合）

**トラック2: ユーザー有効化**
- パイロットグループ向けトレーニング実施
- ドキュメント共有
- オフィスアワー設定

**トラック3: パイロット & フィードバック**
- パイロットグループが製品利用
- 毎週フィードバック収集
- 課題をトリアージし解決

**成果物:** 本番稼働準備チェックリスト完了、パイロットグループ検証完了

**フェーズ4: 本番稼働 & 継続的成功（Week 6+）**

**目標:** 広範囲へ展開し、活用を維持し、ユースケースを拡張する

**Week 6-8（ロールアウト）:**
- 全チームへの広範囲ロールアウト
- トレーニングセッション設定
- サポート提供（Slack、メール、オフィスアワー）

**Week 8-12（価値実証）:**
- 初回価値レポート（Week 7）
- ユーザー成功事例共有（Week 9）
- ユースケース拡張の会話（Week 11）

**Week 12-26（持続活用）:**
- 月次ビジネスレビュー
- 活用トラッキング（アクティブユーザー、頻度、ユースケース）
- 拡張機会の特定

**よくあるミス:**

本番稼働を完了と見なすこと。維持率の勝敗はフェーズ4で決まる。

### 5. 並行トラックのアンチパターン

**パターン:**

多くのオンボーディングチームはワークストリームを**直列**で進める:
1. 技術セットアップ（Week 1-2）
2. 次にトレーニング（Week 3-4）
3. 次にパイロット（Week 5-6）

**合計期間: 6週間**

**より良い方法: 並行トラック**

技術セットアップ、トレーニング、パイロットを**同時並行**で進める:
- Week 1: 技術ディスカバリー + パイロットグループ特定 + トレーニング設定
- Week 2: SSO設定 + パイロットグループトレーニング + パイロット開始
- Week 3: 連携 + 広範囲トレーニング + パイロットフィードバック

**合計期間: 3週間**

**並行が効く理由:**

1. 価値実現までの時間を短縮できる  
2. 顧客の関与を維持できる（毎週何かが進む）  
3. ブロッカーを早期に発見できる（広範囲展開前にパイロットが課題を顕在化）

**実行方法:**

各トラックに明確な責任者を割り当てる:
- トラック1（Admin）: テクニカルリード
- トラック2（Enablement）: トレーニング/DevRelリード
- トラック3（Pilot）: CSM + パイロットグループチャンピオン

依存関係とブロッカーを可視化するため、トラック横断の週次同期を行う。

**よくあるミス:**

「技術セットアップが完璧になるまで」パイロットを待つこと。設定が不完全でも早期にパイロット利用を始める。彼らのフィードバックで広範囲展開はより良くなる。

## 意思決定ツリー

### 顧客オンボーディングを開始すべきか？

```
Salesはプロジェクトオーナーを実名で特定しているか？
├─ No → キックオフ前にプロジェクトオーナーを特定する
└─ Yes → 続行...
    │
    相手のタイムラインは通常の導入を踏まえて現実的か？
    ├─ No → キックオフ前に期待値を再調整する
    └─ Yes → 続行...
        │
        社内キャパシティはあるか？
        ├─ No → キックオフを遅らせるか、追加リソースを確保する
        └─ Yes → キックオフへ進む
```

### このオンボーディングはリスク状態か？

```
顧客は会議招待に応答しているか？
├─ No → Week 4ゴースティング、エグゼクティブスポンサーへエスカレーション
└─ Yes → 続行...
    │
    相手は自分たちのアクションアイテムを完了しているか？
    ├─ No → プロジェクトオーナー不在、誰が推進するかを特定
    └─ Yes → 続行...
        │
        パイロットグループは製品を使っているか？
        ├─ No → パイロットグループ不適切、または製品が課題を解決していない
        └─ Yes → 順調
```

### 本番稼働後の活用は維持されているか？

```
アクティブユーザーはWeek 6 → Week 12で増加しているか？
├─ Yes → 健全な活用
└─ No → 続行...
    │
    アクティブユーザーは減少しているか？
    ├─ Yes → 活用崖、直ちに介入
    └─ No（横ばい）→ リスクあり、価値実証を開始
```

## よくあるミス

**1. 社内アラインメント前に顧客オンボーディングを開始する**  
   - 最初の2〜3週間を浪費し、混乱を生み、信頼を失う

**2. 実質的なプロジェクトオーナーを最初に特定しない**  
   - Week 4で発覚し、再開始か停滞に陥る

**3. 技術要件確認なしでタイムラインを過剰約束する**  
   - 実装途中でブロッカーが発覚し、納期遅延になる

**4. 社内コミュニケーションハブがない**  
   - 意思決定がチーム横断で伝播せず、手戻りが発生する

**5. 本番稼働をプロジェクト完了と扱う**  
   - Week 12で活用崖が発生し、アカウントが危険になる

**6. 並行ではなく直列で進める**  
   - 実装期間が2倍かかり、顧客の勢いを失う

**7. 本番稼働後の継続指標がない**  
   - 活用問題の発見が遅れ、アカウントを救えない

## クイックリファレンス

**キックオフ前検証:**
- [ ] 営業引き継ぎ完了（案件ドライバー、ステークホルダー、要件）
- [ ] 顧客側プロジェクトオーナーを実名で特定
- [ ] タイムラインが現実的（相手目標 vs 標準導入）
- [ ] 社内役割を割り当て済み（CSM、技術、エグゼクティブスポンサー）

**キックオフアジェンダ（30〜45分）:**
1. 自己紹介（5分）
2. 経営アラインメント（5分）
3. 成功定義（10分）
4. タイムラインとマイルストーン（5分）
5. 会議頻度（5分）
6. 次アクション（5分）

**活用トラッキング（Week 6-26）:**
- Week 7: 初回価値レポート
- Week 9: ユーザー成功事例
- Week 11: ユースケース拡張の会話
- Week 13: 初回月次ビジネスレビュー
- Week 26: 拡張準備度評価

**4フェーズ:**
1. キックオフ（Week 1）: 揃える
2. ディスカバリー（Week 2-3）: 計画する
3. 実装（Week 4-6）: パイロットへ展開
4. 本番稼働 & 持続（Week 6+）: ロールアウト、価値実証、拡張

**レッドフラグ:**
- Week 4で顧客が無反応 → プロジェクトオーナー不在
- Week 5でパイロットグループが未利用 → グループまたはユースケースが不適切
- Week 8-12でアクティブユーザー減少 → 活用崖が形成中

*複数のプラットフォーム企業におけるエンタープライズオンボーディングの実践に基づく。パートナーオンボーディングを直接設計し、顧客オンボーディングでCSと密接に連携して得た知見。理論ではなく、Week 4のゴースティングが繰り返し起きる現場を見て学んだ教訓であり、本番稼働 ≠ 成功であること、そして初年度に案件の30%を失わせる活用崖を理解したうえでの内容。*
