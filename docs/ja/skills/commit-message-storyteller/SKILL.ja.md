# メッセージストーリーテラーのコミット

生の git diff と変更の説明を、[Conventional Commits](https://www.conventionalcommits.org/) 仕様に準拠した明確なストーリー主導のコミット メッセージに変換します。 「update file.js」の代わりに、意図、コンテキスト、影響を伝えるメッセージが表示されます。

## このスキルをいつ使用するか

- ユーザーが「コミット メッセージを書いて」、「コミットを手伝って」、または「コミットを生成して」と言った
- ユーザーが git diff を貼り付けるか、コードの変更を説明する
- ユーザーは「これを何としてコミットすればよいですか?」と言います。または「差分を要約してください」
- ユーザーはチームまたはオープンソース プロジェクトのコミット履歴を改善したいと考えています
- ユーザーはプルリクエストを準備しており、意味のあるコミットメッセージを必要としています

## 前提条件

次のうち少なくとも 1 つを準備してください。
- `git diff` または `git diff --staged` からの出力
- 変更した内容とその理由の説明
- 変更されたファイルのリスト

## 仕組み

### ステップ 1: 変更コンテキストを収集する

ユーザーに次のことを尋ねます (または差分から推測します)。

1. **変更内容** — 影響を受けるファイル、関数、ロジック
2. **変更の理由** — バグ修正、新機能、リファクタリング、パフォーマンスなど。
3. **誰/何がトリガーしたのか** — 問題番号、ユーザーのリクエスト、技術的負債など。

ユーザーが生の `git diff` を提供した場合、このコンテキストは diff から自動的に抽出されます。

### ステップ 2: コミット タイプを特定する

このガイドを使用して、変更を従来のコミット タイプにマッピングします。

|タイプ |いつ使用する |
|------|----------|
| `feat` |新しい機能または機能が追加されました |
| `fix` |バグまたは不正な動作が修正されました |
| `refactor` |動作を変更せずにコードを再構築 |
| `perf` |パフォーマンスを向上させる変更 |
| `docs` |ドキュメントのみが変更されます |
| `style` |書式設定、空白、セミコロンの欠落 (ロジックの変更なし) |
| `test` |テストの追加または更新 |
| `chore` |ビルド プロセス、依存関係の更新、構成の変更 |
| `ci` | CI/CD パイプラインの変更 |
| `revert` |以前のコミットを元に戻す |

詳細な例については、`references/conventional-commits-guide.md` を参照してください。

### ステップ 3: コミットメッセージを作成する

次の構造に従います。
```
<type>(<optional scope>): <short imperative summary>

<body — the story: why this change was made, what problem it solves>

<footer — issue refs, breaking change notices>
```

#### 各部のルール

**件名 (最初の行):**
- 命令形を使用します: 「追加」、「修正」、「削除」 — 「追加」や「修正」ではありません
- 最大72文字
- 最後にピリオドはありません
- コロンの後に小文字

**本文 (ストーリー):**
- 「何を」ではなく、「なぜ」を説明してください (差分にはすでに内容が示されています)
- この変更の前に存在した問題について説明してください
- 関連する場合、検討された代替案について言及する
- 行数は 100 文字未満にしてください
- 件名と空白行で区切る

**フッター:**
- 参照問題: `Closes #123`、`Fixes #456`、`Refs #789`
- 重大な変更をマークする: `BREAKING CHANGE: <description>`

### ステップ 4: 出力の生成

コピー可能なコード ブロックでコミット メッセージを作成し、その後に、話した内容を簡単な英語で 1 行説明します。

**出力例:**
```
fix(auth): prevent token refresh loop on expired sessions

When a user's session expired mid-request, the auth middleware was
triggering a token refresh, which itself failed validation and triggered
another refresh — causing an infinite retry loop that crashed the app.

This adds a recursion guard flag that aborts the refresh cycle if a
refresh is already in progress, returning a clean 401 instead.

Closes #312
```

> **ストーリー:** セッションの期限切れ時のサイレント無限ループによりアプリがクラッシュしていました。これによりサイクルが早期に停止され、クリーンなエラーが返されます。

## 1 つの差分からの複数のコミット

diff に **論理的に別々の変更**が含まれている場合は、それらを複数のコミット メッセージに分割してユーザーに伝えます。このヒューリスティックを使用します。

- 無関係な目的を持つ異なるファイル → 別々のコミットになる可能性が高い
- 同じファイルだが異なる懸念事項 (例: バグ修正 + リファクタリング) → 分割を提案
- すべてが密結合 → 1 つのコミットで問題ありません

## エッジケース

|状況 |取り扱い方法 |
|----------|------|
|ユーザーは diff | 以外のコンテキストを提供しません。ファイル名と変更されたシンボルからタイプとスコープを推測する |
|変更は多くのファイルにまたがり、明確なテーマはありません。 「これは論理的な変更が 1 つですか、それとも複数ですか?」と尋ねます。 |
|重大な変更が検出されました | `BREAKING CHANGE:` フッターを自動的に追加 |
|ユーザーが「短くしてください」と言う |本文を省略し、強力な件名だけを書きます |
|発行番号がありません |フッターを完全に省略する |

## クイックリファレンス
```bash
# Get your staged diff to paste into Copilot
git diff --staged

# Or get the last uncommitted working tree changes
git diff
```

型の例とスコープのガイドラインについては、`references/conventional-commits-guide.md` を参照してください。
