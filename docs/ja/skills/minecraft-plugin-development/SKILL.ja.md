# Minecraft プラグイン開発

このスキルは、Paper、Spigot、および Bukkit エコシステムでの Minecraft サーバー プラグインの作業に使用します。

このスキルは、戦闘システム、ウェーブまたはボスとの遭遇、戦争またはチーム モード、アリーナ、キット システム、クールダウン ベースのアビリティ、スコアボード、構成主導のゲーム ルールなど、ゲームプレイに重点を置くプラグインに特に役立ちます。

実際の Paper プラグインから描画された根拠のある実装パターンの場合は、必要に応じて次の参照をロードします。

- 実際のゲームプレイ プラグインで見られる高レベルのアーキテクチャ パターンについては [`references/project-patterns.md`](references/project-patterns.md)
- [`references/bootstrap-registration.md`](references/bootstrap-registration.md) `onEnable`、コマンド配線、リスナー登録、およびシャットダウンの期待
- [`references/state-sessions-and-phases.md`](references/state-sessions-and-phases.md) プレーヤー セッション モデリング、ゲーム フェーズ、試合状態、再接続セーフ ロジック用
- [`references/config-data-and-async.md`](references/config-data-and-async.md) 構成マネージャー、データベースベースのプレーヤー データ、非同期フラッシュ、UI 更新タスク用
- [`references/maps-heroes-and-feature-modules.md`](references/maps-heroes-and-feature-modules.md) マップの回転、ヒーローまたはクラス システム、モジュール機能の拡張用
- [`references/minigame-instance-flow.md`](references/minigame-instance-flow.md) アリーナ インスタンス、カウントダウン、戦利品の更新、ウェーブ システム、可視性の分離、エンティティとゲーム間の所有権
- [`references/persistent-progression-and-events.md`](references/persistent-progression-and-events.md) プロファイル、特典、バフ、クエスト、エコノミー、カスタム ドメイン イベント、拡張レジストリを備えた長期実行 PvP サーバー用
- [`references/build-test-and-runtime-validation.md`](references/build-test-and-runtime-validation.md) Maven または Gradle のパッケージ化、シェーディングされた依存関係、生成されたリソース、ソフト依存関係、構成検証コマンド、および最初のラウンドのサーバー テスト計画

## 範囲

- 対象範囲: Paper、Spigot、Bukkit プラグイン開発
- 対象範囲: `plugin.yml`、コマンド、タブ補完、リスナー、スケジューラ、構成、権限、アドベンチャー テキスト、プレイヤー状態、ミニゲーム フロー、アリーナ インスタンス、マップ コピー、戦利品、ウェーブ、永続プロファイル、特典、バフ、クエスト、経済、PvP/PvE ゲーム ループ
- 範囲: Java ベースのサーバー プラグイン アーキテクチャ、デバッグ、リファクタリング、機能実装
- デフォルトでは範囲外: ファブリック MOD、Forge MOD、クライアント MOD、Bedrock アドオン

ユーザーが「Minecraft プラグイン」と言ったが、スタックが不明瞭な場合は、まずプロジェクトが Paper/Spigot/Bukkit なのか、それとも MOD スタックなのかを判断します。

## デフォルトの作業スタイル

このスキルが発動すると:

1. サーバー API とバージョンのターゲットを特定します。
2. ビルド システムと Java バージョンを特定します。
3. `plugin.yml`、メインのプラグイン クラス、およびコマンドまたはリスナーの登録を検査します。
4. コードを編集する前にゲームプレイ フローをマップします。
   - プレーヤーのライフサイクル
   - ゲームフェーズ
   - タイマーとスケジュールされたタスク
   - チーム、アリーナ、試合の状態
   - 構成と永続性
5. 登録、構成、および実行時の動作の整合性を保つために、最小限の一貫した変更を加えます。

プラグインがゲームプレイを重視するかステートフルである場合は、編集する前に [`references/project-patterns.md`](references/project-patterns.md) と [`references/state-sessions-and-phases.md`](references/state-sessions-and-phases.md) を読んでください。

タスクがアリーナの分離、マップ インスタンス、チェストまたはリソースの補充、ウェーブの生成、ルート投票、観客の可視性、またはゲーム固有のチャットに関わる場合は、[`references/minigame-instance-flow.md`](references/minigame-instance-flow.md) もお読みください。

タスクが永続的なプレイヤーの進行状況、プロフィールの保存、経済報酬、特典、バフ、クエスト、カスタム戦闘イベント、または長時間実行される共有 PvP サーバーに関わる場合は、[`references/persistent-progression-and-events.md`](references/persistent-progression-and-events.md) もお読みください。

タスクがビルド ファイル、`plugin.yml` メタデータ、シェーディングされた依存関係、生成されたリソース出力、テスト サーバーへのデプロイメント、オプションのプラグイン統合、またはリリース検証に関わる場合は、[`references/build-test-and-runtime-validation.md`](references/build-test-and-runtime-validation.md) もお読みください。

## コアルール

### リポジトリ内の具体的なサーバー API を優先します

- プロジェクトがすでに Paper API をターゲットにしている場合は、互換性が明示的に必要でない限り、汎用 Bukkit にダウングレードするのではなく、Paper ファースト API を使い続けてください。
- API がすべてのバージョンに存在すると想定しないでください。まず、既存の依存関係と周囲のコード スタイルを確認してください。

### 登録の同期を保つ

コマンド、権限、またはリスナーを追加するときは、同じ変更で関連する登録ポイントを更新します。

- @@コード0@@
- `onEnable` でのプラグイン起動登録
- コード内の権限チェック
- 関連する設定キーまたはメッセージ キー

### メインスレッドの境界を尊重する

- API が明示的に許可しない限り、非同期タスクから世界の状態、エンティティ、インベントリ、スコアボード、またはほとんどの Bukkit API オブジェクトに触れないでください。
- 外部 I/O、大量の計算、データベース作業には非同期タスクを使用し、ゲームプレイの変更を適用する前にメイン スレッドに戻します。

### 散在するブール値ではなく、状態としてゲームプレイをモデル化します。

ゲームプレイ プラグインの場合は、重複したフラグよりも明示的な状態オブジェクトを優先します。

- 試合またはゲームフェーズ
- プレイヤーの役割またはクラス
- クールダウン状態
- チームメンバーシップ
- アリーナの割り当て
- 生存、排除、観戦、または待機状態

この機能が試合の多いミニゲームや永続的な乱闘ゲームプレイに影響を与える場合は、症状にパッチを当てる前に、まず隠れた状態遷移を探してください。

マルチアリーナ プラグインの場合、ゲームごとの可視性、チャット受信者、スコアボード、戦利品、およびエンティティの所有権を分離します。あるアリーナが別のアリーナを誤って観察したり、突然変異させたりしないでください。

### 構成主導の値を優先する

機能にダメージ、クールダウン、報酬、期間、メッセージ、マップ設定、または切り替えが含まれる場合:

- ハードコーディングよりも構成に基づいた値を優先する
- 賢明なデフォルトを提供する
- キー名を安定して読みやすい状態に保つ
- 欠損値を検証またはサニタイズする

### リロード動作に注意してください

- コードがすでに十分にサポートしている場合を除き、安全なホット リロードを約束することは避けてください。
- 構成のリロード時に、メモリ内キャッシュ、スケジュールされたタスク、およびゲームプレイ状態が一貫して処理されることを確認します。

## 実装パターン

### コマンド

新しいコマンドの場合:

- コマンドを `plugin.yml` に追加します
- 必要に応じてエグゼキュータとタブ補完を実装する
- `Player` にキャストする前に送信者のタイプを検証してください
- 個別の解析、権限チェック、ゲームプレイ ロジック
- 無効な使用に対して明確なプレイヤー向けフィードバックを送信する

最小登録形状:
```yaml
commands:
  arena:
    description: Join or leave an arena
    usage: /arena <join|leave>
```
```java
@Override
public void onEnable() {
    ArenaCommand command = new ArenaCommand(gameService);
    PluginCommand arena = getCommand("arena");
    if (arena != null) {
        arena.setExecutor(command);
        arena.setTabCompleter(command);
    }
}
```

### リスナー

イベントリスナーの場合:

- 早く守って早く帰る
- 現在のプレイヤー、アリーナ、またはゲームフェーズがイベントを処理する必要があるかどうかを確認します
- 移動、損傷、スパムのやり取りなどのホットなイベントでの高コストの作業を避ける
- 繰り返し行われるチェックを現実的な場合には一元化する

### スケジュールされたタスク

タイマー、ラウンド、カウントダウン、クールダウン、定期チェックの場合:

- キャンセルが重要な場合はタスク ハンドルを保存する
- プラグインが無効になったとき、および試合またはアリーナが終了したときにタスクをキャンセルします
- 明示的に意図されていない限り、同じゲームプレイに関する複数の重複タスクを避ける
- 緩く調整された多くの繰り返しタスクよりも、権威のある 1 つのゲーム ループを好む
- ゲームが予期した状態を離れたときにカウントダウンまたは補充タスクが自動的にキャンセルされるようにする

メインスレッドのハンドオフ形状:
```java
Bukkit.getScheduler().runTaskAsynchronously(plugin, () -> {
    PlayerData data = repository.load(playerId);
    Bukkit.getScheduler().runTask(plugin, () -> {
        Player player = Bukkit.getPlayer(playerId);
        if (player != null && player.isOnline()) {
            scoreboard.update(player, data);
        }
    });
});
```

### プレーヤーと試合の状態

プレーヤーごとまたは試合ごとの状態の場合:

- 所有権を明確に定義する
- 終了、キック、デス、マッチ終了、プラグイン無効時のクリーンアップ
- `Player` をキーとする古いマップからのメモリ リークを回避します
- ライブ プレーヤー オブジェクトが厳密に必要でない限り、永続的な追跡には `UUID` を優先します

### テキストとメッセージ

プロジェクトで Adventure または MiniMessage を使用する場合:

- 既存の書式設定アプローチに従う
- 従来のカラーコードとアドベンチャー スタイルを理由なく混合することは避けてください。
- メッセージがゲームプレイ向けである場合、メッセージ テンプレートを構成可能な状態に保つ

## 高リスクエリア

編集するときは特に注意してください。

- ダメージ処理とカスタム戦闘ロジック
- 死亡、リスポーン、観客、排除の流れ
- アリーナの参加と退出の流れ
- スコアボードまたはボスバーの更新
- 在庫の突然変異とキットの配布
- 非同期データベースまたはファイルアクセス
- 経済、クエスト、特典、プロファイルの突然変異
- カスタム イベント ディスパッチまたは拡張レジストリ
- バージョン依存の API 呼び出し
- `onDisable` でのシャットダウンとクリーンアップ
- アリーナ間の可視性、チャット、ブロードキャストの分離
- マップのコピー、アンロード、フォルダー削除ロジック
- Mob、NPC、発射物、または一時的なエンティティの所有権
- チェストまたはリソース補充システム

## 期待される出力

プラグイン コードを実装または修正する場合:

- ユーザーがデザインのみを要求しない限り、疑似コードではなく、実行可能な Java コードを生成します。
- `plugin.yml`、構成ファイル、ビルドファイル、またはリソースに対する必要な更新について言及します
- バージョンの仮定を明示的に呼び出す
- スレッドセーフまたは API 互換性のリスクが存在する場合はそれを指摘します
- プロジェクトの既存の規則とフォルダー構造を維持する

要求された変更がプラグインの起動、非同期データ、マッチ フロー、クラス システム、または回転マップに関わる場合は、編集する前に一致する参照ファイルを参照してください。

## 検証チェックリスト

終了する前に、タスクで可能な限り多くのことを確認してください。

- コマンド、リスナー、または機能が正しく登録されている
- `plugin.yml` は実装された動作と一致します
- インポートと API タイプがターゲットのサーバー スタックと一致する
- スケジューラーの使用は安全です
- コード内で参照されている構成キーが存在するか、デフォルトが設定されています
- マッチ終了、プレーヤー終了、プラグイン無効化の状態クリーンアップ パスが存在します。
- アリーナごとのチャット、可視性、スコアボード、ブロードキャストは分離されています
- 一時的なワールド、モブ、タスク、生成されたリソースがクリーンアップされます
- 明らかな null、cast、またはライフサイクルの危険はない

## よくある落とし穴

- `CommandSender` をチェックせずに `Player` にキャストします
- 非同期タスクからの Bukkit 状態の更新
- リスナーの登録または `plugin.yml` でのコマンドの宣言を忘れている
- `UUID` の方が安全な場合、`Player` オブジェクトを長期マップ キーとして使用する
- ラウンド、アリーナ、またはプラグインのシャットダウン後に繰り返しタスクを存続させたままにする
- 設定内に存在する必要があるゲームプレイ定数をハードコーディングする
- Spigot を対象としたプラグインで Paper のみの API を想定する
- ステートフル プラグインがリロード中に壊れることが多いにもかかわらず、リロードを無料として扱う
- 無関係なゲーム インスタンス間でのブロードキャスト、プレーヤーの表示、またはスコアボードの変更の適用
- チャンクが利用可能になる前にチェスト/コンテナ ブロックをロードまたは変更する
- スポーンされたモブまたは一時的なエンティティを所有するゲームから登録解除するのを忘れる
- `src/main/resources` の下のソース ファイルではなく、`target/classes` または `build/resources` の下にある生成ファイルを編集する

## 推奨される応答形状

実質的なリクエストの場合、構造は次のように機能します。

1. 現在のプラグインのコンテキストと前提条件
2. ゲームプレイまたはライフサイクルへの影響
3. コードの変更
4. 必要な登録または構成の更新
5. 検証と残されたリスク

小さなリクエストの場合は、回答を簡潔にして、必要な `plugin.yml`、設定、またはライフサイクルの更新についても言及してください。
