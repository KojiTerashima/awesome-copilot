# GDPRエンジニアリングスキル

エンジニア、アーキテクト、DevOps、テックリード向けの実践的なGDPRリファレンス。  
CNILの開発者向けガイダンスおよびGDPR第5条、第25条、第32条、第33条、第35条に着想を得ています。

> **黄金律:** 収集を減らす。保存を減らす。露出を減らす。保持を減らす。

詳細は `references/` の参照ファイルを確認してください:
- `references/data-rights.md` — ユーザー権利エンドポイント、DSRワークフロー、RoPA
- `references/security.md` — 暗号化、ハッシュ化、シークレット、匿名化
- `references/operations.md` — クラウド、CI/CD、インシデント対応、アーキテクチャパターン

---

## 1. GDPRの中核原則（第5条）

| 原則 | エンジニアリング上の義務 |
|---|---|
| 適法性、公正性、透明性 | すべての処理活動について法的根拠をRoPAに文書化する |
| 目的限定 | 目的Aのために収集したデータを、新たな法的根拠なしに目的Bへ再利用しては**ならない** |
| データ最小化 | 現時点で文書化された業務上の必要性がある項目のみを収集する |
| 正確性 | 更新用エンドポイントを提供し、修正を下流ストアへ伝播させる |
| 保存期間の制限 | TTLはスキーマ設計時に定義する — 後付けは不可 |
| 完全性と機密性 | 保存時・転送時に暗号化し、アクセスを制限・監査する |
| 説明責任 | 準拠の証跡を維持し、RoPAをいつでもDPA検査に提示できる状態にする |

---

## 2. プライバシー・バイ・デザイン & デフォルト

**必須（MUST）**
- 個人データを保持するすべてのテーブルに、作成時点で `CreatedAt`、`RetentionExpiresAt` を追加する。
- 任意のデータ収集はすべてデフォルトを **off** にする。ユーザーはオプトインするのであり、デフォルトオンからのオプトアウトではない。
- 高リスク処理（生体情報、健康データ、大規模プロファイリング、体系的監視）を構築する前に **DPIA** を実施する。
- 処理活動を導入する新機能ごとに **RoPA** を更新する。
- データを流す前に、すべてのサブプロセッサーと **DPA** を締結する。

**禁止（MUST NOT）**
- 法的根拠を文書化せずに新しいデータ収集機能をリリースする。
- 明示的同意なしに、アナリティクス、トラッキング、テレメトリをデフォルト有効にする。
- RoPAに記載されていないシステムへ個人データを保存する。

---

## 3. データ最小化

**必須（MUST）**
- すべてのDTO/モデル項目を、具体的な業務上の必要性に対応付ける。未文書化の項目は削除する。
- 作成・参照・更新で **別々のDTO** を使う — 同じオブジェクトを使い回さない。
- 呼び出し元に権限のある情報のみ返す — レスポンス投影を使う。
- 境界で機微値をマスクする: カード番号は `****1234` を返し、完全値は返さない。
- 機微項目（DOB、国民ID、健康情報）をデフォルトの一覧/検索投影から除外する。

**禁止（MUST NOT）**
- 個人データを含む可能性がある場合に、リクエスト/レスポンス本文全体をログ出力する。
- URLパスセグメントやクエリパラメータに個人データを含める（CDNログ、ブラウザ履歴）。
- 明示的な法的根拠なしに `dateOfBirth`、国民ID、健康データを収集する。

---

## 4. 目的限定

**必須（MUST）**
- すべての処理活動の目的を、コードコメントとRoPAの両方に文書化する。
- 二次利用前に、新たな法的根拠を取得するか適合性分析を実施する。

**禁止（MUST NOT）**
- サービス提供目的で収集した個人データを、明示的同意なしに広告ネットワークへ共有する。
- 別個の法的根拠とユーザー通知なしに、サポートチケット内容をMLモデル学習に使う。

---

## 5. 保存期間制限と保持

**必須（MUST）**
- 個人データを保持するすべてのテーブルに、定義済みの保持期間が **必須**。
- 保持はスケジュールジョブ（Hangfire、cron）で自動実施する — 手動運用は禁止。
- 保持期限切れ時にデータを匿名化または削除する — 期限切れデータを本番に黙って残さない。

**推奨デフォルト**

| データ種別 | 最大保持期間 |
|---|---|
| 認証 / 監査ログ | 12〜24か月 |
| セッション / リフレッシュトークン | 30〜90日 |
| メール / 通知ログ | 6か月 |
| 非アクティブユーザーアカウント | 最終ログインから12か月 → 通知 → 削除 |
| 支払い記録 | 税法要件に従う（7〜10年）、最小化する |
| 分析イベント | 13か月 |

**推奨（SHOULD）**
- `RetentionExpiresAt` カラムを追加し、insert時に計算する。
- 削除要求猶予期間（30日）後にスケジュールされたハード削除を伴うソフト削除（`DeletedAt`）を使う。

**禁止（MUST NOT）**
- 「後で役立つかもしれない」として個人データを無期限に保持する。

## 6. API設計ルール

**必須（MUST）**
- URLパスまたはクエリパラメータに個人データを含めてはならない。
  - `GET /users/{userId}`
- 個人データを返す/受け取るすべてのエンドポイントを認証する。
- 操作ユーザーの識別はJWTから抽出する — リクエスト本文から取得しない。
- すべてのリソースで所有権を検証する: `if (resource.OwnerId != currentUserId) return 403`。
- UUIDまたは不透明な識別子を使う — 公開リソースIDに連番整数を使わない。

**推奨（SHOULD）**
- 機微エンドポイント（ログイン、データエクスポート、パスワードリセット）にレート制限を設定する。
- `Referrer-Policy: no-referrer` と明示的な `CORS` 許可リストを設定する。

**禁止（MUST NOT）**
- APIレスポンスにスタックトレース、内部パス、DBエラーを返す。
- 認証付きAPIで `Access-Control-Allow-Origin: *` を使う。

---

## 7. ロギングルール

**必須（MUST）**
- アプリケーションログ内のIPを匿名化する — 最後のオクテット（IPv4）または最後の80ビット（IPv6）をマスクする。
  - `192.168.1.xxx`
- ログ出力禁止: パスワード、トークン、セッションID、資格情報、カード番号、国民ID、健康データ。
- PIIが含まれる可能性がある箇所で、リクエスト/レスポンス本文全体をログ出力してはならない。
- ログ保持を強制し、定義済み期間後に自動削除する。

**推奨（SHOULD）**
- データではなく **イベント** を記録する: `"User {UserId} updated email"` であり `"Email changed from a@b.com to c@d.com"` ではない。
- 構造化ログ（JSON）を使い、`userId` はメールアドレスではなく内部識別子として使う。
- 監査ログ（機微アクセス、管理者操作）とアプリケーションログを分離する — 保持期間とACLを別にする。

---

## 8. エラーハンドリング

**必須（MUST）**
- 汎用的なエラーメッセージを返す — スタックトレース、内部パス、DBエラーは公開しない。
  - `"Column 'email' violates unique constraint on table 'users'"`
  - `"A user with this email address already exists."`
- すべてのエラーレスポンスに **Problem Details (RFC 7807)** を使う。
- サーバー側には相関ID付きで完全なエラーを記録し、クライアントには相関IDのみ返す。

**禁止（MUST NOT）**
- エラーレスポンスにファイルパス、クラス名、行番号を含める。
- エラーメッセージに個人データを含める（例: 「User john@example.com not found」）。

## 9. 暗号化（要約 — 詳細は `references/security.md`）

| 対象 | 最低基準 |
|---|---|
| 通常の個人データ | AES-256 ディスク/ボリューム暗号化 |
| 機微データ（健康、金融、生体） | AES-256 **カラムレベル** + KMSによるエンベロープ暗号化 |
| 転送中 | TLS 1.2+（1.3推奨）; HSTS強制 |
| 鍵 | HSMバックのKMS; DEKを毎年ローテーション |

**禁止（MUST NOT）**: TLS 1.0/1.1、null cipher suites、ハードコードされた暗号鍵を許可しない。

---

## 10. パスワードハッシュ化

**必須（MUST）**
- **Argon2id**（推奨）または **bcrypt**（cost ≥ 12）を使う。MD5、SHA-1、SHA-256は不可。
- パスワードごとに一意のsaltを使い、ハッシュのみ保存する。

**禁止（MUST NOT）**
- いかなる形式でもパスワードをログ出力する。URLでパスワードを送信する。リセットトークンを平文で保存する。

---

## 11. シークレット管理

**必須（MUST）**
- すべてのシークレットをKMSに保存する: Azure Key Vault、AWS Secrets Manager、GCP Secret Manager、または HashiCorp Vault。
- シークレットのコミット防止に pre-commit hooks（`gitleaks`, `detect-secrets`）を使う。
- 開発者の離任時、年次スケジュール時、または侵害疑い時にシークレットをローテーションする。

**`.gitignore` に必須で含める:** `.env`, `.env.*`, `*.pem`, `*.key`, `*.pfx`, `*.p12`, `secrets/`

**禁止（MUST NOT）**
- シークレットをソースコードへコミットする。シークレットを平文の環境変数デフォルトとして保存する。

---

## 12. 匿名化と仮名化（要約 — `references/security.md` 参照）

- **匿名化** = 不可逆 → GDPRの適用範囲外。削除後も保持が必要な記録に使う。
- **仮名化** = 鍵で可逆 → 依然として個人データだが、リスクは低減。
- ユーザー削除時は、保持義務のある記録（財務、監査）は削除ではなく匿名化する。
- 仮名化鍵はKMSに保存する — 仮名化データと同じデータベースに保存しない。

再識別がリンク攻撃で可能な場合、そのデータを「匿名化済み」と呼んでは**ならない**。

---

## 13. ダミーデータによるテスト

**必須（MUST）**
- dev、staging、CI環境で本番の個人データを使用してはならない。
- まずPIIをスクラブせずに本番DBバックアップを非本番へ復元してはならない。
- 合成データ生成器を使用する: `Bogus` (.NET), `Faker` (JS/Python/Ruby)。
- テスト用メールアドレスはすべて `@example.com` を使用する。

## 14. アンチパターン

| アンチパターン | 正しいアプローチ |
|---|---|
| URL内のPII | 公開識別子には不透明なUUIDを使う |
| リクエスト本文全体のログ出力 | 構造化されたイベントメタデータのみ記録する |
| 「永久保持」スキーマ | 設計時にTTLを定義する |
| dev/testで本番データ使用 | 合成データ + スクラビングパイプライン |
| チーム間で資格情報を共有 | 個別アカウント + RBAC |
| ハードコードされたシークレット | KMS + シークレットマネージャー |
| 認証APIで `Access-Control-Allow-Origin: *` | 明示的なCORS許可リスト |
| 同意情報をプロファイルデータと同居 | 専用の同意ストア |
| GETクエリパラメータ内のPII | POST本文または認証済みセッション |
| 公開URLで連番整数ID | UUID |
| 準識別子を含む「匿名化済み」データ | k-匿名性を適用し、リンク耐性を検証 |
| EEA外リージョンを混在させたバックアップ | バックアップジョブで明示的なリージョン固定 |

## 15. PRレビュー チェックリスト

### データモデル
- すべての新規PIIカラムに、文書化された目的と保持期間がある。
- 機微項目（健康、金融、国民ID）はカラムレベル暗号化を使用している。
- 公開識別子に連番整数PKを使っていない。

### API
- URLパスまたはクエリパラメータにPIIがない。
- 個人データを返すすべてのエンドポイントが認証されている。
- 所有権チェックが存在し、ユーザーが他人のリソースへアクセスできない。
- 機微エンドポイントにレート制限が適用されている。

### ロギング
- パスワード、トークン、資格情報がログ出力されていない。
- IPが匿名化されている（最後のオクテットをマスク）。
- PIIが含まれる可能性がある箇所で、リクエスト/レスポンス本文全体をログ出力していない。

### インフラ
- 公開ストレージバケットや公開IPのデータベースがない。
- 新しいクラウドリソースに `DataClassification` タグが付いている。
- 新規ストレージリソースで保存時暗号化が有効化されている。
- データ保存の新規地理リージョンがEEA準拠、またはSCCでカバーされている。

### シークレット & CI/CD
- ソースコードやコミット済み設定ファイルにシークレットがない。
- 新規シークレットがKMSとシークレット在庫ドキュメントに追加されている。
- CI/CDシークレットがパイプラインログでマスクされている。

### 保持と削除
- 保持強制ジョブまたはポリシーが、新しいデータストアまたは項目をカバーしている。
- 削除パイプラインが新しいデータストアをカバーするよう更新されている。

### ユーザー権利とガバナンス
- データエクスポートエンドポイントに、新しい個人データ項目が含まれている。
- 新しい処理活動が導入される場合、RoPAが更新されている。
- 新しいサブプロセッサーに署名済みDPAとRoPAエントリがある。
- 変更が高リスク処理を含む場合、DPIAがトリガーされている。
