# Issue Fields Migration（Issueフィールド移行）

[Issueフィールド](https://github.blog/changelog/2026-03-12-issue-fields-structured-issue-metadata-is-in-public-preview/)は組織レベルの型付きメタデータ（単一選択、テキスト、数値、日付）で、ラベルベースの回避策を構造化され検索可能なクロスリポジトリフィールドに置き換えます。すべての組織には`Priority`、`Effort`、`Start date`、`Target date`が事前設定されており、最大25個のカスタムフィールドをサポートします。

このスキルは既存のメタデータを以下の2つのソースからIssueフィールドへ一括移行します：

- **リポジトリラベル**：`p0`、`p1`、`priority/high`などのラベルを構造化されたIssueフィールド値（例：Priorityフィールド）に変換します。複数ラベルの一括移行と、移行後のラベル削除オプションをサポートします。
- **Project V2フィールド**：GitHubプロジェクトのフィールド値（単一選択、テキスト、数値、日付、イテレーション）を対応する組織レベルのIssueフィールドにコピーします。

## 使用タイミング

- ユーザーが既存のプロジェクトフィールドと重複する組織レベルのIssueフィールドを追加した場合
- ユーザーが古いプロジェクトフィールドを削除する前にプロジェクトフィールドの値をIssueフィールドにコピーしたい場合
- ユーザーが「プロジェクトフィールドのデータをIssueフィールドに移行」「転送」「コピー」したいと尋ねた場合
- ユーザーがリポジトリラベル（例：p0、p1、p2、p3）をIssueフィールド値（例：Priorityフィールド）に変換したい場合
- ユーザーがラベルをIssueフィールドに置き換えたい、またはIssueフィールド導入後にラベルを整理したいと尋ねた場合

## 前提条件

- 対象組織でIssueフィールドが有効になっていること
- Issueフィールドが組織レベルで既に存在していること
- プロジェクトフィールド移行の場合：Issueフィールドがプロジェクトに追加されていること
- ラベル移行の場合：対象リポジトリにラベルが存在していること
- ユーザーがリポジトリ（およびプロジェクトフィールド移行時はプロジェクト）への書き込み権限を持っていること
- `gh` CLIが適切なスコープで認証されていること

## 利用可能なツール

### MCPツール（読み取り操作）

| ツール | 用途 |
|------|---------|
| `mcp__github__projects_list` | プロジェクトフィールドの一覧取得（`list_project_fields`）、値付きプロジェクトアイテムの一覧取得（`list_project_items`） |
| `mcp__github__projects_get` | 特定のプロジェクトフィールドまたはアイテムの詳細取得 |

### CLI / REST API

| 操作 | コマンド |
|-----------|---------|
| 組織のIssueフィールド一覧取得 | `gh api /orgs/{org}/issue-fields -H "X-GitHub-Api-Version: 2026-03-10"` |
| Issueフィールド値の読み取り | `gh api /repos/{owner}/{repo}/issues/{number}/issue-field-values -H "X-GitHub-Api-Version: 2026-03-10"` |
| Issueフィールド値の書き込み | `gh api /repositories/{repo_id}/issues/{number}/issue-field-values -X POST -H "X-GitHub-Api-Version: 2026-03-10" --input -` |
| リポジトリIDの取得 | `gh api /repos/{owner}/{repo} --jq .id` |
| リポジトリラベル一覧取得 | `gh label list -R {owner}/{repo} --limit 1000 --json name,color,description` |
| ラベルでのIssue一覧取得 | `gh issue list -R {owner}/{repo} --label "{name}" --state all --json number,title,labels --limit 1000` |
| Issueからラベル削除 | `gh api /repos/{owner}/{repo}/issues/{number}/labels/{label_name} -X DELETE` |

詳細なAPI情報は[references/issue-fields-api.md](references/issue-fields-api.md)、[references/projects-api.md](references/projects-api.md)、[references/labels-api.md](references/labels-api.md)を参照してください。

## ワークフロー

### ステップ0：移行元の選択

ユーザーに何を移行するか尋ねます：

1. **「ラベルを移行しますか？それともプロジェクトフィールドですか？」**
   - **ラベル**：以下の[ラベル移行フロー](#label-migration-flow)へ進みます。
   - **プロジェクトフィールド**：以下の[プロジェクトフィールド移行フロー](#project-field-migration-flow)へ進みます。

2. ユーザーが**ラベル**を選択した場合：
   - 「どの組織とリポジトリにラベルがありますか？」
   - 「どのラベルを移行したいですか？」（名前を指定するか「ラベルを先に見せて」と言えます）

3. ユーザーが**プロジェクトフィールド**を選択した場合：
   - 「プロジェクトのリンクを教えていただけますか？または組織名とプロジェクト番号を教えてください」
   - 「どのフィールドを移行したいですか？」

### ラベル移行フロー

ユーザーがリポジトリラベルをIssueフィールド値に変換したい場合に使用します。ラベルは`single_select`型Issueフィールドにのみマッピング可能です（各ラベル名は1つのオプション値に対応）。

#### フェーズL1：入力とラベル検出

1. ユーザーに**組織名**と**リポジトリ**を尋ねます。
2. 各リポジトリからラベルを取得：

```bash
gh label list -R {owner}/{repo} --limit 1000 --json name,color,description
```

3. 組織のIssueフィールドを取得：

```bash
gh api /orgs/{org}/issue-fields \
  -H "X-GitHub-Api-Version: 2026-03-10" \
  --jq '.[] | {id, name, content_type, options: [.options[]?.name]}'
```

4. **フィルタリング**（ラベルが多いリポジトリ向け）：50個以上のラベルがある場合、共通プレフィックス（例：`priority-*`、`team-*`、`type-*`）や色でグループ化し、ユーザーが「priorityに一致するラベルを表示」「青いラベルを表示」などで絞り込み可能にします。100個以上のラベルを一度に表示しません。

5. ユーザーにどのラベルがどのIssueフィールドとオプションにマッピングされるか尋ねます。以下のパターンをサポート：
   - **単一ラベル→単一フィールド**：例）ラベル「bug」→Typeフィールドの「Bug」オプション
   - **複数ラベル→1つのフィールド（まとめて）**：例）ラベルp0, p1, p2, p3→Priorityフィールドの対応オプション
   - **複数ラベル→複数フィールド**：例）p1→Priority、frontend→Team。別々のマッピンググループとして扱う。

6. **自動マッピング提案**：各ラベルに対し以下の順でIssueフィールドオプションと照合を試みます：
   - **完全一致**（大文字小文字無視）：ラベル`Bug`→オプション`Bug`
   - **プレフィックス-数字**（`{prefix}-{n}`→`{P}{n}`）：ラベル`priority-1`→オプション`P1`
   - **区切り文字除去**（ハイフン、アンダースコア、スペース）：ラベル`good_first_issue`→オプション`Good First Issue`
   - **部分文字列含有**：ラベル`type: bug`→オプション`Bug`

   すべての提案を一括で提示し、ユーザーに確認、修正、スキップを促します。

**例：**

```
github/my-repoのラベル（関連するものを表示）：
  p0, p1, p2, p3, bug, enhancement, frontend, backend

組織のIssueフィールド（single_select）：
  Priority: Critical, P0, P1, P2, P3
  Type: Bug, Feature, Task
  Team: Frontend, Backend, Design

提案されたマッピング：
  ラベル "p0" → Priority "P0"
  ラベル "p1" → Priority "P1"
  ラベル "p2" → Priority "P2"
  ラベル "p3" → Priority "P3"
  ラベル "bug" → Type "Bug"
  ラベル "frontend" → Team "Frontend"
  ラベル "backend" → Team "Backend"
  ラベル "enhancement" → （自動マッチなし；スキップまたは手動マッピング）

マッピングを確認、調整、または追加しますか？
```

#### フェーズL2：競合検出

ラベル→オプションマッピングを確定後、競合をチェックします。競合とは、単一選択フィールドに対して複数のラベルが同じIssueに付いている場合です（単一選択フィールドは1つの値しか持てません）。

1. ラベルマッピングをターゲットIssueフィールドごとにグループ化。
2. 複数のラベルソースがあるフィールドは競合の可能性ありと記録。
3. ユーザーに競合解決方法を尋ねます：
   - **最初にマッチしたものを使う**：マッピングリストの順で最初のラベルを優先
   - **スキップ**：競合するラベルがあるIssueはスキップし報告
   - **手動**：各競合をユーザーに提示し個別に判断

**例：**

```
潜在的競合：ラベル "p0" と "p1" が両方Priorityフィールドにマッピングされています。
もしIssueに両方のラベルが付いていたら、どちらの値を優先しますか？

選択肢：
  1. 最初にマッチしたもの（マッピングリストで先に出る "p0" を使用）
  2. 競合するIssueはスキップ
  3. ケースバイケースで判断する
```

#### フェーズL3：事前チェック＆データスキャン

1. 各リポジトリの書き込み権限を確認し、`repository_id`をキャッシュ：

```bash
gh api /repos/{owner}/{repo} --jq '{full_name, id, permissions: .permissions}'
```

2. マッピングされた各ラベルについて、該当Issueを取得：

```bash
gh issue list -R {owner}/{repo} --label "{label_name}" --state all \
  --json number,title,labels,type --limit 1000
```

   **注意**：`--limit 1000`は結果を1000件で切り捨てます。ラベルに1000件以上のIssueがある場合は手動でページングするか、総数を先に確認してください（例：`gh issue list --label "X" --state all --json number | jq length`）。

   **PRフィルタリング**：`gh issue list`はIssueとPR両方を返します。`--json`に`type`を含め、Issueのみ移行したい場合は`type == "Issue"`でフィルタリングしてください。

3. **すべての選択ラベルでIssueが0件の場合**は処理を中止し、ユーザーに別のラベルやスペル確認、別リポジトリの検討を促します。空の移行は行いません。

4. 複数リポジトリ移行の場合は指定されたすべてのリポジトリで繰り返します。

5. 各Issueについて：
   - 既にターゲットIssueフィールドに値がある場合はスキップ
   - 複数ラベルによる競合を検出
   - フェーズL2で選択された競合解決策を適用
   - 分類：**移行対象**、**スキップ（既設定）**、**スキップ（競合）**、**スキップ（該当ラベルなし）**

#### フェーズL4：プレビュー／ドライラン

書き込み前に概要を提示。

**例：**

```
ラベル移行プレビュー

ソース：github/my-repoのラベル
ターゲットフィールド：Priority, Type, Team

| カテゴリ                 | 件数  |
|-------------------------|-------|
| 移行対象Issue           |   156 |
| 既設定（スキップ）      |    12 |
| 競合ラベル（スキップ）  |     3 |
| ラベル付きIssue合計     |   171 |

ラベル別内訳：
  "p1" → Priority "P1": 42件
  "p2" → Priority "P2": 67件
  "p3" → Priority "P3": 38件
  "bug" → Type "Bug": 9件

変更例（最初の5件）：
  github/my-repo#101: Priority → "P1"
  github/my-repo#203: Priority → "P2", Type → "Bug"
  github/my-repo#44:  Priority → "P3"
  github/my-repo#310: Priority → "P1"
  github/my-repo#7:   Type → "Bug"

移行後、移行したラベルをIssueから削除しますか？（任意）

推定所要時間：約24秒（156 API呼び出し、1回あたり0.15秒）

実行しますか？
```

#### フェーズL5：実行

1. 移行対象の各Issueに対しIssueフィールド値を書き込み（プロジェクトフィールド移行と同じエンドポイント）：

```bash
echo '{"issue_field_values": [{"field_id": FIELD_ID, "value": "OPTION_NAME"}]}' | \
  gh api /repositories/{repo_id}/issues/{number}/issue-field-values \
    -X POST \
    -H "X-GitHub-Api-Version: 2026-03-10" \
    --input -
```

   `FIELD_ID`は整数のフィールドID（例：`1`）、`OPTION_NAME`はオプション名の文字列に置き換えます。

2. ユーザーがラベル削除を選択した場合、フィールド書き込み成功後に各ラベルを削除：

```bash
gh api /repos/{owner}/{repo}/issues/{number}/labels/{label_name} -X DELETE
```

   スペースや特殊文字を含むラベル名はURLエンコードしてください。

3. **ペース管理**：呼び出し間に100msの遅延。HTTP 429時は指数関数的バックオフ（1秒、2秒、4秒、最大30秒）。
4. **進捗報告**：25件ごとに報告（例：「75/156件移行済み...」）。
5. **エラー処理**：失敗はログに記録し続行。ラベル削除失敗は別途記録。
6. **最終サマリー**：

```
ラベル移行完了

| 結果                  | 件数  |
|-----------------------|-------|
| フィールド設定済み    |   153 |
| ラベル削除済み        |   153 |
| スキップ              |    15 |
| 失敗（フィールド書き込み） |     2 |
| 失敗（ラベル削除）    |     1 |

失敗した項目：
  github/my-repo#501: 403 Forbidden（権限不足）
  github/my-repo#88:  422 Validation failed（リポジトリでフィールド利用不可）
  github/my-repo#120: ラベル削除失敗（404、既に削除済み）
```

### プロジェクトフィールド移行フロー

GitHub Project V2のフィールド値を対応する組織レベルのIssueフィールドにコピーしたい場合に使用します。

以下の6フェーズを順に実行。必ず実行前にプレビューを行います。

#### フェーズP1：入力と検出

1. ユーザーに**組織名**と**プロジェクト番号**（またはプロジェクトURL）を尋ねます。
2. プロジェクトフィールドを取得：

```bash
# MCPツールを使用
mcp__github__projects_list(owner: "{org}", project_number: {n}, method: "list_project_fields")
```

3. 組織のIssueフィールドを取得：

```bash
gh api /orgs/{org}/issue-fields \
  -H "X-GitHub-Api-Version: 2026-03-10" \
  --jq '.[] | {id, name, content_type, options: [.options[]?.name]}'
```

4. **プロキシフィールドの除外**：Issueフィールドがプロジェクトで有効化されると、一部のプロジェクトフィールドは空の`options: []`を持つ「プロキシ」エントリとして表示されます。これは実際のIssueフィールドを反映しているため無視し、実際にオプション値を持つプロジェクトフィールドのみを対象にします。

5. 名前（大文字小文字無視）と互換性のある型で自動マッチング：

| プロジェクトフィールド型 | Issueフィールド型 | 互換性 |
|-------------------------|-----------------|---------|
| TEXT                    | text            | はい（直接コピー） |
| SINGLE_SELECT           | single_select   | はい（オプションマッピング必要） |
| NUMBER                  | number          | はい（直接コピー） |
| DATE                    | date            | はい（直接コピー） |
| ITERATION               | （なし）        | なし（警告を出してスキップ） |

6. 提案されたフィールドマッピングを表形式で提示。ユーザーに確認、調整、スキップを促す。

**例：**

```
3件の候補フィールドマッピングを検出：

| # | プロジェクトフィールド | 型             | Issueフィールド     | 状態       |
|---|-----------------------|----------------|--------------------|------------|
| 1 | Priority (名前変更済み) | SINGLE_SELECT  | Priority           | 自動マッチ |
| 2 | Due Date              | DATE           | Due Date           | 自動マッチ |
| 3 | Sprint                | ITERATION      | （該当なし）       | スキップ   |

フィールド1と2で進めますか？手動マッピングも追加可能です。
```

#### フェーズP2：オプションマッピング（単一選択フィールドのみ）

マッチした単一選択フィールドごとに：

1. プロジェクトフィールドとIssueフィールドのオプション名を比較（大文字小文字無視）。
2. 同名のオプションは自動マッチ。
3. マッピングされていないプロジェクトオプションは**すべてまとめて**一覧表示し、一括でユーザーにマッピングを入力してもらう。1つずつではなく一括で行う。
4. 最終的なオプションマッピング表を提示し確認。

**例：**

```
「Release - Target」のオプションマッピング：

自動マッチ済み（大文字小文字無視）：
  "GA" → "GA"
  "Private Preview" → "Private Preview"
  "Public Preview" → "Public Preview"

未マップのプロジェクトオプション（入力が必要）：
  1. "Internal Only" → どのIssueフィールドオプション？（スキップ可）
  2. "Retired" → どのIssueフィールドオプション？（スキップ可）
  3. "Beta" → どのIssueフィールドオプション？（スキップ可）
  4. "Deprecated" → どのIssueフィールドオプション？（スキップ可）

未マップのIssueフィールドオプション： "Internal", "Sunset", "Beta Testing", "End of Life"

上記4つのオプションのマッピングを一括で入力してください（例："1→Internal, 2→Sunset, 3→Beta Testing, 4→skip"）。
```

#### フェーズP3：事前チェック

アイテムスキャン前に、操作対象となるリポジトリの書き込み権限を確認：

1. プロジェクトアイテム（最初のページ）からユニークな`{owner}/{repo}`のセットを収集。
2. 各リポジトリについて認証ユーザーのIssue書き込み権限を確認：

```bash
gh api /repos/{owner}/{repo} --jq '{full_name, permissions: .permissions}'
```

3. `push: false`または`triage: false`のリポジトリがあれば、ユーザーに警告。これらのリポジトリのアイテムは書き込み時に失敗します。
4. 各リポジトリの`repository_id`（整数）をキャッシュ。フェーズ6で使用：

```bash
gh api /repos/{owner}/{repo} --jq .id
```

#### フェーズP4：データスキャン

1. MCPで全プロジェクトアイテムを取得。**重要**：200件以上のアイテムがあるプロジェクトは`gh api graphql --paginate`が信頼できません（JSON連結が不正、タイムアウトの可能性）。MCPツールを使うか、カーソルベースのページングを明示的に行ってください。

```bash
# 推奨：MCPツール（ページング自動処理）
mcp__github__projects_list(owner: "{org}", project_number: {n}, method: "list_project_items")

# 大規模プロジェクトの代替：カーソルベースページング
# 1ページ100件ずつ取得し、次ページのカーソルを使って繰り返す。
# メモリ問題回避のため各ページ処理後に次ページ取得。
# 中断時はページ番号または最後のカーソルを保存し再開可能。
```

2. 各アイテムについて：
   - 下書きアイテム（実際のIssueでないもの）はスキップ。
   - ソースのプロジェクトフィールド値を抽出。
   - ソース値が空ならスキップ。
   - 既にターゲットIssueフィールドに値があるか確認：

```bash
gh api /repos/{owner}/{repo}/issues/{number}/issue-field-values \
  -H "X-GitHub-Api-Version: 2026-03-10"
```

   - 既設定ならスキップ（既存データ保持）。

3. 各アイテムを以下に分類：
   - **移行対象**：ソース値あり、ターゲット未設定
   - **スキップ（既設定）**：ターゲットIssueフィールドに既に値あり
   - **スキップ（ソースなし）**：プロジェクトフィールド値が空
   - **スキップ（下書き）**：下書きアイテム
   - **スキップ（未マップオプション）**：単一選択値がマッピングされていない

#### フェーズP5：プレビュー／ドライラン

書き込み前に概要を提示。

**ドライラン要求時**：すべてのアイテムの詳細レポート（各Issue、現在値、提案値、スキップ理由）を表示し停止。実行しません。

**通常プレビューモード**：集計件数と変更例を表示し、ユーザーに確認を求めます。

**例：**

```
プロジェクト#42の移行プレビュー

移行対象フィールド：Priority, Due Date

| カテゴリ               | 件数  |
|------------------------|-------|
| 移行対象アイテム       |   847 |
| 既設定（スキップ）     |    23 |
| ソース値なし（スキップ）|   130 |
| 下書きアイテム（スキップ）|   12 |
| プロジェクトアイテム合計| 1,012 |

変更例（最初の5件）：
  github/repo-a#101: Priority → "High"
  github/repo-a#203: Priority → "Medium", Due Date → "2025-03-15"
  github/repo-b#44:  Priority → "Low"
  github/repo-a#310: Due Date → "2025-04-01"
  github/repo-c#7:   Priority → "Critical"

推定所要時間：約127秒（847 API呼び出し、1回あたり0.15秒）

移行を実行しますか？3リポジトリ合計847件のIssueが更新されます。
```

#### フェーズP6：実行

1. フェーズ3でキャッシュした`repository_id`を使用。

2. 移行対象の各アイテムに対しIssueフィールド値を書き込み：

```bash
echo '{"issue_field_values": [{"field_id": FIELD_ID, "value": "VALUE"}]}' | \
  gh api /repositories/{repo_id}/issues/{number}/issue-field-values \
    -X POST \
    -H "X-GitHub-Api-Version: 2026-03-10" \
    --input -
```

   `FIELD_ID`は整数のフィールドID（例：`1`）、`VALUE`は値の文字列に置き換えます。

3. **ペース管理**：API呼び出し間に100ms遅延。HTTP 429時は指数関数的バックオフ（1秒、2秒、4秒、最大30秒）。
4. **進捗報告**：25件ごとに報告（例：「75/847件移行済み...」）。
5. **エラー処理**：失敗はログに記録し処理継続。
6. **最終サマリー**：

```
移行完了

| 結果    | 件数  |
|---------|-------|
| 成功    |   842 |
| スキップ|   165 |
| 失敗    |     5 |

失敗した項目：
  github/repo-a#501: 403 Forbidden（権限不足）
  github/repo-b#88:  422 Validation failed（リポジトリでフィールド利用不可）
  ...
```

## 重要な注意点

- **書き込みエンドポイントの仕様**：Issueフィールド値のREST API書き込みは`owner/repo`ではなく`repository_id`（整数）を使います。必ず`gh api /repos/{owner}/{repo} --jq .id`でリポジトリIDを取得してください。
- **単一選択値**：REST APIはオプションIDではなくオプション名（文字列）を受け入れます。プロジェクトフィールドもラベルもマッピングが簡単です。
- **値の読み取り**：APIレスポンスのIssueフィールド値は`.single_select_option.name`で人間可読値を取得します。`.value`は内部のオプションID（例：1201）で表示名ではありません。
- **APIバージョンヘッダー**：すべてのIssueフィールドエンドポイントは`X-GitHub-Api-Version: 2026-03-10`が必要です。
- **クロスリポジトリアイテム**：プロジェクトは複数リポジトリのIssueを含みます。リポジトリごとにIDをキャッシュし重複取得を避けます。
- **既存値の保持**：既に値が設定されているIssueフィールドは上書きしません。スキップします。
- **イテレーションフィールド**：Issueフィールドに対応がないため、必ず警告を出してスキップします。
- **下書きアイテム**：実際のIssueにリンクしていないプロジェクトアイテムはIssueフィールド値を持てません。スキップし注記します。
- **ラベルはリポジトリ単位**：プロジェクトフィールドと異なり、ラベルはリポジトリごとに存在します。同名ラベルが複数リポジトリにある場合、移行はリポジトリごとに個別に行います。
- **ラベル競合**：単一選択フィールドに複数ラベルがマッピングされているIssueは必ず検出し、実行前に解決します。
- **ラベル削除は任意**：移行後にラベルをバックアップとして残すか削除するかはユーザーに必ず確認します。
- **ラベル名のURLエンコード**：スペースや特殊文字を含むラベル名はREST APIパスでURLエンコードが必要です（例：`good%20first%20issue`）。
- **大規模移行用スクリプト生成**：100件以上のIssue移行では、エージェント経由で1件ずつAPI呼び出しするより、独立したシェルスクリプトを生成する方が高速で再開可能、タイムアウト回避に有効です。
- **冪等性**：移行を再実行しても安全です。既に値が設定されているIssueはスキップされるため、途中から再開しても重複作業になりません。
- **`--limit 1000`の切り捨て**：`gh issue list --limit 1000`は1000件で結果を切り捨てます。1000件超のラベルはカーソルベースページングや複数クエリで対応してください（例：日付範囲で分割）。
- **macOSのbashバージョン**：macOS標準のbash 3.xは連想配列`declare -A`をサポートしません。生成スクリプトはPOSIX互換の構文を使うか、互換性がない旨を伝え`brew install bash`を推奨してください。
- **IssueとPRの区別**：`gh issue list`はIssueとプルリクエスト両方を返します。Issueのみ移行したい場合は`--json`に`type`を含め、`type == "Issue"`でフィルタリングしてください。

## 例

### 例1：完全移行

**ユーザー**：「プロジェクトのPriority値を新しい組織のPriority Issueフィールドに移行したい」

**操作**：フェーズP1〜P6を順に実行。フィールド検出、オプションマッピング、権限確認、アイテムスキャン、プレビュー、実行。

### 例2：ドライランのみ

**ユーザー**：「プロジェクト#42のフィールドを移行した場合の結果を見せてほしい。実際の移行はしないで」

**操作**：フェーズP1〜P5のみ実行。すべてのアイテムの詳細レポートを表示し停止。実行しない。

### 例3：複数フィールド

**ユーザー**：「プロジェクト#15のPriorityとDue DateをIssueフィールドに移行したい」

**操作**：同じワークフローで両フィールドを一括処理。データスキャン時に各アイテムのすべてのマッピング済みフィールド値を収集し、1回のAPI呼び出しで複数フィールド値を書き込み。

### 例4：単一ラベル→Issueフィールド

**ユーザー**：「'bug'ラベルをType Issueフィールドに移行したい」

**操作**：ラベル移行フローへ。組織/リポジトリを尋ね、ラベル一覧を取得。マッピング確認（ラベル"bug"→Typeフィールドの"Bug"オプション）。該当ラベルのIssueをスキャンし、プレビュー後に実行。移行後のラベル削除を確認。

### 例5：複数ラベル→1フィールド（まとめて）

**ユーザー**：「p0、p1、p2、p3ラベルをPriority Issueフィールドに変換したい」

**操作**：ラベル移行フローへ。4つのラベルをPriorityフィールドの対応オプションにマッピング（p0→P0、p1→P1、p2→P2、p3→P3）。競合（複数Priorityラベルが付いたIssue）を検出。すべての変更を1つの概要でプレビュー。1回の処理で実行。移行後に4つのラベルを任意で削除。

### 例6：複数リポジトリでのラベル移行＋ラベル削除

**ユーザー**：「'frontend'と'backend'ラベルをTeam Issueフィールドにgithub/issues、github/memex、github/mobileの3リポジトリで移行し、その後古いラベルを削除したい」

**操作**：ラベル移行フローへ。対象リポジトリとラベルマッピングを確認（"frontend"→Teamの"Frontend"、"backend"→Teamの"Backend"）。3リポジトリすべてで該当ラベルのIssueをスキャン。競合（両ラベルが付いたIssue）を検出。リポジトリ横断でプレビュー。フィールド書き込み後にラベル削除。リポジトリごとの統計を報告。
