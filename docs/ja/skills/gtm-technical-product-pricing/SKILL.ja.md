# 技術プロダクトの価格設定


## 初期評価

価格を提案する前に、以下を把握します。

1. **プロダクトタイプ**: API/プラットフォーム、開発者ツール、SaaSアプリケーション、インフラのどれか？
2. **現在の価格設定**: 今はいくらで提供しているか？ その価格をどれくらい続けているか？
3. **GTMモーション**: セルフサーブ、営業支援型、エンタープライズ、またはハイブリッド？
4. **コスト構造**: 顧客/ユーザー/単位あたりの限界コストはいくらか？
5. **競合環境**: 代替手段はいくらかかるか？（「何もしない」も含む）

---

## コアフレームワーク

### 1. 誰にも気づかれなかった値上げ（あなたの価格はおそらく安すぎる）

**よくあるパターン:**

成長段階のプラットフォーム企業。価格はローンチ以来変更なし。エンタープライズ顧客は、年間$200K超のエンジニア工数削減効果がある製品に対して、年間$15Kを支払っていた。

経営陣の議論: 「値上げしたら顧客が離れるのでは？」

**実際に起きたこと:**

エンタープライズプランを年額$15Kから$45Kに引き上げ。値上げの根拠として、専用サポート、SSO、監査ログを追加。

失った顧客: エンタープライズ顧客0。ゼロ。

得たもの: エンタープライズ1社あたり売上3倍。さらに、継続顧客は製品をより本格的に活用し始めた。導入率向上、社内推進者の増加、追加展開の拡大。

**なぜこうなるのか:**

技術系創業者はコスト基準で価格を決めがち（「提供コストが$Xだから$2Xで売る」）。エンタープライズ購買側は価値基準で判断する（「$200K節約できるなら$45Kは安い」）。

**価格妥当性チェック:**

顧客セグメントごとに次を計算します。

```
Value Ratio = Customer's alternative cost / Your price

If Value Ratio > 10x → You're massively underpriced
If Value Ratio > 5x  → You're underpriced (most startups are here)
If Value Ratio 3-5x  → Healthy pricing
If Value Ratio < 3x  → Approaching ceiling
If Value Ratio < 2x  → You're expensive (need strong differentiation)
```

**代替コストの計算方法:**

- 手作業にかかる時間 × 時間単価 × 頻度
- 内製コスト（エンジニア人数 × 月数 × 総コスト）
- 既存ツールの費用 + スイッチングコスト + 移行中の生産性低下
- *問題を解決しないこと*のコスト（インシデント、ダウンタイム、解約）

**よくある間違い:**

顧客の代替コストではなく競合価格と比較すること。競合基準では消耗戦になりやすい。価値基準なら、顧客が実際に節約できる額に価格を結びつけられる。

### 2. 3つの価格モデル（そして各モデルが破綻する場面）

**モデル1: シート課金（$X/ユーザー/月）**

**有効な場面:**
- 価値がユーザー数に比例する（コラボレーションツール、コミュニケーション）
- ユーザーごとの利用量の差が小さい
- 予測可能な売上を重視したい

**破綻する場面:**
- ヘビーユーザーとライトユーザーが同額（ライトユーザーが離脱）
- 製品価値がシート数に比例しない（1人の管理者が1,000人分を設定）
- 顧客がコスト削減のためにシートを統合（利用は増えるが売上は増えない）

**モデル2: 従量課金（$X/単位）**

**有効な場面:**
- 顧客ごとに利用量の差が大きい（APIコール、計算、ストレージ）
- 限界コストが無視できない（利用増と売上増を連動させる必要がある）
- 価値が利用量と直接相関する

**破綻する場面:**
- 顧客が請求額を予測できない（月末に請求ショック）
- 低利用顧客のサポート採算が合わない
- 高利用顧客がボリュームディスカウントを要求し、利益率が圧迫される

**モデル3: 成果課金（$X/結果）**

**有効な場面:**
- 成果を信頼性高く計測できる（獲得リード数、解決チケット数、デプロイされたコード量）
- 成果が顧客価値を直接生む
- 自社プロダクトの有効性に確信がある

**破綻する場面:**
- 成果が自社コントロール外の要因に左右される
- 計測に争いが起きる（「そのリードはあなたのツール由来ではない」）
- 顧客が指標を都合よく操作する

**多くの場合に勝つハイブリッド:**

プラットフォーム基本料金（固定費を回収） + 従量/成果の変動料金（価値に連動）。

例: 月額$500の基本料 + 取引あたり$0.05（またはAPIコール、完了タスク数、処理レコード数など、あなたの価値単位）。

これが機能する理由:
- 基本料で全顧客の提供コストを最低限カバーできる
- 変動料で価格と価値が一致する
- 顧客は最低支出（基本料）を予測しつつ自然にスケールできる
- 顧客成長時のアップサイドを取り込める

### 3. フリーミアムしきい値設計（無料の終わりと有料の始まり）

**よくあるパターン:**

開発者向けツールで最も難しい価格判断は、無料と有料の境界線をどこに引くか。

**フレームワーク: 本番利用の境界を見つける**

課金しない無料ユーザーが存在すること自体は問題ない。認知、コミュニティ、コンテンツを生むため。問題は、*本番利用ユーザー*が永遠に無料のままなこと。

**境界の見つけ方:**

利用分布をマッピングする。

```
Usage Level          |  User Type        |  Willingness to Pay
─────────────────────────────────────────────────────────────
<100 units/mo        |  Hobbyist/learner |  $0 (never paying)
100-1K units/mo      |  Side project     |  $0-20/mo (maybe)
1K-10K units/mo      |  Production use   |  $50-200/mo (will pay)
>10K units/mo        |  Business-critical|  $200-2K/mo (must pay)
```

**無料枠上限は、本番利用が始まる直前に設定する。** この例なら月1,000ユニット無料。

理由: ホビーユーザーや学習者は無料に残せる（マーケティングエンジンになる）。本番利用者は自然に上限へ到達し、有料化する（予算を持っている）。

**無料→有料のトリガー3種:**

**1. 利用量上限**（プラットフォームで最も一般的）
- 無料: 月1,000ユニット（APIコール、タスク、レコードなど価値単位）
- 発火条件: 本番利用が上限を超える
- 転換シグナル: ユーザーが実用的なものを構築している

**2. チーム/コラボレーションのゲート**（ツールに最適）
- 無料: 個人利用
- 発火条件: 2人目を招待したとき
- 転換シグナル: 共有したくなるほど価値がある

**3. エンタープライズ機能のゲート**（プラットフォームに最適）
- 無料: コア機能
- 発火条件: SSO、RBAC、監査ログ、SLAが必要になったとき
- 転換シグナル: IT/セキュリティ部門が関与（実運用）

**よくある間違い:**

無料枠を高くしすぎる（「開発者に愛されたい」）。本番利用者が上限に達しなければ、有料化しない。無料枠の寛容さは*学習者*向けであるべきで、*本番利用者*向けではない。

### 4. エンタープライズ価格設定（数字ではなく対話）

**よくあるパターン:**

エンタープライズ価格はWebサイト上の1ページではない。対話で決まる。「Contact Sales」ボタンがあるのは、案件ごとに要件が違うからであり、メニュー価格ではなく価値基準で価格を決めるべきだから。

**エンタープライズ価格の変数:**

**1. デプロイモデル**（セルフサーブクラウド、専有クラウド、オンプレ、ハイブリッド）
- 提供コストが異なる → 価格下限も異なる
- オンプレはクラウド比で2〜5倍のプレミアムが取れる（サポート複雑性）

**2. 利用規模**（シート数、API量、データ量）
- ボリュームディスカウントは「提供コスト + 40%マージン」を下回らない
- 割引は定価に対して適用し、すでに割引後の価格には適用しない

**3. サポートレベル**（コミュニティ、標準、プレミアム、専任）
- プレミアムサポート: 基本価格の1.5〜2倍
- 専任CSM: 基本価格の2〜3倍
- SLA付き24/7サポート: 基本価格の3〜5倍

**4. コンプライアンス要件**（SOC 2、HIPAA、FedRAMP、データレジデンシー）
- 各基準は実コストを伴う（監査、インフラ、プロセス）
- それに応じて価格設定: コンプライアンス基準ごとに基本価格の1.5〜2倍

**エンタープライズ価格の対話:**

見込み客が「いくらですか？」と言ったとき:

1. **数字で答えない。** 質問で返す: 「導入形態と規模要件で変わります。必要条件を教えてください。」

2. **要件を整理する:**
   - ユーザー/シート/ユニット数は？
   - クラウドかオンプレか？
   - コンプライアンス要件は？
   - サポート期待値は？
   - 連携要件は？

3. **価格提示前に価値をアンカーする:**
   - 「お話の内容だと、現在この課題に[X]を使っています。当社のソリューションは通常それを[Y%]削減します。」
   - その後、削減額の一部として価格を提示する。

4. **3つの選択肢を提示する:**
   - Good: 最低要件を満たす
   - Better: 要件 + あると望ましい項目を満たす（ここをアンカー）
   - Best: 要望外の項目まで含むフル構成
   - 多くの購買担当はBetterを選ぶ。そこが実質的な本命価格。

**よくある間違い:**

エンタープライズ価格をWebサイトで公開すること。数字を公開した瞬間、それが上限になり、交渉は下方向にしか進まない。エンタープライズ価格は対話として扱う。

### 5. ポジショニングシグナルとしての価格

**よくあるパターン:**

価格は「誰向けの製品か」を買い手に伝える。これは売上判断であると同時に、ポジショニング判断でもある。

**価格シグナル:**

**$0（オープンソース / 無料枠）:**
- シグナル: 購入前に試したい開発者向け
- 引き寄せる層: 個人貢献者、実験志向のユーザー
- リスク: 「エンタープライズ対応でない」と見なされる

**$20-100/月:**
- シグナル: チームや中小企業向け
- 引き寄せる層: セルフサーブ購買層、スタートアップ
- リスク: エンタープライズに本気で見てもらえない（安すぎる）

**$500-2,000/月:**
- シグナル: 本番ワークロード向け
- 引き寄せる層: 実予算を持つ成長企業
- リスク: スタートアップには高く、無料枠が必要な場合がある

**$5,000-50,000/年:**
- シグナル: エンタープライズ向け
- 引き寄せる層: ミッドマーケットとエンタープライズ
- リスク: 営業チームが必要（この価格帯でセルフサーブは難しい）

**$100K+/年:**
- シグナル: ミッションクリティカルなインフラ
- 引き寄せる層: 大企業
- リスク: 長い営業サイクル、重いサポート期待

**ポジショニングテスト:**

月$50で売りながらエンタープライズ顧客を狙うなら、価格がポジショニングを壊している。エンタープライズ購買は低価格を低価値と結びつける。狙う顧客を引き寄せるために、*値上げ*が必要なこともある。

**よくある間違い:**

目の前の顧客向けに価格を決めること。目指す顧客像がエンタープライズなら、価格もエンタープライズ向けに設計する。今日いくつかのSMB顧客を失っても、それが正しい場合がある。

### 6. 値上げのタイミングと進め方

**タイミングのシグナル:**

- 多くの顧客で価値比率が5x超
- 受注率が40%以上（価格が負け要因ではない）
- 直近6カ月で価格への顧客反発がない
- 顧客の拡大速度が想定より速い
- 競合が値上げしてもシェアを失っていない

**顧客を失わずに値上げする方法:**

**1. 既存顧客の料金据え置き（12〜24カ月）**
- 新規顧客のみに新価格を適用
- 既存顧客には事前告知 + 移行時期を提示
- 見込み客には緊急性を生む（「もうすぐ値上げ」）

**2. 値上げを正当化する価値追加**
- 新機能を含む新しい上位プランを追加
- 現行プラン機能の一部を新上位プランへ移す
- これは単なる値上げではなく再ポジショニング

**3. 契約に年次改定条項を入れる**
- エンタープライズ契約に年5〜10%のエスカレーターを含める
- 価格改定を通常運用にする
- 「4年間ずっと同じ価格です」という交渉を防ぐ

**コミュニケーション例:**

「当社は[具体的な改善点]への投資を進めています。この投資水準を維持するため、[date]に価格を改定します。現在のプランは[grandfather date]まで現行価格で据え置きます。」

値上げを謝罪しないこと。顧客が愛用する製品への投資として伝える。

## 意思決定ツリー

### どの価格モデルを選ぶべきか？

```
Does usage vary >5x between customers?
├─ Yes → Usage-based (or hybrid with usage component)
└─ No → Continue...
    │
    Does value scale with team size?
    ├─ Yes → Seat-based
    └─ No → Continue...
        │
        Can you measure customer outcomes reliably?
        ├─ Yes → Outcome-based (or hybrid)
        └─ No → Platform fee + feature-based tiers
```

### 値上げすべきか？

```
Is value ratio > 5x for most customers?
├─ Yes → Raise prices
└─ No → Continue...
    │
    Are win rates > 40%?
    ├─ Yes → Price isn't the problem, but consider raising
    └─ No → Continue...
        │
        Are you losing deals specifically on price?
        ├─ Yes → Don't raise. Improve value or segment better.
        └─ No → Something else is wrong (product, positioning, sales)
```
