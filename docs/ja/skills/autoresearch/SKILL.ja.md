# Autoresearch: 自律反復実験

あらゆるプログラミングタスク向けの自律実験ループです。目標と測定方法を定義すると、エージェントが自律的に反復します――コードを変更し、実験を実行し、結果を測定し、変更を採用または破棄します――中断されるまで続きます。

このスキルは [Karpathy's autoresearch](https://github.com/karpathy/autoresearch) に着想を得ており、ML トレーニングから **測定可能な成果を持つあらゆるプログラミングタスク** へ一般化したものです。

---

## エージェントの振る舞いルール

1. **DO** ループ開始前に、Setup フェーズを対話形式でユーザーに案内する。
2. **DO** 変更を加える前にベースライン測定を確立する。
3. **DO** 実行前にすべての実験試行をコミットする（きれいに巻き戻せるようにするため）。
4. **DO** すべての実験を追跡する結果ログ（TSV）を保持する。
5. **DO** 指標を改善しない変更は元に戻す（既知の最良状態へ git reset）。
6. **DO** ループ開始後は自律的に実行する――「続けますか？」と停止して尋ねない。
7. **DO NOT** ユーザーがスコープ外として指定したファイルを変更しない。
8. **DO NOT** 測定ステップを省略しない――すべての実験は必ず測定する。
9. **DO NOT** ユーザーがトレードオフを明示的に許可しない限り、指標を悪化させる変更を保持しない。
10. **DO NOT** ユーザーの承認なしに新規依存関係の追加や環境変更を行わない。

---

## フェーズ 1: Setup（対話式）

実験を始める前に、以下のパラメータをユーザーと確立します。  
各項目をユーザーに直接尋ねてください。推測やスキップはしないでください。

### 1.1 目標の定義

ユーザーに尋ねる:

> **何を改善または最適化したいですか？**
>
> 例: 実行時間、メモリ使用量、バイナリサイズ、テスト合格率、コードカバレッジ、
> API 応答レイテンシ、スループット、エラー率、ベンチマークスコア、ビルド時間、バンドルサイズ、
> コード行数、循環的複雑度 など。

ユーザーの回答を **goal** として記録します。

### 1.2 指標の定義

ユーザーに尋ねる:

> **成功をどう測定しますか？ 指標はどの正確なコマンドで得られますか？**
>
> 必要なのは:
> 1. 実行する **コマンド**（例: `dotnet test`, `npm run benchmark`, `time ./build.sh`, `pytest --tb=short`）
> 2. 出力から **指標を抽出する方法**（例: 正規表現パターン、特定の行、JSON フィールド）
> 3. **方向**: 小さいほど良いか、大きいほど良いか？
>
> 例: 「`dotnet test --logger trx` を実行し、合格テスト数を数える。大きいほど良い。」
> 例: 「`hyperfine './my-program'` を実行し、平均時間を抽出する。小さいほど良い。」

記録する:
- `METRIC_COMMAND`: 実行するコマンド
- `METRIC_EXTRACTION`: 出力から数値指標を抽出する方法
- `METRIC_DIRECTION`: `lower_is_better` または `higher_is_better`

### 1.3 スコープの定義

ユーザーに尋ねる:

> **どのファイルまたはディレクトリを変更してよいですか？**
>
> また、どのファイルが変更禁止（読み取り専用）ですか？

記録する:
- `IN_SCOPE_FILES`: エージェントが編集可能なファイル/ディレクトリ
- `OUT_OF_SCOPE_FILES`: 変更してはならないファイル/ディレクトリ

### 1.4 制約の定義

ユーザーに尋ねる:

> **守るべき制約はありますか？**
>
> 例:
> - 実験ごとの時間予算（例: 「各実行は 2 分未満」）
> - 新規依存関係なし
> - 既存テストはすべて合格を維持
> - 公開 API を変更しない
> - 後方互換性を維持
> - VRAM/メモリ上限
> - コード複雑度の上限（よりシンプルな解法を優先）

`CONSTRAINTS` として記録します。

### 1.5 実験予算の定義（任意）

ユーザーに尋ねる:

> **実験を何回実行すべきですか？ それとも停止されるまで続けますか？**
>
> 数値（例: 「20 回試す」）または「unlimited」（中断されるまで実行）を指定できます。

`MAX_EXPERIMENTS`（数値または `unlimited`）として記録します。

### 1.6 シンプルさの基準

デフォルトのシンプルさポリシーをユーザーに伝える:

> **シンプルさポリシー（デフォルト）:** 他条件が同じなら、よりシンプルな方が良いです。わずかな改善のために
> 見苦しい複雑さを追加する価値はありません。指標を維持または改善しつつコードを削減できるのは
> 優れた結果です。改善幅と複雑化コストを比較して判断します。
> このポリシーで問題ありませんか？ それとも調整しますか？

調整があれば `SIMPLICITY_POLICY` として記録します。

### 1.7 Setup の確認

全パラメータを明確な表でユーザーに要約して返します:

| Parameter          | Value                        |
| ------------------ | ---------------------------- |
| Goal               | ...                          |
| Metric command     | ...                          |
| Metric extraction  | ...                          |
| Direction          | lower is better / higher ... |
| In-scope files     | ...                          |
| Out-of-scope files | ...                          |
| Constraints        | ...                          |
| Max experiments    | ...                          |
| Simplicity policy  | ...                          |

ユーザーに確認を求めます。確認されるまで先に進まないでください。

## フェーズ 2: ブランチ & ベースライン

ユーザーが確認したら:

1. **ブランチを作成**: 今日の日付に基づくタグを提案（例: `autoresearch/mar17`）。
   ブランチを作成: `git checkout -b autoresearch/<tag>`。

2. **スコープ内ファイルを読む**: 現在状態の全体文脈を把握するため、スコープ内の全ファイルを読みます。

3. **results.tsv を初期化**: リポジトリルートに `results.tsv` を作成し、ヘッダー行を次のようにします:
   ```
   experiment	commit	metric	status	description
   ```
   `results.tsv` と `run.log` を `.git/info/exclude` に追加（未登録なら追記）し、追跡対象ファイルを変更せずに未追跡のまま維持します。

4. **ベースラインを実行**: 現在の未変更コードで指標コマンドを実行します。
   結果を `results.tsv` に実験 `0`、ステータス `baseline` として記録します。

5. **ベースラインをユーザーに報告**:
   > ベースライン確立: **[metric_name] = [value]**
   > 自律実験ループを開始します。

## フェーズ 3: 実験ループ

このループを継続的に実行します。ユーザーに確認するために停止しません。次のいずれかまで実行します:
- `MAX_EXPERIMENTS` に到達、または
- ユーザーが手動で中断

### 各実験ごとに:

```
LOOP:
  1. THINK   - これまでの結果と現在のコードを分析する。
               実験仮説を生成する。
               何が有効だったか、何がだめだったか、何が未試行かを検討する。

  2. EDIT    - アイデアを実装するためにスコープ内ファイルを変更する。
               変更は実験ごとに焦点を絞り、最小限に保つ。

  3. COMMIT  - git add + git commit を短く説明的なメッセージで行う。
               形式: "experiment: <short description of what changed>"

  4. RUN     - 指標コマンドを実行する。
               出力がコンテキストウィンドウにあふれないよう run.log にリダイレクトする。
               シェルに応じたリダイレクトを使う:
               - Bash/Zsh: `<command> > run.log 2>&1`
               - PowerShell: `<command> *> run.log`

  5. MEASURE - run.log から指標を抽出する。
               抽出に失敗した場合（クラッシュ/エラー）は、
               run.log の末尾 50 行を読んでエラーを確認する。

  6. DECIDE  - 現在の最良値と指標を比較する:
               - IMPROVED: コミットを保持する。「best」ベースラインを更新。
                 status = "keep" を記録。
               - SAME OR WORSE: 巻き戻す。`git reset --hard HEAD~1`。
                 status = "discard" を記録。
               - CRASH: クイック修正（typo、import、単純なエラー）を試みる。
                 修正を含めて実験コミットを amend（`git commit --amend`）し、
                 再実行する。実験番号は元のまま維持。
                 2 回試して修正不能なら、実験全体を巻き戻し
                 （`git reset --hard HEAD~1`）、status = "crash" を記録。

  7. LOG     - results.tsv に行を追記:
               experiment_number  commit_hash  metric_value  status  description

  8. CONTINUE - ステップ 1 に戻る。
```

### 実験戦略

実験アイデアを生成するときは、次の優先順に従います:

1. **まず低い果実から**: 単純なパラメータ調整、明白な非効率の改善。
2. **結果に基づく**: 有望だった方向性があれば、その方向をさらに掘る。
3. **停滞後は多様化**: 直近 3〜5 実験がすべて失敗なら、まったく別のアプローチを試す。
4. **勝ち筋の組み合わせ**: 実験 A と B がそれぞれ独立に改善したなら、組み合わせを試す。
5. **単純化パス**: 定期的にコード/複雑さを削っても指標が維持されるか確認する。
6. **大胆な変更**: 漸進的アイデアを使い切った後は、より大きなアーキテクチャ変更を試す。

### 制約への対応

- **時間予算**: 実行が想定時間の 2 倍を超えたら停止し、クラッシュとして扱う。
- **既存テスト**: 制約でテスト合格が必要なら、前後で実行し、壊れたら巻き戻す。
- **メモリ/リソース**: 監視し、指定上限を超えたら巻き戻す。

## フェーズ 4: レポート

ループ終了時（予算到達またはユーザー中断）:

1. **results.tsv 全体を表示**（整形済みテーブルとして）。
2. **要約**:
   - 実行した実験総数
   - 採用 / 破棄 / クラッシュの実験数
   - 開始時指標（ベースライン）と最終指標の比較
   - 改善率（パーセンテージ）
   - 最も効果の高かった変更 Top 3
3. **採用実験の累積 git log を表示**:
   `git log --oneline <start_commit>..HEAD`
4. **次のステップを提案**: 結果に基づき、人間の研究者が次に試すべきこと（自動実験にはリスク/複雑さが高すぎた案）を提案する。

## クイックリファレンス

### Results TSV 形式

タブ区切り、5 列:

```
experiment	commit	metric	status	description
0	a1b2c3d	0.997900	baseline	unmodified code
1	b2c3d4e	0.993200	keep	increase learning rate to 0.04
2	c3d4e5f	1.005000	discard	switch to GeLU activation
3	d4e5f6g	0.000000	crash	double model width (OOM)
```

### Git ワークフロー

- すべての実験は `autoresearch/<tag>` ブランチで実施
- 各実験は実行前にコミット
- 失敗した実験は `git reset --hard HEAD~1` で巻き戻す
- 成功した実験のみブランチを前進させる
- `results.tsv` と `run.log` は未追跡のまま維持（`.git/info/exclude` に追加）

### 主要原則

1. **すべてを測定する**: 測定なしの実験はしない。
2. **失敗は巻き戻す**: ブランチは改善時のみ前進。
3. **自律性を維持する**: 質問のために停止しない。行き詰まったらより深く考える。
4. **シンプルさを保つ**: 複雑さはコスト。得られる改善と比較する。
5. **すべてを記録する**: TSV は研究ジャーナル。
