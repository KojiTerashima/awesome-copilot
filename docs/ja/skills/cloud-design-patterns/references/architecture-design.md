# Architecture & Design Patterns

## Anti-Corruption Layer パターン

**課題**: 新しいシステムが、旧式のモデルや技術を使うレガシーシステムと統合する必要がある。

**解決策**: レガシー制約が新しい設計へ影響しないよう、モダンアプリケーションとレガシーシステムの間にファサードまたはアダプタ層を実装する。

**使用タイミング**:
- レガシーシステムから段階的に移行するとき
- ドメインモデルが異なるサードパーティシステムと統合するとき
- モダンアーキテクチャをレガシー制約から保護したいとき

**実装時の考慮点**:
- ドメインモデル間の変換レイヤーを作る
- レガシーとモダンのデータ構造間でマッピングする
- レガシーシステムのインターフェースを抽象化の背後に隔離する
- 変換による性能影響を考慮する
- 移行完了後に削除できるよう計画する

## Backends for Frontends (BFF) パターン

**課題**: 単一バックエンドでは、異なるクライアント種別に最適に対応できない場合がある。

**解決策**: 特定のフロントエンドアプリケーションやインターフェース向けに、個別のバックエンドサービスを作成する。

**使用タイミング**:
- クライアント種別（Web、モバイル、IoT）ごとに要件が異なるとき
- クライアントごとにペイロードのサイズや形を最適化したいとき
- フロントエンドと共通バックエンドの結合を弱めたいとき

**実装時の考慮点**:
- ユーザー体験またはクライアント種別ごとに1つのBFFを作る
- フロントエンドの要件に合わせてAPI契約を調整する
- BFF間でビジネスロジックを重複させない
- BFF間で共通サービスを共有する
- サービス数の増加を管理する

## Gateway Aggregation パターン

**課題**: クライアントが複数のバックエンドサービスからデータを必要とする。

**解決策**: ゲートウェイで複数リクエストを集約し、単一リクエストにまとめる。

**使用タイミング**:
- クライアントとバックエンド間のチャッタリングを減らしたいとき
- 単一ビューのために複数ソースのデータを結合するとき
- バックエンド呼び出しの並列化でレイテンシを下げたいとき

**実装時の考慮点**:
- APIゲートウェイで複数サービスの応答を集約する
- 可能な限りバックエンド呼び出しを並列実行する
- 部分的な障害を適切に処理する
- 集約応答のキャッシュを検討する
- ゲートウェイをモノリシック化しない

## Gateway Offloading パターン

**課題**: 複数サービス間で共通機能が重複している。

**解決策**: 共通機能または専門機能をゲートウェイプロキシへオフロードする。

**使用タイミング**:
- 横断的関心事（SSL、認証、ログ）を集約したいとき
- サービス実装を簡素化したいとき
- 共通機能を標準化したいとき

**実装時の考慮点**:
- SSL終端をゲートウェイへオフロードする
- 認証・認可をゲートウェイで実装する
- レート制限とスロットリングを処理する
- リクエスト/レスポンスのログを提供する
- ゲートウェイがボトルネックにならないようにする

## Gateway Routing パターン

**課題**: クライアントが単一エンドポイント経由で複数サービスへアクセスする必要がある。

**解決策**: 単一エンドポイントでリクエストをルーティングし、複数サービスへ振り分ける。

**使用タイミング**:
- 複数サービスへの単一入口を提供したいとき
- クライアントからバックエンド構成を抽象化したいとき
- サービスのバージョニングや移行戦略を有効にしたいとき

**実装時の考慮点**:
- URLパス、ヘッダー、クエリパラメータでルーティングする
- URL書き換えと変換をサポートする
- A/Bテストやカナリアデプロイを可能にする
- バックエンドサービスのヘルスチェックを実装する
- ルーティング性能を監視する

## Sidecar パターン

**課題**: アプリケーションが密結合なしで補助機能を必要としている。

**解決策**: 分離とカプセル化を提供するため、アプリケーションのコンポーネントを別プロセスまたは別コンテナとしてデプロイする。

**使用タイミング**:
- 既存アプリを変更せず機能追加したいとき
- 横断的関心事（ログ、監視、セキュリティ）を実装するとき
- 異種環境をサポートするとき

**実装時の考慮点**:
- メインアプリの隣にサイドカーを配置する
- ライフサイクル、リソース、ネットワークをメインアプリと共有する
- プロキシ、ログ、設定、監視に利用する
- 追加コンテナのリソースオーバーヘッドを考慮する
- サービス間でサイドカー実装を標準化する

## Strangler Fig パターン

**課題**: レガシーシステムを一括置換するのはリスクが高い。

**解決策**: 新しいアプリケーションやサービスで機能を少しずつ置き換え、レガシーシステムを段階的に移行する。

**使用タイミング**:
- レガシーアプリをモダナイズするとき
- ビッグバン移行のリスクを下げたいとき
- ビジネス価値を段階的に提供したいとき

**実装時の考慮点**:
- 段階移行する機能を特定する
- ファサードやプロキシで旧新の振り分けを行う
- 低リスクのコンポーネントから先に移行する
- 初期は旧新システムを並行稼働させる
- 最終的なレガシー廃止計画を立てる
