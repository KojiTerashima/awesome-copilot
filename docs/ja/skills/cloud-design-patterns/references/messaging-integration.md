# Messaging & Integration Patterns

## Choreography パターン

**課題**: 中央オーケストレータは結合を生み、単一障害点になる。
**解決策**: イベント駆動の協調によって、各サービスが業務処理の実行タイミングと実行方法を自律的に判断する。

**使用タイミング**:
- 疎結合なマイクロサービスアーキテクチャ
- イベント駆動システム
- 中央オーケストレーションのボトルネック回避

**実装時の考慮点**:
- publish-subscribe メッセージングでイベント配信する
- 各サービスがドメインイベントを発行し、必要なイベントを購読する
- 複雑なワークフローには saga パターンを実装する
- イベント重複配送を想定し冪等性を確保する
- 包括的なログと分散トレーシングを提供する

## Claim Check パターン

**課題**: 大きなメッセージがメッセージ基盤を圧迫する。
**解決策**: 大きなメッセージを、claim check（参照）と別保管ペイロードに分割する。

**使用タイミング**:
- メッセージサイズがシステム上限を超えるとき
- メッセージバス負荷を下げたいとき
- 大容量ファイル転送を非同期で扱うとき

**実装時の考慮点**:
- ペイロードをBlob StorageやDBに保存する
- メッセージバスには参照/URIのみ送る
- 保存ペイロードの有効期限ポリシーを実装する
- ペイロード保管のアクセス制御を行う
- ストレージコストと送信コストのバランスを考慮する

## Competing Consumers パターン

**課題**: 単一コンシューマではメッセージ量に追随できない。
**解決策**: 同一メッセージチャネルから複数の同時コンシューマが処理できるようにする。

**使用タイミング**:
- 高スループットが必要なとき
- メッセージ処理を水平スケールしたいとき
- 複数インスタンスに負荷分散したいとき

**実装時の考慮点**:
- メッセージが任意順序で処理可能であることを確認する
- 競合コンシューマキュー（Service Bus、RabbitMQ）を使う
- ハンドラの冪等性を実装する
- poison message をリトライ/デッドレターで処理する
- キュー深度に応じてコンシューマ数を調整する

## Messaging Bridge パターン

**課題**: 異なるシステムでメッセージ技術が非互換。
**解決策**: 非互換なメッセージシステム間を接続する中継層を構築する。

**使用タイミング**:
- メッセージシステム移行中
- レガシー統合時
- クラウドとオンプレミスメッセージング接続時

**実装時の考慮点**:
- システム間でメッセージ形式を変換する
- プロトコル差異に対応する
- 必要に応じて順序を維持する
- エラーハンドリングとリトライを実装する
- ブリッジの性能と健全性を監視する

## Pipes and Filters パターン

**課題**: 複雑な処理タスクは保守・再利用が難しい。
**解決策**: 複雑処理を独立再利用可能な要素（filters）へ分割し、チャネル（pipes）で接続する。

**使用タイミング**:
- 複数変換を伴うデータストリーム処理
- 再利用可能な処理部品を構築するとき
- 独立処理を並列化したいとき

**実装時の考慮点**:
- 各フィルタは単一変換のみ担当する
- メッセージキューやストリームで接続する
- 可能な限り並列実行を有効にする
- フィルタ内またはパイプライン全体でエラー処理する
- フィルタの合成・並べ替えをサポートする

## Publisher-Subscriber パターン

**課題**: 複数の関心コンシューマへ情報をブロードキャストしたい。
**解決策**: 送信側と受信側を疎結合に保ちつつ、イベントを複数コンシューマへ非同期通知する。

**使用タイミング**:
- 複数関係者へイベントを配信するとき
- イベント生成者と消費者を疎結合化したいとき
- イベント駆動アーキテクチャを実装するとき

**実装時の考慮点**:
- トピックベースまたはコンテンツベース購読を使う
- 要件に合う配送保証を確保する
- 選択的消費のため購読フィルタを実装する
- コンシューマ障害が発行側へ影響しないようにする
- 購読者ごとの順序要件を考慮する

## Scheduler Agent Supervisor パターン

**課題**: 分散アクションに調整と監視が必要。
**解決策**: スーパーバイザがワークフローを監視・管理し、分散サービス/リソースにまたがる一連のアクションを調整する。

**使用タイミング**:
- 複数ステップのワークフローをオーケストレーションするとき
- 分散トランザクションを調整するとき
- 耐障害性のある長時間プロセスを実装するとき

**実装時の考慮点**:
- Scheduler が Agent へタスクを配布する
- Agent が処理し状態を報告する
- Supervisor が進捗監視と障害対応を行う
- 失敗ステップの補償ロジックを実装する
- 回復のためワークフロー状態を保持する
