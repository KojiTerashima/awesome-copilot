# Deployment & Operational Patterns

## Compute Resource Consolidation パターン

**課題**: 複数タスクを分離して実行すると、リソース消費が非効率になる。

**解決策**: 複数のタスクや処理を単一の計算ユニットに統合する。

**使用タイミング**:
- インフラコストを削減したいとき
- リソース利用率を高めたいとき
- デプロイと運用管理を簡素化したいとき

**実装時の考慮点**:
- スケーリング要件が近い関連タスクをまとめる
- コンテナまたはマイクロサービスホスティングを活用する
- タスクごとのリソース使用量を監視する
- セキュリティ/信頼性のため必要な分離を確保する
- 統合効果と障害分離のバランスを取る

## Deployment Stamps パターン

**課題**: アプリケーションをリージョンや顧客セグメントごとにスケールさせる必要がある。

**解決策**: リージョンや顧客セグメントごとに提供するため、データストアを含むアプリケーションコンポーネントの独立したコピー（stamp）を複数デプロイする。

**使用タイミング**:
- 単一stampの限界を超えてスケールしたいとき
- リージョンごとのデータ所在地要件に対応するとき
- セキュリティや性能のためテナントを分離したいとき

**実装時の考慮点**:
- 各stampを完全に自己完結したデプロイにする
- 地理分散のため複数リージョンにstampを配置する
- 適切なstampへリクエストをルーティングする
- stampデプロイを一貫して管理する（IaC）
- stampの容量計画と追加タイミングを定義する

## External Configuration Store パターン

**課題**: アプリケーション設定がデプロイパッケージに埋め込まれている。

**解決策**: 設定情報をアプリケーションのデプロイパッケージから分離し、集中管理場所へ移す。

**使用タイミング**:
- 複数環境にまたがって設定管理するとき
- 再デプロイなしで設定変更したいとき
- 複数アプリ間で設定を共有したいとき

**実装時の考慮点**:
- Azure App Configuration、Key Vault などを使用する
- 設定変更通知を実装する
- 依存低減のためローカルキャッシュする
- 機密設定（接続文字列、シークレット）を保護する
- 設定変更をバージョン管理する

## Geode パターン

**課題**: 異なるリージョンのユーザーでレイテンシが高い。

**解決策**: バックエンドサービスを地理ノード群に展開し、どのリージョンのクライアント要求にも各ノードが対応できるようにする。

**使用タイミング**:
- 世界中に分散したユーザーのレイテンシを下げたいとき
- リージョンをまたぐ高可用性を提供したいとき
- active-active の地理分散を実装するとき

**実装時の考慮点**:
- 複数リージョンにアプリインスタンスを配置する
- グローバルにデータ複製する（一貫性への影響を考慮）
- 最も近く健全なリージョンへユーザーを誘導する
- マルチマスター書き込みの競合解決を実装する
- リージョンごとの健全性と性能を監視する

## Static Content Hosting パターン

**課題**: 計算インスタンスから静的コンテンツを配信するのは非効率。

**解決策**: 静的コンテンツをクラウドベースのストレージサービスへ配置し、クライアントへ直接配信する。

**使用タイミング**:
- 画像、動画、CSS、JavaScriptファイルをホスティングするとき
- Webサーバーの負荷を下げたいとき
- コンテンツ配信性能を改善したいとき

**実装時の考慮点**:
- Blob Storage、CDN、静的Webサイトホスティングを使う
- クロスオリジンアクセス用にCORSを有効化する
- 適切なキャッシュヘッダーを実装する
- グローバル配信にはCDNを使う
- 必要に応じてSASトークンで保護する
