# Performance Patterns

## Asynchronous Request-Reply パターン
**課題**: クライアントは同期応答を期待するが、バックエンド処理は非同期である。
**解決策**: バックエンド処理が非同期である必要がある一方で、フロントエンドには明確な応答が必要な場合に、両者を疎結合化する。
**使用タイミング**:
- 長時間実行のバックエンド処理
- クライアントが同期応答を待てない
- Web層から計算負荷の高い処理をオフロードしたい
**実装時の考慮点**:
- HTTP 202 (Accepted) と status 確認用 location header を返す
- ポーリング用 status endpoint を実装する
- callback 通知に webhook を検討する
- correlation ID でリクエスト追跡する
- 長時間処理のタイムアウトを実装する

## Cache-Aside パターン
**課題**: アプリケーションが同一データを繰り返しデータストアから取得する。
**解決策**: 必要時にデータストアからキャッシュへデータを読み込む。
**使用タイミング**:
- 高頻度アクセスの読み取り中心データ
- 更新頻度が低いデータ
- 主要データストア負荷を軽減したい
**実装時の考慮点**:
- データストア前にキャッシュを確認する
- cache miss 時に読み込み（lazy loading）する
- 適切な有効期限ポリシーを設定する
- キャッシュ無効化戦略を実装する
- キャッシュ障害時はデータストアへフォールバックする
- 分散環境でキャッシュ整合性を考慮する

## CQRS (Command Query Responsibility Segregation) パターン
**課題**: 読み取りと書き込みで要件やスケーリング特性が異なる。
**解決策**: 読み取り操作と更新操作を異なるインターフェースに分離する。
**使用タイミング**:
- 読み書きの性能特性が大きく異なる
- 読み書きを別チームが担当する
- 協調開発でマージ競合を減らしたい
- 読み書きで業務ロジックが大きく異なる
**実装時の考慮点**:
- 読み取りモデルと書き込みモデルを分離する
- event sourcing でモデルを同期する
- 読み書きを独立にスケールさせる
- 結果整合性の影響を考慮する
- command と query で適切にセキュリティを分ける

## Index Table パターン
**課題**: クエリが参照するフィールドに効率的なインデックスがない。
**解決策**: 頻繁に参照するフィールドに対してインデックスを作成する。
**使用タイミング**:
- クエリ性能を改善したい
- 複数のクエリパターンを支えたい
- ネイティブ索引が弱いNoSQLを使う
**実装時の考慮点**:
- 特定クエリ向け最適化テーブル/コレクションを分離作成する
- イベントやトリガーで非同期更新する
- 重複データのストレージ増加を考慮する
- インデックス更新失敗や不整合に対応する

## Materialized View パターン
**課題**: 必要なクエリに対しデータ形式が適していない。
**解決策**: クエリに最適でないデータに対し、1つ以上のデータストア上で事前計算済みビューを生成する。
**使用タイミング**:
- 正規化データへの複雑クエリ
- 複雑なJOIN/集約の読み取り性能改善
- 複数クエリパターンを効率対応したい
**実装時の考慮点**:
- バックグラウンドジョブ/トリガーで非同期更新する
- マテリアライズデータの鮮度許容を設計する
- ストレージコストとクエリ性能を両立する
- 可能なら増分更新を実装する

## Priority Queue パターン
**課題**: 一部リクエストは他より速い処理が必要。
**解決策**: 高優先度リクエストを先に処理する。
**使用タイミング**:
- 顧客ごとのサービスレベル差分提供
- 重要処理を先行実行したい
- 重要度が異なる混在ワークロード管理
**実装時の考慮点**:
- メッセージ優先度メタデータを使う
- 優先度別に複数キューを実装する
- 低優先度メッセージの飢餓を防ぐ
- 優先度ごとにキュー深度/処理時間を監視する

## Queue-Based Load Leveling パターン
**課題**: 断続的な高負荷でサービスが圧倒される。
**解決策**: タスクとサービスの間にキューを置き、負荷を平準化する。
**使用タイミング**:
- トラフィックスパイクからサービスを守る
- Producer/Consumer を疎結合化する
- 非同期処理を有効にする
**実装時の考慮点**:
- 適切なキュー技術（Azure Storage Queue、Service Bus など）を選ぶ
- 飽和検知のためキュー長を監視する
- キュー深度に基づくオートスケールを実装する
- 適切な message TTL を設定する
- dead-letter queue で poison message を処理する

## Rate Limiting パターン
**課題**: リソース枯渇防止のため利用量制御が必要。
**解決策**: アプリ、テナント、サービスのリソース消費を制御し、枯渇やスロットリングを防ぐ。
**使用タイミング**:
- バックエンド過負荷防止
- 公平利用ポリシー実装
- 単一テナントの独占防止
**実装時の考慮点**:
- token bucket / leaky bucket / fixed window を実装する
- 超過時に HTTP 429 を返す
- Retry-After ヘッダーを返す
- クライアント/ティア別の制限値を検討する
- 制限値を設定可能かつ監視可能にする

## Sharding パターン
**課題**: 単一データストアに容量・性能限界がある。
**解決策**: データストアを水平分割（shard）へ分割する。
**使用タイミング**:
- 単一DB限界を超えてスケールしたい
- データセット縮小でクエリ性能を改善したい
- 複数DBへ負荷分散したい
**実装時の考慮点**:
- 適切な shard key（hash/range/list）を選ぶ
- 偏りの少ないキーでホットパーティションを避ける
- クロスシャードクエリを慎重に扱う
- shard 再バランス/分割を計画する
- 複数shard運用の複雑性を考慮する

## Throttling パターン
**課題**: システム過負荷防止のためリソース消費制限が必要。
**解決策**: アプリ、テナント、サービスが使うリソース消費を制御する。
**使用タイミング**:
- 定義容量内で運用を保証したい
- ピーク時の枯渇防止
- SLAベースの配分を強制したい
**実装時の考慮点**:
- APIゲートウェイまたはサービスレベルで実装する
- 拒否/キューイング/機能劣化など戦略を使い分ける
- 適切なHTTPステータス（429, 503）を返す
- スロットリング内容をクライアントへ明確に伝える
- メトリクス監視で容量調整する
