# Reliability & Resilience Patterns

## Ambassador パターン
**課題**: サービスはネットワークリクエスト向けのプロキシ機能（ログ、監視、ルーティング、セキュリティ）を必要とする。  
**解決策**: コンシューマサービス/アプリケーションの代わりにネットワークリクエストを送るヘルパーサービスを作る。  
**使用タイミング**:
- 共通接続処理（監視、ログ、ルーティング）のオフロード
- 改修しづらいレガシーアプリ対応
- リトライ、circuit breaker、timeout handling の実装
**実装時の考慮点**:
- サイドカープロセス/コンテナとして同居させる
- プロキシ層で追加されるレイテンシを考慮する
- 単一障害点にならないようにする

## Bulkhead パターン
**課題**: 1コンポーネント障害が連鎖し全体へ波及する。  
**解決策**: アプリ要素をプールに分離し、1つが失敗しても他は継続できるようにする。  
**使用タイミング**:
- 重要リソースを非重要リソースから隔離
- 一部の枯渇が他領域へ影響するのを防止
- 消費者とリソースを分割して可用性向上
**実装時の考慮点**:
- バックエンド別に接続プールを分離
- サービスインスタンスをグループ分割
- 区画ごとにCPU/メモリ/スレッド上限を設定
- 健全性と容量を監視する

## Circuit Breaker パターン
**課題**: 失敗しやすい処理への再試行でリソースを浪費する。  
**解決策**: 失敗見込みの高い処理の繰り返し実行を止め、障害修復待ちで停止しないようにする。  
**使用タイミング**:
- 連鎖障害の防止
- リモートサービス停止時のfail fast
- ダウン時のフォールバック提供
**実装時の考慮点**:
- 発火閾値（失敗数/時間窓）を定義
- Closed/Open/Half-Openの3状態を実装
- 適切なタイムアウトを設定
- 状態遷移と失敗をログ化
- 意味のあるエラーメッセージを返す

## Compensating Transaction パターン
**課題**: 分散トランザクションは実装困難で未対応なことがある。  
**解決策**: 結果整合性オペレーションを構成する一連のステップで、実行済み作業を取り消す。  
**使用タイミング**:
- 分散システムで結果整合性を実装
- 途中失敗した多段業務をロールバック
- 2PC不可の長時間トランザクション処理
**実装時の考慮点**:
- 各ステップに補償ロジックを定義
- 取り消しに必要な状態を保存
- 補償処理の冪等性を確保
- 補償順序依存を考慮

## Retry パターン
**課題**: 分散システムでは一時障害が頻発する。  
**解決策**: 失敗操作を再試行し、予期される一時障害に対応する。  
**使用タイミング**:
- 一時的障害（ネットワーク揺らぎ、短時間停止）対応
- 短時間後の成功が見込める操作
- 非冪等操作（慎重な設計前提）
**実装時の考慮点**:
- 指数バックオフを使う
- 最大再試行回数を設定
- 一時障害と恒久障害を区別
- 冪等性確保または試行追跡
- thundering herd 回避の jitter を導入

## Health Endpoint Monitoring パターン
**課題**: 外部ツールがシステム健全性と可用性を検証する必要がある。  
**解決策**: 外部ツールが定期アクセスできる公開エンドポイントで機能チェックを提供する。  
**使用タイミング**:
- Webアプリ/バックエンド監視
- readiness/liveness probe 実装
- オーケストレータへ詳細な健康情報提供
**実装時の考慮点**:
- `/health` `/ready` `/live` などを公開
- DB、キュー、外部サービスの重要依存をチェック
- 適切なHTTPステータス（200, 503）を返す
- 機密健康情報に認証/認可を適用
- セキュリティ文脈で詳細度を切り替える

## Leader Election パターン
**課題**: 分散タスクは単一インスタンスによる調整が必要。  
**解決策**: 1インスタンスをリーダーとして選出し、協調タスクを管理させる。  
**使用タイミング**:
- 分散タスクの調整
- クラスタで共有リソース管理
- 重要タスクの単一実行保証
**実装時の考慮点**:
- Redis、etcd、ZooKeeperなど分散ロック利用
- リーダー障害時の自動再選出
- heartbeat で健全性検知
- フォロワーの迅速昇格を可能にする

## Saga パターン
**課題**: 分散トランザクションなしでマイクロサービス間の整合性を維持したい。  
**解決策**: ローカルトランザクションの連鎖で分散トランザクション時の整合性を管理する。  
**使用タイミング**:
- 複数サービスにまたがる長時間業務
- 2PCなしの分散トランザクション
- マイクロサービス間の結果整合性要件
**実装時の考慮点**:
- orchestration（集中）か choreography（イベント）を選ぶ
- ロールバック用補償トランザクションを定義
- 部分障害とロールバック処理に対応
- 全ステップの冪等性を確保
- 明確な監査証跡と監視を提供

## Sequential Convoy パターン
**課題**: 独立メッセージ群を止めず、関連メッセージは順序処理したい。  
**解決策**: 関連メッセージ群は定義順で処理しつつ、他群はブロックしない。  
**使用タイミング**:
- グループ内で厳密順序が必要
- 独立グループは並列処理可能
- セッションベースメッセージ処理を実装
**実装時の考慮点**:
- session ID / partition key で関連メッセージを束ねる
- 各グループ内は逐次、グループ間は並列で処理
- セッション内のメッセージ障害を適切に処理
