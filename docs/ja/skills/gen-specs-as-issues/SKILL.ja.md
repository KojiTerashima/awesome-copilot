# プロダクトマネージャー補助: 機能の特定と仕様化

このワークフローは、不足している機能を体系的に見つけ、優先順位を付け、実装に向けた詳細仕様を作るための手順を案内します。

## 1. プロジェクト理解フェーズ

- プロジェクト構成を確認し、全体の整理のされ方を把握する
- README.md と関連ドキュメントを読み、プロジェクトの中核機能を理解する
- 次の観点から既存実装の状況を把握する
  - 主要なエントリーポイント（CLI、API、UI など）
  - コアモジュールとその機能
  - 期待される振る舞いを理解するためのテスト
  - プレースホルダー実装の有無

**確認のための質問:**
- このプロジェクトの主目的は何か。
- どのようなユーザー課題を解決するのか。
- 現在の実装にはどのようなパターンがあるか。
- ドキュメントで触れられているのに、十分には実装されていない機能はどれか。

## 2. ギャップ分析フェーズ

- ドキュメント化された機能と実際の実装を比較する。ただし比較対象は実装済みの現状のみに限定する
- 実機能を持たない「プレースホルダー」コードを特定する
- ドキュメントにはあるが、堅牢な実装が欠けている機能を探す
- ユーザージャーニーを見て、壊れている手順や欠けている手順を特定する
- まずは中核機能を優先し、あると良い機能は後回しにする

**作成する出力:**
- 不足している可能性のある機能の一覧を作成する（5〜7 件）
- 各機能について次を記録する
  - 現在の実装状況
  - ドキュメント上の参照箇所
  - 未実装だった場合のユーザー体験への影響

## 3. 優先順位付けフェーズ

- 特定した各ギャップに対し、次の観点でスコアを付ける

**スコアリング表（1〜5 点）:**
- ユーザー影響度: どれだけ多くのユーザーが恩恵を受けるか
- 戦略適合性: コアミッションに合っているか
- 実装実現性: 技術的な複雑さはどの程度か
- 必要リソース: 開発工数はどの程度か
- リスク水準: 想定される負の影響はどの程度か

**優先度 = (ユーザー影響度 × 戦略適合性) / (実装工数 × リスク水準)**

**作成する出力:**
- スコアにもとづく上位 3 件の不足機能を提示する
- 各機能について次を示す
  - 機能名
  - 現在の状況
  - 未実装のままの場合の影響
  - 他機能への依存関係

## 4. 仕様策定フェーズ

- 優先度の高い各機能について、実用的で詳細な仕様を作成する
  - まず、複雑さより単純さを優先するという方針から始める
  - まずは MVP の機能に集中する
  - 開発者体験を考慮する
  - 仕様は実装しやすい形に保つ

**各機能仕様で扱う内容:**
1. **概要とスコープ**
   - どんな問題を解決するか
   - 何を含み、何を明確に含まないか

2. **技術要件**
   - 必要な中核機能
   - ユーザー向けインターフェイス（API、UI、CLI など）
   - 既存コードとの統合ポイント

3. **実装計画**
   - 作成または変更すべき主要モジュール / ファイル
   - アプローチを示す簡潔なコード例
   - 明確なデータ構造とインターフェイス

4. **受け入れ基準**
   - 何をもって完了とみなすか
   - 具体的にどの機能が動作する必要があるか
   - どのテストが通るべきか

## 5. GitHub Issue 作成フェーズ

- 各仕様について GitHub issue を作成する
  - 明確で説明的なタイトル
  - 本文に包括的な仕様
  - 適切なラベル（enhancement、high-priority など）
  - 必要に応じて MVP 方針を明示する

**Issue テンプレート構成:**

# [機能名]

## 概要
[機能と目的の簡単な説明]

## スコープ
[何を含み、何を明示的に含まないか]

## 技術要件
[具体的な技術要件と制約]

## 実装計画
[簡潔なコード例を含む段階的な進め方]

## 受け入れ基準
[機能完了とみなすための明確な要件一覧]

## 優先度
[優先度付けの根拠]

## 依存関係
- **ブロックする:** [この issue によってブロックされる issue の一覧]
- **ブロックされる:** [この issue が依存する issue の一覧]

## 実装規模
- **想定工数:** [Small/Medium/Large]
- **サブ issue:** [親 issue の場合はサブ issue へのリンク]


## 5.5 作業分担の最適化

- **独立性の分析**
  - 各仕様を確認し、本当に独立して進められる構成要素を特定する
  - 独立した作業ストリームを最大化できるように仕様を再構成する
  - 相互依存する要素の境界を明確にする

- **依存関係マッピング**
  - 依存が避けられない機能について、明確な issue 階層を定める
  - 全体機能の親 issue と、その構成要素のサブ issue を作る
  - `blocked by` と `blocks` の関係を明示的に記録する

- **作業量の平準化**
  - 大きい仕様は、小さく扱いやすいサブ issue に分割する
  - 各サブ issue は 1〜3 日で進められる規模にする
  - サブ issue ごとの受け入れ基準を含める

**実装ガイドライン:**
- GitHub issue のリンク記法を使って依存関係を明示する
- 依存状態を示すラベル（例: `blocked`, `prerequisite`）を付ける
- 各 issue に想定複雑度 / 工数を含め、スプリント計画に役立てる

## 6. 最終レビュー フェーズ

- 作成したすべての仕様を要約する
- 機能間の実装依存関係を強調する
- 論理的な実装順序を提案する
- 想定される課題や考慮点を記録する

このプロセス全体を通じて、次を忘れないこと:
- 複雑さより単純さを優先する
- まずは動く最小実装から始める
- 開発者体験を重視する
- 将来拡張できる土台をつくる
- オープンソースのコミュニティと貢献モデルを考慮する

このワークフローを体現することで、機能の仕様化と優先順位付けの進め方に一貫性が生まれ、ソフトウェアプロジェクトをより思慮深く、ユーザー中心に進化させやすくなります。
