# OOコンポーネントドキュメント

オブジェクト指向コンポーネントの新しいドキュメントを作成するか、現在の実装を分析して既存のコンポーネントドキュメントファイルを更新します。

## まずモードを決定する

何かを書く前にワークフローを選択してください：

1. ユーザーが既存のドキュメントMarkdownファイルを提供する、ドキュメントパスを指定する、または既存ドキュメントの更新や改訂を明示的に要求する場合は、**更新モード**を使用します。[references/update-mode.md](references/update-mode.md)に従ってください。
2. ユーザーがソースファイルまたはフォルダーを提供する、コンポーネントパスを指定する、またはコードからドキュメントを生成するよう要求する場合は、**作成モード**を使用します。[references/create-mode.md](references/create-mode.md)に従ってください。
3. コードと既存のドキュメントファイルの両方が提供された場合は、既存のドキュメントファイルを出力ターゲットとして扱い、現在のソースコードを真実の情報源として使用します。
4. 要求が曖昧な場合は、可能な限りパスの種類からモードを推測してください：既存のMarkdownドキュメントファイルは更新モード、ソース/コンポーネントパスは作成モードを意味します。

## ドキュメント標準

- DOC-001: C4モデルのドキュメントレベル（コンテキスト、コンテナ、コンポーネント、コード）に従う
- DOC-002: Arc42ソフトウェアアーキテクチャドキュメントテンプレートに整合させる
- DOC-003: IEEE 1016ソフトウェア設計記述標準に準拠する
- DOC-004: アジャイルドキュメンテーションの原則（価値を追加する十分なドキュメント）を使用する
- DOC-005: 主な対象読者を開発者および保守者とする

## 共有分析ガイダンス

- ANA-001: 主なコンポーネント境界を決定し、入力がフォルダー、ファイル、または既存のドキュメントターゲットのいずれかかを判断する
- ANA-002: クラス構造、継承、コンポジション、インターフェースについてソースコードファイルを調査する
- ANA-003: デザインパターン、アーキテクチャ上の決定、統合ポイントを特定する
- ANA-004: 公開API、インターフェース、依存関係、使用パターンを文書化または更新する
- ANA-005: メソッドのパラメーター、戻り値、非同期動作、例外、ライフサイクルの懸念を記録する
- ANA-006: パフォーマンス、セキュリティ、信頼性、保守性、拡張性の特性を評価する
- ANA-007: データフロー、協調パターン、周辺コンポーネントとの関係を推測する
- ANA-008: 実装に基づいたドキュメントを作成し、コードでサポートされていない動作を創作しない

## 共有出力要件

- [assets/documentation-template.md](assets/documentation-template.md)を正規のセクションチェックリストおよび基本構造として使用する
- Markdown形式で出力し、明確な見出し階層、必要に応じて表、例示用のコードブロック、アーキテクチャ関係を可視化する場合はMermaid図を使用する
- 例やインターフェースの説明は一般的なプレースホルダーではなく、現在の実装に合わせる
- コード、プロジェクト構造、設定、または明確に述べられた仮定で裏付けられる情報のみを含める
- ソースのカバレッジが不完全な場合は推測せず、制限を明示的に記述する

## 言語別最適化

- LNG-001: **C#/.NET** - async/await、依存性注入、設定、破棄、オプションパターン
- LNG-002: **Java** - Springフレームワーク、アノテーション、例外処理、パッケージング、依存性注入
- LNG-003: **TypeScript/JavaScript** - モジュール、非同期パターン、型、npm依存関係、ランタイム境界
- LNG-004: **Python** - パッケージ、仮想環境、型ヒント、テスト、依存関係管理

## エラー処理

- ERR-001: パスが存在しない場合、期待されるパスとスキルがソースパスまたは既存のドキュメントファイルのどちらを必要とするかを説明する
- ERR-002: 関連するソースファイルが見つからない場合、そのギャップを文書化し、次に調査すべき可能性のある場所を提案する
- ERR-003: 要求からドキュメントターゲットを推測できない場合は曖昧さを述べ、推測が不可能な場合にのみ不足しているパスを尋ねる
- ERR-004: コードが非標準のアーキテクチャパターンを使用している場合は、一般的なパターンに無理に当てはめるのではなくカスタムアプローチを文書化する
- ERR-005: ソースアクセスが不完全な場合は、利用可能な証拠で続行し、サポートされていないセクションを明確に指摘する

## ワークフロー

1. タスクが作成モードか更新モードかを決定する。
2. コンポーネントの実装および公開インターフェースや内部構造を理解するために必要な関連ファイルを調査する。
3. [assets/documentation-template.md](assets/documentation-template.md)を共有ドキュメントの足場として使用する。
4. [references/create-mode.md](references/create-mode.md)または[references/update-mode.md](references/update-mode.md)のモード別ルールを適用する。
5. 図、例、インターフェース、依存関係、品質属性が現在の実装を反映するようにドキュメントを作成または改訂する。

## 完了基準

- ドキュメントはコンポーネントの目的、アーキテクチャ、インターフェース、実装詳細、使用パターン、品質属性、参照を明確に特定している。
- フロントマターのフィールドは選択されたモードに正確である。
- 例と図は実装に一致している。
- 不明点、ギャップ、仮定は明示的に指摘されている。
