# 更新モード

入力が既存のドキュメントMarkdownファイルである場合や、ユーザーが既存のコンポーネントドキュメントの更新を依頼した場合に、このワークフローを使用します。

## 入力処理

- まず既存のドキュメントを読み込み、現在の構造、用語、およびフロントマターのメタデータを理解します。
- `component_path`フロントマターが存在する場合は、そこからコンポーネントのソースパスを抽出します。
- `component_path`がない場合は、ドキュメントの内容や周辺のリポジトリ構造からコンポーネントパスを推測します。
- ドキュメントとコードが矛盾する場合は、現在の実装を真実の情報源として使用します。

## 更新特有の要件

- 既存のドキュメントファイルを出力先として保持します。
- `date_created`は保持します。
- `last_updated`は現在の日付に更新します。
- バージョン履歴や所有権のメタデータは、依然として正確な場合は保持し、コードやリポジトリの証拠で変更が示されている場合のみ更新します。
- 既存の構成は有用な場合は維持しますが、内容が共有テンプレートの期待に沿うよう整合性を保ちます。

## 更新特有の分析の焦点

- 既存のドキュメントと現在のコードを比較し、古くなったAPI、時代遅れの図、名前変更された依存関係、変更された使用パターンを特定します。
- 明らかな破壊的変更、非推奨機能、または大きなアーキテクチャの変化を強調します。
- メソッド表、例、図、依存関係リスト、品質属性の注記を現在の実装に合わせて更新します。
- コンポーネントが成長した場合や、現在のドキュメントにメンテナ向けに必要な情報が欠けている場合のみ、欠落しているセクションを追加します。

## 更新特有の出力ガイダンス

- 既存ドキュメントの有用な編集上の選択は保持し、古くなったり誤解を招く内容は削除します。
- 例は現在のAPI形状に概念的に合うように更新します。
- Mermaid図は汎用のプレースホルダーに置き換えるのではなく、更新します。
- 更新によって重要な互換性や動作の変更が明らかになった場合は、移行ノートや変更履歴を追加します。
