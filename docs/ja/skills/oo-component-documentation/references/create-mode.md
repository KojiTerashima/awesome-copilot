# 作成モード

入力がコンポーネントのソースパスである場合や、ユーザーがコードから新しいドキュメントを生成するよう要求した場合にこのワークフローを使用します。

## 入力処理

- コンポーネントを表す単一ファイルまたはフォルダパスを受け入れます。
- 入力がフォルダの場合、そのフォルダ内の関連ソースファイルおよび近隣のサポートファイルを解析します。
- 入力が単一ファイルの場合、それを主要なコンポーネントのエントリポイントとして扱い、協力者やインターフェースを理解するために隣接ファイルを必要に応じて調査します。

## 作成特有の要件

- 新しいドキュメントは `/docs/components/` に保存します。
- ファイル名は `[component-name]-documentation.md` とします。
- `component_path` はユーザーが提供したソースパスに設定します。
- `date_created` は現在の日付に設定します。
- `last_updated` は対象領域のリポジトリ規約で作成時に必要とされる場合のみ設定します。
- `version`、`owner`、`tags` などの任意のメタデータは、信頼できる推測が可能な場合のみ設定します。

## 作成特有の解析の焦点

- コード構造から主要なコンポーネント名と責務を特定します。
- 初期のシステムコンテキスト、スコープの境界、依存関係、デザインパターン、協力モデルを明らかにします。
- 実際の公開インターフェースからインターフェース表と使用例を作成します。
- ドキュメントを初めて見る読者向けに、コンポーネント構造、依存関係、データフローを紹介するMermaid図を作成します。

## 作成特有の出力ガイドライン

- `../assets/documentation-template.md` の完全なセクション構造を使用します。
- 導入部はコンポーネントの機能と存在理由の新鮮な概要として記述します。
- プレースホルダーよりも完全なセクションを優先し、情報がない場合はテンプレート文を残すのではなく短い制限事項の注記でそのセクションをマークします。
- 変更履歴や移行ノートは、コードやリポジトリ履歴に以前のバージョンや移行の懸念がある証拠がある場合のみ含めます。
