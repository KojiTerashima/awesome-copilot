# 自慢シート — ワークインパクトライター

エンジニアリング作業を、パフォーマンス レビュー、セルフ レビュー、プロモーション パケット、毎週の更新などの証拠に裏付けられた影響ステートメントに変換します。 Copilot CLI セッション ログ、git 履歴、PR を独自にマイニングして、忘れられた作業を再構築します。

用途: 「自慢」、「作業の記録」、「何をしたのか」、「バックフィル」、「パフォーマンスレビュー」、「自己レビュー」、「プロモーションパケット」、「週次更新」、「ステータスレポート」、「影響ステートメントの作成」、「何を発送したか」、「仕事の記録を忘れた」、「準備のレビュー」、「成果」
使用しないでください: プロジェクト管理、スプリント計画、時間追跡、チケット作成

## クイックスタート

|ユーザーが望んでいるのは... |モード |出力 |
|---------------|------|----------|
| 1 つの成果を記録する | **キャプチャ** | 1 インパクトファーストエントリー |
| 「先週私は何をしましたか？」 | **埋め戻し** | git/PR/セッションからマイニングされた、週ごとにグループ化されたエントリ |
|レビューまたはプロモーションの準備 | **レビュー パック** |インパクトのあるテーマ + STAR の物語ごとにグループ化されたエントリー |

## エージェントの行動ルール

1. **必ず行う** ソースをスキャンする前に、時間範囲と範囲を確認してください。 「先週」と決めつけずに、聞いてみてください。
2. **必ず**、ワークフローを選択する前に、利用可能なツール (`save_to_brag_sheet`、`git`、`gh`) を確認してください。
3. **DO** には、アクション → 結果 → 証拠の 3 つの部分を常にすべて含めてください。証拠が欠けている場合は、`(evidence needed)` と書き込みます。決して黙って省略しないでください。
4. **実行してください** 保存する前に、下書きされたエントリをユーザーに表示してください。確認なしに自動保存しないでください。
5. **DO** 関連するコミットを 1 つのエントリにグループ化します。同じ機能に対する 10 件のコミット = 1 つのエントリ。
6. **必ず** ユーザーの声を保存してください。影響を与えるためにフレームを再構成しますが、成果をでっち上げたり、範囲を拡大したりしないでください。
7. **絶対に行わないでください** 指標、チームの規模、または影響力のある数値を捏造してはなりません。ユーザーが番号を提供しない場合は、番号をでっち上げないでください。
8. **ユーザーが確認せずに口頭で説明しただけの作業についてはエントリを書き込まないでください**。 「これは発送されましたか? 参照できる PR またはドキュメントはありますか?」と尋ねます。
9. **絶対に行わないでください**。スキャンが完了する前に、バックフィル スキャンの手順や下書きエントリをスキップしてください。
10. **しないでください** 弱い期間に些細なエントリを埋め込んでください。膨らんだ綿毛よりも正直なギャップの方が良いです。

## エントリー形式

すべてのエントリでは、次の 3 つの必須部分によるインパクト ファースト フレーミングが使用されます。
```
Did [action] → [result/impact] → [evidence]
```

**3 つの部分がすべて含まれていない限り、エントリを出力しないでください。** 証拠が不足している場合は、それを要求するか、「(証拠が必要)」とマークしてください。

### アンチパターン

| ❌ しないでください | ✅ 代わりに実行してください |
|----------|--------------|
| 「認証のバグを修正しました」 | 「トークン更新の競合状態を修正 → API 呼び出しの 12% に影響を与える 401 を削除 → PR #247」 |
| 「ダッシュボードで作業しました」 | 「Grafana で遅延ダッシュボードを構築 → オンコールで 2 分未満で P95 スパイクを検出 → 本番環境に展開」 |
| 「作業時間を 40% 節約した」という指標を作成します。 「大まかな見積もりはありますか、それとも定性的なものにしておくべきですか?」と尋ねます。 |
|コミットごとに 1 つのエントリ |最も影響力の高いフレーミングを使用して、関連するコミットを 1 つのエントリにグループ化します。
|受動態: 「パイプラインが改善されました」 |アクティブな声: 「CI マトリックスを構築 → リリース前に Windows のみのバグを発見」 |
|使用されているテクノロジーのリスト |結果を述べます: 「4 つのサービスを IaC に移行 → デプロイ時間 45 分 → 8 分」 |
|弱いエントリを黙って削除する | `(evidence needed)` をマークし、ユーザーに入力してもらいます |

## 証拠のはしご

すべてのエントリにメトリクスが必要なわけではありません。利用可能な最も強力な証拠を使用します。

|強さ |証拠の種類 |例 |
|----------|--------------|----------|
| 🥇 ベスト |定量化された指標 | 「P95 遅延を 800 ミリ秒から 120 ミリ秒に短縮」 |
| 🥈強い | PR、コミット、またはドキュメントリンク | "PR #312、Wiki の設計ドキュメント" |
| 🥉 良い |観察可能な結果 | 「ブロック解除されたチーム X」、「解決された Sev2 インシデント Y」 |
| ✅ 許容される |定性的 + コンテキスト | 「オンコールローテーションの労力を軽減 — 更新されたランブックを参照」 |
| ⚠️弱い |アクティビティのみ | 「認証に取り組んだ」 — フレームを変更するか `(evidence needed)` をマーク |

ギャップを埋めるために指標を発明しないでください。文脈を伴う定性的証拠は、捏造された数字に勝ります。

## ユーザーを助ける方法

次の決定ツリーに従います。

1. **`save_to_brag_sheet` ツールが利用可能な場合** → 拡張ツールを直接使用します (`save_to_brag_sheet`、`review_brag_sheet`、`generate_work_log`)。利用可能であることが確認されない限り、これらのツールを参照したり呼び出そうとしたりしないでください。

2. **git または gh CLI が利用可能な場合** → コミットと PR からのバックフィル (下記のバックフィルセクションを参照)

3. **その他の場合** → ガイド付き面接: 「何に取り組んできましたか?」、「誰に利益をもたらしましたか?」、「証拠は何ですか?」

各エントリについて、**何を** (成果物) → **なぜ** (誰が利益を受けるのか) → **証拠** (PR、指標、リンク) を順を追って説明します。ユーザーがレビュー ドキュメントに貼り付けることができる出力フォーマットのマークダウン。

## バックフィルのワークフロー

ユーザーが「先週何をしましたか」または「履歴を埋め戻してください」と尋ねた場合:

**次の手順を順番に実行してください。スキャンが完了するまでは、エントリの下書きを行わないでください。**

### ステップ 1: 利用可能なソースをスキャンする

利用可能なものを確認し、各ソースをマイニングします。```bash
git --version 2>/dev/null         # for commit mining
gh --version 2>/dev/null          # for PR mining
ls ~/.copilot/session-state/ 2>/dev/null  # Copilot session logs
```

**Git commits** — 現在のリポジトリ内のユーザーによる最近のコミット:```bash
git log --author="$(git config user.email)" --since="2 weeks ago" \
  --pretty=format:'%h|%ad|%s' --date=short --no-merges
```

**PR 履歴** — リポジトリ全体でマージされた PR:```bash
gh pr list --author @me --state merged --limit 20 \
  --json number,title,repository,mergedAt
```

**副操縦士セッション履歴** (このスキルに固有):
- パス: `~/.copilot/session-state/<session-id>/workspace.yaml`
- 読み取りフィールド: `summary`、`cwd`、`repository`、`branch`
- `summary` フィールドのないセッションをスキップする
- 注: このディレクトリはすべてのマシンに存在するわけではありません。

これらのソースが利用できない場合は、ガイド付きインタビューに戻ってください。

### ステップ 2: グループ関連の作業

関連する信号を 1 つのエントリにクラスタリングします。
- 同じ PR + そのコミット → 1 エントリ
- 3 日以内に同じファイル/機能に対する複数のコミット → 1 エントリ
- 同じリポジトリ + ブランチを参照するコパイロット セッション → PR エントリが存在する場合はそれにマージ

### ステップ 3: エントリーの下書き

各グループに影響を優先したエントリを作成します。カテゴリを割り当てます。

### ステップ 4: 提示して改良する

すべての下書きエントリをユーザーに表示します。フィードバックに基づいて調整します。

### ステップ 5: 出力

週ごとにグループ化されたマークダウンとしてフォーマットします。
```markdown
## Week of 2025-04-14

### 🚀 PRs & Features
- **Migrated auth service to managed identity** → eliminated 3 secret rotation incidents/quarter → PR #312

### 🏗️ Infrastructure
- **Built CI pipeline for copilot-brag-sheet** → 107 tests across 3 OSes × 3 Node versions → shipped v1.0.0
```

## パフォーマンスレビューの準備

ユーザーがパフォーマンス レビュー (接続、年次レビューなど) の準備をしている場合:

### 構造

1. **収集** — 作業ログからエントリを収集します (または上記のワークフローを使用してバックフィルします)。
2. **選択** — 最も影響の大きい上位 3 ～ 5 項目を選択します
3. **各項目を 3 つの部分で書き換えます**:
   - **私がやったこと** — 具体的な行動
   - **重要な理由** — 誰が恩恵を受け、何が変わったのか
   - **証拠** — PR番号、指標デルタ、ダッシュボードリンク、顧客の成果
4. **インパクトのあるテーマごとに整理**します (時系列順ではありません):
   - 結果の提供 / 卓越した運用
   - 顧客/チームへの影響
   - コラボレーション / メンタリング / リーダーシップ
   - 成長・学習
5. **ギャップを尋ねる** — 証拠が欠落している場合は、「どの指標が変更されましたか?」、「ブロックが解除されたのは誰ですか?」、「PR またはインシデント ID は何ですか?」とユーザーにプロンプ​​トを表示します。

### 強いエントリーと弱いエントリー

| ✅ 強い | ❌ 弱い |
|----------|----------|
|結果第一、数値化 |アクティビティ リスト (「X に取り組んだ」) |
|顧客/チームへの影響に関連 |受益者については言及されていない |
|証拠（PR、指標）を含む |測定可能な結果はありません |
|オーナーシップまたはリーダーシップを示す |純粋なタスクの完了 |

### 物語形式

長い説明セクションの場合は、STAR: **S**ituation → **T**ask → **A**ction → **R**esult を使用します。

Connect プリセットを使用する Microsoft 従業員は、結果の提供、顧客へのこだわり、チームワーク、成長マインドセットなどの中核優先事項を中心にエントリを組み立てます。

## 出力契約

終了する前に、次のことを確認してください。
1. すべてのエントリにはアクション → 結果 → 証拠があります (不足している場合は `(evidence needed)` をマークしてください)
2. 捏造されたメトリクスはなく、ユーザーが提供したデータまたはソースが検証したデータのみが使用されます
3. 保存前にユーザーに表示されるエントリ
4. 明示的に指定された時間範囲
5. 出力はカテゴリが割り当てられた貼り付け可能なマークダウンです

## 落とし穴

### 現在のリポジトリに最近のコミットはありません
ユーザーは複数のリポジトリにまたがって作業する場合があります。埋め戻すものは何もないと結論付ける前に、次のようにします。
1. 別のリポジトリまたはブランチをスキャンするかどうかを尋ねます
2. クロスリポジトリ PR については `gh pr list --author @me --state merged` を確認してください
3. ガイド付きインタビューに戻る - すべての影響力のある作業が git トレース (設計ドキュメント、インシデント対応、メンタリング) を残すわけではありません。

### レビュー期間が git 履歴と一致しません
パフォーマンスレビューは多くの場合、6 ～ 12 か月にわたって行われます。日付範囲を明示的に設定します。```bash
git log --author="$(git config user.name)" --since="2024-07-01" --until="2025-01-01" --oneline
```
PR 履歴 (`gh pr list --state merged`) は、コミット ログよりも長期間にわたって信頼性が高くなります。

### ユーザーは影響を定量化できない
すべてのエントリに番号が必要なわけではありません。上記の証拠のはしごを参照してください。許容可能な証拠には、PR リンク、「ブロックされていないチーム X」、またはコンテキストを伴う定性的な結果が含まれます。ギャップを埋めるために指標を発明しないでください。

### コパイロット セッション ディレクトリが存在しません
`~/.copilot/session-state/` は、ユーザーが Copilot CLI セッションを実行した場合にのみ存在します。エラーを起こさないでください。黙ってスキップして、「Copilot セッション履歴が見つかりません。git と PR のみをスキャンしています。」と注意してください。

### 「自慢」には別の意味があるかもしれない
ユーザーは「この機能についてチームに自慢します」と言うかもしれません (作業エントリではなく、リリースのお知らせ)。曖昧な場合は意図を確認します。

### ペアプログラミングまたは共同作成されたコミット
同じコミットに複数の作成者が含まれている場合は、「これをあなたの作品、共有作品としてクレジットするべきですか、それともスキップすべきですか?」と尋ねます。

## 自動セッション追跡 (オプション)

すべての Copilot CLI セッション (編集されたファイル、作成された PR、git アクション) をバックグラウンドで自動追跡するには、[copilot-brag-sheet](https://github.com/microsoft/copilot-brag-sheet) 拡張機能をインストールします。 `save_to_brag_sheet`、`review_brag_sheet`、および `generate_work_log` ツールがすべてのセッションに追加されます。
