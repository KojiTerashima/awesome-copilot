# Automate This

手作業プロセスの画面録画を分析し、それを動く自動化に落とし込みます。

ユーザーは繰り返しや面倒な作業をしている自分を録画し、その動画ファイルをあなたに渡します。あなたは何をしていて、なぜそれをしていて、どうスクリプト化して省力化できるかを見極めます。

## 前提条件チェック

録画を分析する前に、必要なツールが使えるか確認します。これらのチェックは静かに実行し、問題がある場合のみ表示します。

```bash
command -v ffmpeg >/dev/null 2>&1 && ffmpeg -version 2>/dev/null | head -1 || echo "NO_FFMPEG"
command -v whisper >/dev/null 2>&1 || command -v whisper-cpp >/dev/null 2>&1 || echo "NO_WHISPER"
```

- **ffmpeg は必須です。** ない場合はユーザーに次を案内します: `brew install ffmpeg`（macOS）または利用 OS 向けの同等手段。
- **Whisper は任意です。** 録画にナレーションがある場合のみ必要です。未導入かつ録画に音声トラックがある場合は、`pip install openai-whisper` または `brew install whisper-cpp` を提案します。ユーザーが導入を希望しなければ、映像のみの分析で進めます。

## Phase 1: 録画からコンテンツを抽出する

動画ファイルのパス（通常は `~/Desktop/`）が与えられたら、映像フレームと音声の両方を抽出します。

### フレーム抽出

2 秒ごとに 1 フレームを抽出します。これは網羅性とコンテキストウィンドウ制限のバランスがよい設定です。

```bash
WORK_DIR=$(mktemp -d "${TMPDIR:-/tmp}/automate-this-XXXXXX")
chmod 700 "$WORK_DIR"
mkdir -p "$WORK_DIR/frames"
ffmpeg -y -i "<VIDEO_PATH>" -vf "fps=0.5" -q:v 2 -loglevel warning "$WORK_DIR/frames/frame_%04d.jpg"
ls "$WORK_DIR/frames/" | wc -l
```

このセッション中の後続の一時ファイルパスはすべて `$WORK_DIR` を使ってください。実行ごとに作られる mode 0700 のディレクトリにより、抽出フレームは現在のユーザーだけが読めます。

録画が 5 分を超える場合（150 フレーム超）は、コンテキスト制限内に収めるため 4 秒ごとに 1 フレームへ間隔を広げます。長尺録画のためサンプリング頻度を下げることをユーザーに伝えてください。

### 音声抽出と文字起こし

動画に音声トラックがあるか確認します。

```bash
ffprobe -i "<VIDEO_PATH>" -show_streams -select_streams a -loglevel error | head -5
```

音声がある場合:

```bash
ffmpeg -y -i "<VIDEO_PATH>" -ac 1 -ar 16000 -loglevel warning "$WORK_DIR/audio.wav"

# 利用可能な whisper バイナリを使用
if command -v whisper >/dev/null 2>&1; then
  whisper "$WORK_DIR/audio.wav" --model small --language en --output_format txt --output_dir "$WORK_DIR/"
  cat "$WORK_DIR/audio.txt"
elif command -v whisper-cpp >/dev/null 2>&1; then
  whisper-cpp -m "$(brew --prefix 2>/dev/null)/share/whisper-cpp/models/ggml-small.bin" -l en -f "$WORK_DIR/audio.wav" -otxt -of "$WORK_DIR/audio"
  cat "$WORK_DIR/audio.txt"
else
  echo "NO_WHISPER"
fi
```

どちらの whisper バイナリも利用できず、かつ録画に音声がある場合は、ナレーション文脈が欠けることをユーザーに伝え、Whisper をインストールするか（`pip install openai-whisper` または `brew install whisper-cpp`）、映像のみ分析で進めるか確認します。

## Phase 2: プロセスを再構築する

抽出したフレーム（利用可能なら文字起こしも）を分析し、ユーザーが何をしたかを構造化して理解します。フレームを順番に見て、次を特定します。

1. **使用アプリケーション** — 録画にどのアプリが登場するか（browser, terminal, Finder, mail client, spreadsheet, IDE など）
2. **操作の順序** — ユーザーは何を、どの順で行ったか。クリック単位・手順単位で。
3. **データフロー** — 手順間でどんな情報が移動したか（コピーしたテキスト、ダウンロードファイル、フォーム入力など）
4. **判断ポイント** — ユーザーが立ち止まって確認したり、選択した場面はあったか
5. **繰り返しパターン** — 異なる入力で同じことを複数回行っていたか
6. **つらいポイント** — どこが遅い・ミスしやすい・面倒に見えたか。ナレーションで直接示されることが多い（「ここ嫌い」「これ毎回すごく時間かかる」「これを全部に対してやる必要がある」など）。

この再構築結果を番号付き手順リストとしてユーザーに提示し、**自動化提案前に**正確か確認を取ってください。ここは非常に重要です。理解が間違っていると自動化は役に立ちません。

形式:

```
この録画であなたがしている作業は、次のように見えます。

1. Chrome を開き、[specific URL] に移動
2. 認証情報でログイン
3. レポートダッシュボードへクリックして進む
4. CSV をエクスポートしてダウンロード
5. CSV を Excel で開く
6. 列 B が "pending" の行をフィルタ
7. それらの行を新しいスプレッドシートにコピー
8. 新しいスプレッドシートを [recipient] にメール送信

レポート種別ごとに、手順 3〜8 を 3 回繰り返していました。

[ナレーションがあった場合]: エクスポート手順が最も遅く、
これを毎週月曜の朝に行っていると話していました。

この理解で合っていますか？間違いや漏れはありますか？
```

ユーザーが再構築結果の正確性を確認するまで、Phase 3 には進まないでください。

## Phase 3: 環境フィンガープリント

自動化を提案する前に、ユーザーが実際に使える環境を把握します。次のチェックを実行します。

```bash
echo "=== OS ===" && uname -a
echo "=== Shell ===" && echo $SHELL
echo "=== Python ===" && { command -v python3 && python3 --version 2>&1; } || echo "not installed"
echo "=== Node ===" && { command -v node && node --version 2>&1; } || echo "not installed"
echo "=== Homebrew ===" && { command -v brew && echo "installed"; } || echo "not installed"
echo "=== Common Tools ===" && for cmd in curl jq playwright selenium osascript automator crontab; do command -v $cmd >/dev/null 2>&1 && echo "$cmd: yes" || echo "$cmd: no"; done
```

これを使って、提案はユーザーがすでに持っているツールに制約してください。より簡単な道が本当に機能しない場合を除き、新規ツールを 5 つも入れる前提の自動化は提案しないでください。

## Phase 4: 自動化を提案する

再構築したプロセスとユーザー環境に基づいて、最大 3 段階で自動化を提案します。すべてのプロセスに 3 段階が必要なわけではありません。適切に判断してください。

### Tier 構成

**Tier 1 — Quick Win（セットアップ 5 分以内）**  
最小限で効果のある自動化。shell alias、ワンライナー、キーボードショートカット、AppleScript 断片など。プロセス全体ではなく、最もつらい 1 ステップを自動化します。

**Tier 2 — Script（セットアップ 30 分以内）**  
フルプロセスをエンドツーエンドで自動化する単体スクリプト（bash、Python、Node のうちユーザー環境にあるもの）。一般的なエラーを処理し、必要時に手動実行できます。

**Tier 3 — Full Automation（セットアップ 2 時間以内）**  
Tier 2 のスクリプトに加えて、定期実行（cron、launchd、または GitHub Actions）、ログ、エラー通知、および必要な連携の足場（API キー、auth token など）を整備します。

### 提案フォーマット

各 tier で次を提示します:

```
## Tier [N]: [Name]

**What it automates:** [再構築したどの手順を自動化するか]
**What stays manual:** [どの手順は人手のままか]
**Time savings:** [録画時間と繰り返し回数に基づく、1 回あたりの推定削減時間]
**Prerequisites:** [未インストールで必要なもの。理想はなし]

**How it works:**
[平易な英語で 2〜3 文の説明]

**The code:**
[疑似コードではなく、完全に動くコメント付きコード]

**How to test it:**
[可能ならドライランから始め、動作確認する正確な手順]

**How to undo:**
[問題時に変更を戻す方法]
```

### アプリ種別ごとの自動化戦略

録画に現れるアプリに応じて、次の戦略を使ってください。

**ブラウザ中心のワークフロー:**
- 第一候補: サイトに公開 API があるか確認。API 呼び出しはブラウザ自動化より 10 倍信頼性が高い。API ドキュメントを探す。
- 第二候補: 既知エンドポイントへの単純な HTTP リクエストなら `curl` または `wget`。
- 第三候補: UI クリックが必要な場合は Playwright または Selenium。Playwright を優先（高速で不安定さが少ない）。
- パターンを見る: ダッシュボードから同じレポートを繰り返しダウンロードしているなら、ほぼ確実に API またはクエリパラメータ付き直 URL で取得可能。

**スプレッドシート・データ処理ワークフロー:**
- データのフィルタ・変換・集計には pandas を使った Python。
- Excel の単純な列操作なら、5 行の Python スクリプトで手作業全体を置き換えられる。
- コードを書かずに CSV を手早く扱うなら `csvkit`。
- 出力を Excel 形式のままにする必要があるなら openpyxl。

**メールワークフロー:**
- macOS: `osascript` で Mail.app を操作し、添付付きメール送信が可能。
- クロスプラットフォーム: 送信に Python `smtplib`、受信に `imaplib`。
- メールがテンプレート化されているなら、テンプレートファイルに変数置換して本文生成。

**ファイル管理ワークフロー:**
- move/copy/rename パターンにはシェルスクリプト。
- バッチ処理には `find` + `xargs`。
- 変更トリガー実行には `fswatch` または `watchman`。
- 日付や種類でフォルダ分けしているなら、3 行のシェルスクリプトで済む。

**Terminal/CLI ワークフロー:**
- 頻出コマンドには shell alias。
- 複数手順の連続実行には shell function。
- プロジェクト固有タスク群には Makefile。
- 同じコマンドを引数違いで繰り返したならループ化できる。

**macOS 固有ワークフロー:**
- ネイティブアプリ制御（Mail、Calendar、Finder、Preview など）には AppleScript/JXA。
- コード不要の単純な複数アプリ連携には Shortcuts.app。
- ファイルベースのフローには `automator`。
- 定期実行は `launchd` plist を推奨（macOS では cron より推奨）。

**アプリ横断ワークフロー（アプリ間データ移動）:**
- データ受け渡し地点を特定する。各受け渡し点は自動化の機会。
- 録画でクリップボード受け渡しが多いなら、アプリ同士が直接連携していないサイン。代わりに API、ファイル連携、直接統合を探す。
- App A からコピーして App B に貼り付けている場合、自動化では A のデータソースを直接読み、B の入力形式へ直接出力する。

### 提案を的確にするために

すべての提案で次の原則を適用してください。

1. **まずボトルネックを自動化する。** 録画のナレーションと所要時間から、本当に痛い手順がわかる。最悪の手順を 30 秒短縮する自動化は、全体を 2 時間かけて自動化するより価値が高い場合がある。

2. **ユーザーのスキルレベルに合わせる。** 録画でターミナルに慣れているならシェルスクリプトを提案。GUI 中心なら、簡単に起動できる手段（スクリプトをダブルクリック、Shortcut 実行、1 コマンド入力）を提案。

3. **実際の時間削減を見積もる。** 録画時間に実行頻度を掛ける。「この録画は 4 分。毎日実行なら年 17 時間。Tier 1 で毎回 30 秒になれば、年 16 時間戻せる」。

4. **まず 80% ケースを完璧に。** 初版はよくある経路を確実にカバー。エッジケースは Tier 3 で扱うか、手動介入として明示。

5. **人の確認ポイントを残す。** 録画で確認・承認している箇所は手動ステップとして維持。判断を勝手に自動化しない。

6. **ドライランを提案する。** すべてのスクリプトに「実行予定だけ表示する」モードを持たせる。`--dry-run` フラグ、プレビュー出力、破壊的操作前の確認プロンプトなど。

7. **認証と秘密情報を考慮する。** ログインや資格情報が関わる場合、ハードコード禁止。環境変数、キーチェーン（macOS の `security` コマンド）、または実行時入力を使う。

8. **失敗モードを考える。** サイト停止時、ファイル不存在時、形式変更時にどうなるか。良い提案はこれを明示し、対処する。

## Phase 5: 実装とテスト

ユーザーが tier を選んだら:

1. 完全な自動化コードをファイルに書き出す（妥当な場所を提案。プロジェクトディレクトリがあればそこ、なければ `~/Desktop/`）。
2. ユーザーが見ている状態でドライランまたはテストを進める。
3. テストが通れば、本番実行方法を示す。
4. 失敗したら診断して修正する。1 回で諦めない。

## クリーンアップ

分析完了後（結果に関わらず）、抽出したフレームと音声を削除します。

```bash
rm -rf "$WORK_DIR"
```

一時ファイルをクリーンアップして何も残らないことを、ユーザーに伝えてください。
