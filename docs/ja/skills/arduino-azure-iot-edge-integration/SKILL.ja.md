# Arduino Azure IoT エッジの統合

このスキルは、ユーザーが Arduino クラスのデバイスを Azure IoT に接続する必要がある場合、特にエッジが多いシナリオ (ゲートウェイ、断続的なネットワーク、オフライン バッファリング、ローカル作動) で使用します。

## いつ使用するか

このスキルは次のようなリクエストに使用します。

- 「ArduinoのセンサーをAzureに接続したい」
- 「MQTT テレメトリを IoT Hub に送信するにはどうすればよいですか?」
- 「フィールドデバイス用のエッジゲートウェイが必要です」
- 「クラウドからデバイスへのコマンドと OTA 構成の更新が必要です」

## 必須の文書レビュー

IoT Edge トポロジまたはランタイム動作を推奨する前に、以下を確認してください。

- https://learn.microsoft.com/azure/iot-edge/

ドキュメントを参照できない場合は、明示的な仮定に基づいて続行し、専用のセクションでそれらを強調表示します。

## 公式の Arduino リファレンスとベスト プラクティス (必須)

ファームウェア、配線、通信実装の詳細を提案する前に、まず Arduino の公式ソースを参照してください。

- https://www.arduino.cc/en/ガイド
- https://docs.arduino.cc/
- https://docs.arduino.cc/言語リファレンス/
- 参考資料/arduino-official-best-practices.md

代替実装を選択するときは、逸脱する明確な技術的理由がない限り、コミュニティのスニペットよりも公式の Arduino ガイダンスを優先してください。

## 目的

- Arduino デバイスからクラウドの洞察までの安全なエンドツーエンドの参照パスを生成します。
- 不安定なリンク (ストア アンド フォワード、再試行、べき等) を処理します。
- 実用的なデバイスとクラウド バックログを定義します。

## 統合パターン

### パターン A: Arduino を IoT Hub に直接接続する

接続が安定しており、クラウドの遅延が許容できる場合に使用します。

- プロトコル: MQTT over TLS。
- ID: デバイスごとの資格情報 (SAS または X.509)。
- テレメトリ ペイロード: タイムスタンプ、デバイス ID、メトリクス、およびオプションの品質フラグを含むコンパクトな JSON。

### パターン B: Arduino からローカル ゲートウェイ、その後 IoT Edge

リンクが制約されている場合、ローカル制御が必要な場合、またはバッチ処理によりコスト/信頼性が向上する場合に使用します。

- Arduino はローカル ゲートウェイ (シリアル、BLE、ローカル MQTT、RS-485、Modbus ブリッジ) と通信します。
- ゲートウェイは、IoT Edge ランタイムを通じてアップストリームに公開し、データを IoT Hub にルーティングします。
- ローカル モジュールは、クラウドの停止中であってもアクションをフィルタリング、集約、トリガーできます。

## 設計フロー

### 1) 端末契約

定義する：

- センサーのカタログとユニット。
- サンプリング周波数と予想されるスループット。
- メッセージ スキーマのバージョン管理戦略。
- 実行時の動作を制御するために必要な/報告されたデバイス ツイン プロパティ。

### 2) セキュリティベースライン

必要とする：

- デバイスごとに一意の ID。
- ソース コードやファームウェア アーティファクトにハードコーディングされたシークレットはありません。
- 資格情報のローテーション戦略。
- 可能な場合は、署名されたファームウェアと制御された更新プロセス。

### 3) 信頼性とオフライン動作

計画と文書化:

- ジッターを伴うバックオフ。
- サイズが制限されたローカル キュー/バッファ戦略。
- 重複の抑制またはダウンストリームの冪等処理。
- 最後に正常に実行された構成にフォールバックします。

### 4) クラウドおよびエッジルーティング

以下のルートを定義します。

- コールド ストレージへの生のテレメトリ。
- 厳選されたテレメトリーから最新の分析まで。
- オペレーションチャネルへのアラート。
- コマンドと設定をエッジ/デバイスに戻します。

### 5) 可観測性

最小限の操作テレメトリを指定します。

- デバイスのハートビートとファームウェアのバージョン。
- 接続状態の遷移。
- メッセージ送信成功/エラーカウンター。
- ゲートウェイ モジュールの健全性と再起動の理由。

また、`references/arduino-official-best-practices.md` をファームウェアとハ​​ードウェアの推奨事項の品質ベースラインとして使用します。

## 必要な出力

常に以下を提供してください:

1. 選択された接続パターンと根拠。
2. メッセージ コントラクト (フィールド、ユニット、サンプル ペイロード)。
3. ID/資格情報/更新に関するセキュリティ チェックリスト。
4. 信頼性計画 (再試行、バッファリング、重複排除)。
5. 実装のバックログ (ファームウェア、ゲートウェイ、クラウド)。

## 出力テンプレート

1. シナリオと仮定
2. 推奨アーキテクチャ
3. デバイスとゲートウェイの契約
4. セキュリティと信頼性の管理
5. 導入計画と検証テスト

## ガイドライン

- デバイス間で共有された認証情報を使用した運用展開を提案しないでください。
- 現場での導入では常時接続を想定しないでください。
- アクチュエータのシナリオでは、コマンドの認可と監査を省略しないでください。
