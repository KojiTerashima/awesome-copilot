# Product-Led Growth

セルフサーブでの獲得と拡張のモーションを構築する。だがその前に、そもそもPLGが自社プロダクトに適したモーションかを見極めること。

## いつ使うか

**トリガー:**
- 「PLGを作るべき？それともセールス主導？」
- 「どうやってセルフサーブ導入を進める？」
- 「フリーミアムから有料への転換がうまくいかない」
- 「開発者主導の導入戦略」
- 「どの成長チャネルに投資すべき？」
- 「PLGが機能するかどうか、どう判断する？」

**コンテキスト:**
- 開発者向けツールやプラットフォーム
- セルフサーブの可能性があるB2B SaaS
- デモなしでも価値が伝わるプロダクト
- ボトムアップ型の導入モーション
- 成長チャネルの優先順位付け

## コアフレームワーク

### 1. PLGリアリティチェック（コミット前に検証する）

**両方のモーションを並行運用して学んだこと:**

スタートアップで定番の議論。PLG派は「開発者はセルフサーブを求める」。セールス派は「エンタープライズには手厚い伴走が必要」。議論する代わりに、6か月間両方をテストした。同じプロダクトで2つのGTMモーションを走らせ、すべてを計測した。

**結果:**

PLGは高ボリューム・低ACV（約$5K）・売上化までが速い・解約率が高い。セールス主導は低ボリューム・高ACV（約$50K）・売上化までが遅い・解約率が低い。**件数は10分の1でも、売上額ではセールスが10倍勝った。**

**なぜか:** プロダクトの複雑性 + 購買者の上位性 = セールス主導が勝つ。既存インフラとの統合、チーム横断のチェンジマネジメント、複数ステークホルダーの合意が必要だった。開発者はセルフサーブを好んだ。だが、経済的な意思決定者ではなかった。

**PLGが機能する条件:**
- 最初の5分で価値が明確
- 実装が容易
- チーム合意なしでも個人ユーザーが価値を得られる
- 調達・法務のハードルがない
- Buyer = user

**セールス主導が機能する条件:**
- プロダクトに統合/セットアップが必要
- 複数ステークホルダーの足並み合わせが必要
- Buyer ≠ user
- 案件規模が人の関与を正当化できる
- 顧客が価値を理解するために教育を必要とする

**PLGを作る前に、まずモーションを検証すること。流行っているからという理由でPLGを前提にしない。** PLGは量を捌く効率に優れるが、複雑性が高い場合はセールス主導のほうが収益性が高いことがある。

### 2. 成長方程式（入力を出力に対応づける）

**パターン:**

成長は、活動とユーザー獲得の関係を仕組み化したときに複利で効く。「マーケを増やす」ではなく、具体的な入力を測定可能な出力に対応づける。

**成長方程式の作り方:**

各チャネルについて定義する: Activity (input) → Traffic (output) → Conversions。

- **Organic Search:** 高品質なブログ1本 → 月400ユーザー → 5% conversion = 新規20ユーザー
- **Paid Ads:** 100Kインプレッションで8% conversion、$1K投下 = 8Kクリック → X%でコンバージョン
- **Community Events:** イベント1回 → 60参加者 → 35% conversion = 21ユーザー
- **Referral:** 連携パートナー1社 → N人紹介ユーザー → Y%でコンバージョン

**重要な理由:**

方程式を検証できれば、スケールは数学になる。「来月あと200ユーザー必要」→「ブログをあと10本」または「広告費をあと$5K」。方程式がなければ、すべて勘になる。

**方程式の検証:**

1. 仮説から始める: 「Xを作ればYのconversionを生む」
2. 小さく試す: ブログ1本で実測conversionを計る
3. 検証する: 現実は仮説と一致するか？
4. 確信を持って拡大: 一致するなら入力を増やす
5. 合わなければ止める: 判断には4週間のデータで十分

**よくあるミス:**

検証せずにconversion率を見積もる。同じチャネルのユーザーは同質だと仮定する。方程式の検証前にスケールする。

### 3. チャネル経済性（負け筋を切り、勝ち筋に集中）

**パターン:**

すべてのチャネルには経済性がある。追跡しなければ、負け筋に過剰投資し、勝ち筋に過小投資する。

**チャネルごとに追う指標:**
1. **CAC:** 総支出 / 新規ユーザー数
2. **Conversion rate:** Signups → paying
3. **Retention:** ソース別30日・90日
4. **LTV:** チャネル別の顧客生涯売上
5. **Payback period:** CAC回収までの期間

**意思決定フレームワーク:**

- CAC < (LTV × margin) → 積極的にスケール
- CAC ≈ (LTV × margin) → スケールせず最適化
- CAC > (LTV × margin) → 4週間以内に停止

**月次チャネルレビュー:** どのチャネルが利益を生むか？どれが赤字か？四半期ごとに再配分: 勝ち筋に予算3倍、負け筋は停止。

**重要な洞察: チャネル品質はばらつく**

CACが安いことは、良いCACを意味しない。自然検索はCAC $0で30日Retention 85%かもしれない。有料検索はCAC $12で30日Retention 45%かもしれない。RetentionとLTVを加味すると、「無料」チャネルの価値が10倍になることもある。

**体系的なテスト:**

毎月新チャネルを2つ試す。各チャネルに4週間のデータを与える。経済性が合わなければ迷わず停止。結果に関係なく学びを文書化する——うまくいかなかった知見も同じくらい価値がある。

**よくあるミス:**

Retentionを見ずにCACだけ追う。離脱する安価チャネルは、定着する高価チャネルよりコスト高になる。

### 4. Time to First Value（唯一のアクティベーション指標）

**パターン:**

ユーザーは最初の5〜10分で価値を判断する。aha momentに素早く到達できなければ離脱する。

**アクティベーション監査:**

1. 新規ユーザーとして自社プロダクトに登録する
2. 初回価値到達までの時間を測る
3. aha momentまでのステップ数を数える
4. どこで詰まるか確認する

**TTFV > 10分なら、アクティベーションに問題がある。**

**Before:** Sign up → confirm email → fill profile → configure settings → read docs → first action

**After:** Sign up → pre-loaded sample data → first action (immediate aha moment)

**具体的な改善策:**

1. **サンプルデータを事前投入する。** ユーザーは設定ではなく価値を見たい。すぐ動く例を与える。
2. **本質でない設定を後回しにする。** メール確認、プロフィール、設定はaha moment後でよい。
3. **Progressive disclosure。** 最初から全機能を見せない。中核ワークフロー1つから始め、複雑さは段階的に開示する。
4. **説明より体験。** インタラクティブなチュートリアル > 動画 > テキストdocs。クリックして流れを体験させる。

**よくあるミス:**

ユーザーがドキュメントを読む前提にする。実際は5分ほど触って、何も進まなければ離脱する。

### 5. $5K → $50Kの変曲点（PLGが壊れるとき）

**パターン:**

PLGは$1K〜$10K ARRで機能する。$20K〜$50Kでは組織的摩擦（調達、法務、セキュリティ、複数ステークホルダー承認）が効き始め、モーションが崩れる。

**ハイブリッドアプローチ:**

**PLG ($0-$10K):** セルフサーブ登録 → free tier → paid tier → クレジットカード決済 → 自動オンボーディング

**Sales-Assisted ($10K-$50K):** セルフサーブで発見 → 利用シグナルを見てセールスが関与 → 人手で契約交渉 → 専任オンボーディング

**Enterprise ($50K+):** アウトバウンドまたはインバウンドリード → デモ → POC → 提案 → 法務/セキュリティ審査 → エグゼクティブスポンサー

**PQLシグナル（セールスを起動するタイミング）:**

- **Usage depth:** 日次アクティブ、コア機能利用、上限接近
- **Expansion signals:** 同一企業から複数ユーザー、チーム機能、連携
- **Buying signals:** SSO/compliance/SLAの要望、チーム料金の問い合わせ

**ハンドオフ:**

Bad: 「登録を確認しました。」（冷たく汎用的で、信頼を損なう）
Good: 「御社チームは[specific feature]を12 reposで利用しています。[specific value]を支援できます。15分お時間いただけますか？」（温かく具体的で価値提示がある）

**よくあるミス:**

<$5K案件にセールスが早期介入する。PLGモーションを壊し、ユーザーを警戒させる。支援が必要になるまではセルフサーブに任せる。

### 6. 成長予測（不確実性を前提に計画する）

**パターン:**

予測は必ず外れる。それでも計画は価値がある。思考を強制し、説明責任を生むからだ。

**3つのシナリオをモデル化する:**

**Baseline（現行トレンド継続）:**
- Organic search: 35%成長 → 新規40Kユーザー
- Paid: 横ばい → 新規2Kユーザー
- Community: 10%成長 → 新規400ユーザー
- 合計: 42.4K

**Upside（成長施策がすべて実行できた場合）:**
- Organic: 50%成長（コンテンツ3倍）→ 48K
- Paid: 投下2倍、効率同じ → 4K
- 新施策（パートナーシップ）: 立ち上がり → 3K
- 合計: 55K

**Downside（主要チャネルが失敗した場合）:**
- Organic: 0%成長 → 26K
- Paid: CPAが2倍 → 1K
- 合計: 27K

**用途:**
- ベースライン目標の設定（baseline scenario）
- ストレッチ目標（upside scenario）
- エスカレーショントリガー（downsideに落ちるなら何かを変える必要がある）
- リソース配分（upside達成に必要な入力は何か？）

**月次更新:** 予測と実績を比較し、モデルを調整する。予測して放置しない。

**よくあるミス:**

すべてうまくいく前提の楽観予測。月次更新しない。予測を目標値として扱う（予測は単一値ではなくレンジ）。

### 7. プレイブック文書化の習慣

**パターン:**

知識は人とともに失われる。目標は単発の勝利ではなく、機能するものの仕組み化。

**成功したキャンペーンや実験のたびに、1ページのプレイブックを書く:**

```
PLAYBOOK: [Channel/Tactic Name]

Goal: [What outcome]
Steps: [Numbered, specific enough for someone unfamiliar]
Expected Output: [Specific metrics]
Metrics to Track: [How to measure]
Risks & Mitigations: [What could go wrong]
Owner: [Name]
Last Updated: [Date]
```

**テスト:** 関与していない人でもこのプレイブックを実行できるか？できなければ抽象的すぎる。

**四半期ごとに見直す。** もう機能しないプレイブックは削除し、進化したものは更新する。これが成長オペレーティングシステムになる。

**よくあるミス:**

学びを文書化せずに実験を回す。仕組み理解前にスケールする。成長知識が一人の頭の中に閉じる。

## 意思決定ツリー

### PLGを作るべきか、セールス主導か？

```
Can users get value in <10 min without docs?
├─ No → Sales-led required
└─ Yes → Can they self-serve implementation?
    ├─ No → Sales-led required
    └─ Yes → Is buyer = user?
        ├─ No → Hybrid (PLG + sales-assist)
        └─ Yes → Pure PLG viable
```

### このチャネルは維持・拡大・停止のどれか？

```
CAC < (LTV × margin)?
├─ No → Kill within 4 weeks
└─ Yes → 90-day retention > 60%?
    ├─ No → Optimize (improve activation/onboarding)
    └─ Yes → Scale aggressively (3x budget)
```

## よくあるミス

**1. PLGは常に機能すると決めつける**
プロダクトの複雑性 + 購買者の上位性 = セールス主導が勝つ。コミット前に検証する。

**2. チャネル経済性がない**
すべてのチャネルにCAC、Retention、LTVがある。追わなければ手探りになる。

**3. free tierが寛大すぎる、または厳しすぎる**
寛大すぎると転換しない。厳しすぎると活性化しない。10〜20回のaha momentを許容する。

**4. 成長方程式がない**
「マーケを増やす」は戦略ではない。チャネルごとに入力 → 出力 → コンバージョンを対応づける。

**5. 検証前にスケールする**
どのチャネルもスケール前に4週間のデータを取る。経済性が合わなければ明確に止める。

**6. 成長知識が一人の頭の中にある**
成功した実験はすべてプレイブックとして文書化する。

## クイックリファレンス

**PLG readiness:** <10分で価値到達 + セルフサーブ実装可能 + buyer = user

**Growth equation:** Activity (input) → Traffic (output) → Conversions をチャネルごとに定義

**Channel economics:** CAC、conversion、30/90-day retention、LTV、payback をチャネルごとに月次レビュー

**Kill criteria:** CAC > (LTV × margin) → 4週間改善、それでもだめなら停止

**PQL signals:** Usage depth + expansion（複数ユーザー）+ buying（SSO/compliance要望）

**Sales handoff:** <$10K: PLG → $10K-$50K: Sales-assist → >$50K: Full sales

**Forecast:** Baseline + Upside + Downside を月次更新
