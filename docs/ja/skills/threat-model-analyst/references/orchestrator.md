# Orchestrator — 脅威モデル分析ワークフロー

このファイルには、脅威モデル分析を実行するための完全なオーケストレーション ロジックが含まれています。
これは、`/threat-model-analyst` スキルの主要なワークフロー ドキュメントです。

## ⚡ コンテキスト バジェット — ファイルを選択的に読み取る

**セッション開始時に 10 個のスキル ファイルすべてを読まないでください。** 各フェーズで必要なものだけを読んでください。これにより、実際のコードベース分析用のコンテキスト ウィンドウが保存されます。

**フェーズ 1 (コンテキスト収集):** このファイルを読み取ります (`orchestrator.md`) + `analysis-principles.md` + `tmt-element-taxonomy.md`
**フェーズ 2 (レポートの作成):** 各ファイルを書き込む前に、`skeletons/` から関連するスケルトンを読み取ります。ルールについては `output-formats.md` + `diagram-conventions.md` を参照してください。ただし、スケルトンを構造テンプレートとして使用します。
- `0.1-architecture.md` の前: `skeletons/skeleton-architecture.md` を読み取ります
- `1.1-threatmodel.mmd` の前: `skeletons/skeleton-dfd.md` を読み取ります
- `1-threatmodel.md` の前: `skeletons/skeleton-threatmodel.md` を読んでください
- `2-stride-analysis.md` の前: `skeletons/skeleton-stride-analysis.md` を読んでください
- `3-findings.md` の前: `skeletons/skeleton-findings.md` を読んでください
- `0-assessment.md` の前: `skeletons/skeleton-assessment.md` を読んでください
- `threat-inventory.json` の前: `skeletons/skeleton-inventory.md` を読んでください
- `incremental-comparison.html` の前: `skeletons/skeleton-incremental-html.md` を読んでください
**フェーズ 3 (検証):** サブエージェントに委任し、サブエージェントのプロンプトに `verification-checklist.md` を含めます。サブエージェントは、新しいコンテキスト ウィンドウを使用して完全なチェックリストを読み取ります。親エージェントはそれを読み取る必要はありません。

**重要な原則:** サブエージェントは新しいコンテキスト ウィンドウを取得します。すべてを親コンテキストに保持するのではなく、検証と JSON 生成をサブエージェントに委任します。

## ✅ 必須ルール — 始める前にお読みください

これらは、すべての脅威モデル レポートに必要な動作です。各ルールに正確に従います。1. 重大度レベルごとではなく、**悪用可能性の層** (層 1/2/3) ごとに調査結果を整理します。
2. 各コンポーネントの STRIDE テーブルを Tier 1、Tier 2、Tier 3 のサブセクションに分割します。
3. すべての検出結果に `Exploitability Tier` と `Remediation Effort` を含めます - どちらも必須です
4. STRIDE 概要テーブルには T1、T2、T3 列が含まれなければなりません。
4b. **STRIDE + 悪用ケースのカテゴリは、正確には次のとおりです。** **なりすまし、**不正行為、**R**証言、**情報開示、**サービス停止**、**特権の昇格、**悪用 (ビジネス ロジックの悪用、ワークフロー操作、機能の悪用 - 正規の機能の悪用をカバーする標準 STRIDE の拡張)。 A は常に「悪用」であり、「AI の安全性」、「認可」、またはその他の解釈は決してありません。認可の問題は E (特権の昇格) に属します。
5. `.md` ファイル: 1 行目の `# Heading` で始まります。`create_file` ツールは生のコンテンツを書き込みます - コード フェンスはありません
6. `.mmd` ファイル: 1 行目の `%%{init:` で始まります。生の Mermaid ソース、フェンスなし
7. セクションのタイトルは正確に `## Action Summary` にする必要があります。 `### Quick Wins` サブセクションに Tier 1 の低労力の結果テーブルを含めます
8. K8s サイドカー: ホスト コンテナに `<br/>+ Sidecar` の注釈を付ける — 個別のサイドカー ノードを作成しないでください (`diagram-conventions.md` ルール 1 を参照)
9. ポッド内の localhost フローは暗黙的です。図に描かないでください。
10. アクションの概要は推奨事項です。個別の `### Key Recommendations` セクションはありません
11. エグゼクティブ サマリーに `> **Note on threat counts:**` ブロック引用を含める
12. すべての結果には CVSS 4.0 (スコアと完全なベクトル文字列)、CWE (ハイパーリンク付き)、および OWASP (`:2025` サフィックス) が必要です。
13. OWASP サフィックスは常に `:2025` (例: `A01:2025 – Broken Access Control`)
14. `3-findings.md` の最後に脅威カバレッジ検証テーブルを含めて、すべての脅威をマッピング→検出します
15. `0.1-architecture.md` のすべてのコンポーネントは `2-stride-analysis.md` に出現する必要があります
16. `0.1-architecture.md` の最初の 3 つのシナリオには Mermaid シーケンス図が必要です
17. `0-assessment.md` には `### Needs Verification` テーブルと `### Finding Overrides` テーブルを含める必要があります
18. `### Quick Wins` サブセクションは「アクションの概要」の下に必須です (ない場合は見出しに注記を含めます)
19. `0-assessment.md` の 7 つのセクションはすべて必須です: レポート ファイル、エグゼクティブ サマリー、アクション サマリー、分析コンテキストと前提条件、参照した参考文献、レポート メタデータ、分類リファレンス
20. **展開分類は BINDING です。** `0.1-architecture.md` で、`Deployment Classification` を設定し、コンポーネント エクスポージャ テーブルに記入します。分類が `LOCALHOST_DESKTOP` または `LOCALHOST_SERVICE` の場合: 非リスナー コンポーネントの T1 検出結果はゼロ、`Prerequisites = None`、`AV:N` はゼロ。 `analysis-principles.md` デプロイメント コンテキスト テーブルを参照してください。
21. 検索 ID は上から下に連続する必要があります: FIND-01、FIND-02、FIND-03... 並べ替え後に番号を付け直します。
22. CWE にはハイパーリンクを含める必要があります: `[CWE-306](https://cwe.mitre.org/data/definitions/306.html): Missing Authentication`
23. STRIDE の後、`analysis-principles.md` でテクノロジー固有のセキュリティ チェックリストを実行します。リポジトリ内のすべてのテクノロジーには、少なくとも 1 つの発見または文書化された軽減策が必要です
24. CVSS `AV:L` または `PR:H` → Tier 1 になることはできません。T2/T3 にダウングレードします。 `analysis-principles.md` の CVSS から層への整合性チェックを参照してください。
25. `Low`/`Medium`/`High` エフォート ラベルのみを使用します。時間の見積もり、スプリント フェーズ、またはスケジュールは決して生成しないでください。 `output-formats.md` の禁止コンテンツを参照してください。
26. 参照する参考文献: `output-formats.md` — `### Security Standards` (完全な URL を含む 3 列のテーブル) および `### Component Documentation` (URL を含む 3 列のテーブル) の正確な 2 つのサブセクション形式を使用します。
27. レポート メタデータ: `output-formats.md` テンプレートのすべてのフィールド — モデル、分析開始、分析完了、期間を含めます。 `0-assessment.md` を書き込む前に、ステップ 1 で `Get-Date -Format "yyyy-MM-dd HH:mm:ss" -AsUTC` を実行します。
28. `2-stride-analysis.md` の `## Summary` テーブルは、`## Exploitability Tiers` の直後、個々のコンポーネント セクションの前に先頭に表示されなければなりません。
29. 関連する脅威: すべての脅威 ID は `2-stride-analysis.md#component-anchor` へのハイパーリンクでなければなりません。形式: `[T02.S](2-stride-analysis.md#component-name)`
30. 図の色: `diagram-conventions.md` から classDef 行をそのままコピーします。許可されるフィルのみ: `#6baed6` (プロセス)、`#fdae61` (外部)、`#74c476` (データストア)。許可されるストロークのみ: `#2171b5`、`#d94701`、`#238b45`、`#e31a1c`。 `%%{init: {'theme': 'base', 'themeVariables': { 'background': '#ffffff', 'primaryColor': '#ffffff', 'lineColor': '#666666' }}}%%` のみを使用し、他のテーマ変数キーは使用しないでください
31. DFD の概要: `1.1-threatmodel.mmd` を作成した後、ステップ 4 で POST-DFD ゲートを実行します。ゲートと `skeleton-summary-dfd.md` は、`1.2-threatmodel-summary.mmd` が生成されるかどうかを制御します。
32. `0-assessment.md` のレポート ファイル テーブル: `0-assessment.md` (このドキュメント) を最初の行としてリストし、その後に 0.1-architecture.md、1-threatmodel.md などが続きます。`output-formats.md` の正確なテンプレートを使用します。
33. `threat-inventory.json` は、分析を実行するたびに生成されなければなりません (ステップ 8b)。このファイルにより、将来の比較が可能になります。スキーマについては `output-formats.md` を参照してください。
34. **リポジトリ内の既存の `threat-model-*` または `threat-model-compare-*` フォルダーは決して削除、変更、削除しないでください**。独自のタイムスタンプ付き出力フォルダーにのみ書き込みます。作成した一時的な git ワークツリーをクリーンアップすることは許可されています。他のレポート フォルダーを削除することは禁止されています。### ルールの優先順位 (ガイダンスが矛盾する場合)

次の順序でルールを適用します。
1. `skeletons/skeleton-*.md` のリテラル スケルトン — 正確なセクション/テーブル ヘッダーと属性行
2. `orchestrator.md` の必須ルール (このリスト)
3. `output-formats.md` の例 (例は説明のためのものであり、文字通りの骨格と異なる場合は権威を示すものではありません)

競合が検出された場合は、最も優先順位の高い項目に従います。

**生成後:** 検証サブエージェントは、`verification-checklist.md` フェーズ 0 にリストされているすべての既知の逸脱について出力をスキャンします。最終処理する前に、失敗があれば修正してください。

## ワークフロー

**除外事項:** 次のディレクトリをスキップしてください:
- `threat-model-*` (以前のレポート)
- `node_modules`、`.git`、`dist`、`build`、`vendor`、`__pycache__`

**事前作業:** 出力ファイルを書き込む前に、`verification-checklist.md` フェーズ 1 (ファイルごとの構造チェック) とフェーズ 2 (ダイアグラム レンダリング チェック) をスキャンします。これにより品質ゲートが内部化されるため、最初のパスで出力が正しくなり、コストのかかるやり直しが防止されます。完全な検証はまだ実行しないでください。それはステップ 10 で起こります。

### ⛔ サブエージェントのガバナンス (必須 — 重複作業の防止)

サブエージェントは **独立した実行コンテキスト** です。サブエージェントは親の状態、命令、または他のサブエージェントの記憶を持ちません。厳密なガバナンスがないと、サブエージェントが独立して全体の分析を実行し、重複したレポート フォルダーが作成され、重複ごとに最大 15 分の計算と最大 100,000 のトークンが無駄になります。

**ルール 1 — 親はすべてのファイル作成を所有します。** 親エージェントは、レポート ファイル (0.1-architecture.md、stride-analysis.md、founding.md など) に対して `create_file` を呼び出す唯一のエージェントです。サブエージェントはレポート ファイルを決して書きません。

**ルール 2 — サブエージェントは読み取り専用のヘルパーです。** サブエージェントは次のことを行うことができます。
- 特定のパターンのソース コードを検索します (例: 「すべての認証関連コードを検索」)
- ファイルを読み取って分析し、構造化データを親に返します。
- 検証チェックを実行し、PASS/FAIL 結果を返します。
- ターミナル コマンド (git diff、grep) を実行し、出力を返します。**ルール 3 — サブエージェントのプロンプトは狭く、具体的である必要があります。** サブエージェントに「脅威モデル分析を実行する」または「レポートを生成する」ように指示しないでください。代わりに:
- ✅ 「これら 5 つの Go ファイルを読み取り、資格情報を処理するすべての関数をリストします。関数名、ファイル、行番号のテーブルを返します。」
- ✅ 「{folder} 内のファイルに対して検証チェックリストを実行します。各チェックに対して PASS/FAIL を返します。」
- ✅ 「{path} からthreat-inventory.jsonを読み取り、すべての配列の長さがメトリクスと一致することを確認します。不一致を返します。」
- ❌ 「このコードベースを分析し、脅威モデル ファイルを作成します。」
- ❌ 「このコンポーネントの 0.1-architecture.md と stride-analysis.md を生成します。」

**ルール 4 — 出力フォルダーのパス。** 親はステップ 1 でタイムスタンプ付きの出力フォルダーを作成し、その正確なパスをすべての `create_file` 呼び出しに使用します。サブエージェントが以前に書き込まれたレポート ファイルを読み取る必要がある場合は、サブエージェント プロンプトでフォルダー パスを渡します。

**ルール 5 — 唯一の例外**は `threat-inventory.json` の生成 (ステップ 8b) です。データが大きすぎる場合、親は JSON 書き込みをサブエージェントに委任できます。その場合、サブエージェントのプロンプトには、(a) 正確な出力ファイル パス、(b) シリアル化するデータ、および (c) 「この 1 つのファイルのみを書き込みます。他のファイルやフォルダーは作成しないでください。」という明示的な指示が含まれなければなりません。

### ステップ

1. **開始時刻を記録し、コンテキストを収集する**
   - `Get-Date -Format "yyyy-MM-dd HH:mm:ss" -AsUTC` を実行し、`START_TIME` として保存します
   - git 情報の取得: `git remote get-url origin`、`git branch --show-current`、`git rev-parse --short HEAD`、`git log -1 --format="%ai" HEAD` (コミット日 - 今日の日付ではありません)、`hostname`
   - システムのマッピング: コンポーネント、信頼境界、データ フローを特定します。
   - **参照:** `analysis-principles.md` セキュリティ インフラストラクチャ インベントリ

   **⛔ 導入分類 (必須 — コードの脅威を分析する前にこれを実行してください):**
   コードの証拠からシステムのデプロイメント クラスを決定します (値については `skeleton-architecture.md` を参照してください)。
   `0.1-architecture.md`→「展開モデル」セクションに記録します。次に、**コンポーネント公開テーブル** に入力します。コンポーネントごとに 1 行で、リッスン アドレス、認証バリア、外部到達可能性、および最小前提条件を示します。
   このテーブルは、前提条件フロアに関する**唯一の信頼できる情報源**です。いかなる脅威や発見も、そのコンポーネントに対して暴露表で許可されているものよりも低い前提条件を持つことはできません。**⛔ 決定的な名前付け — ファイルを書き込む前に適用してください:**
   
   コンポーネントを識別するときは、それぞれに正規の PascalCase `id` を割り当てます。名前付けは決定的でなければなりません。同じコードベースで 2 つの独立した実行を行うと、同じコンポーネント ID が生成されなければなりません。

   **⛔ 絶対的なルール: すべてのコンポーネント ID は実際のコード アーティファクトに固定されている必要があります。**
   特定するすべてのコンポーネントについて、そのコンポーネントの「アンカー」であるコードベース内の特定のクラス、ファイル、またはマニフェストを指定できなければなりません。そのようなアーティファクトが存在しない場合、コンポーネントは存在しません。

   **命名手順 (IN ORDER に従い、最初の一致で停止):**
   1. **プライマリ クラス名** — ソース コードからの正確なクラス名を使用します。省略したり、拡大したり、言い換えたりしないでください。
      - `TaskProcessor.cs` → `TaskProcessor` (`TaskServer`、`TaskService` ではありません)
      - `SessionStore.cs` → `SessionStore` (`FileSessionStore`、`SessionService` ではありません)
      - `TerminalUserInterface.cs` → `TerminalUserInterface` (`TerminalUI` ではありません)
      - `PowerShellCommandExecutor.cs` → `PowerShellCommandExecutor` (`PowerShellExecutor` ではありません)
      - `ResponsesAPIService.cs` → `ResponsesAPIService` (`LLMService` ではありません。これは異なるクラスです)
      - `MCPHost.cs` → `MCPHost` (`OrchestrationHost` ではありません)
   2. **プライマリ スクリプト名** → `Import-Images.ps1` → `ImportImages`
   3. **プライマリ設定/マニフェスト名** → `Dockerfile` → `DockerContainer`、`values.yaml` → `HelmChart`
   4. **ディレクトリ名** (コンポーネントが複数のファイルにまたがる場合) → `src/ParquetParsing/` → `ParquetParser`
   5. **テクノロジー名** (外部サービス/データストア用) → 「Azure OpenAI」 → `AzureOpenAI`、「Redis」 → `Redis`
   6. **外部アクターの役割** → `Operator`、`EndUser` (これらを削除しないでください)**⛔ Helm/Kubernetes デプロイメントの名前付け (安定性の比較に重要):**
   コンポーネントが Helm チャートまたは Kubernetes マニフェスト経由でデプロイされる場合は、Helm テンプレートのファイル名やディレクトリ構造ではなく、**Kubernetes ワークロード名** (Deployment/StatefulSet メタデータ.名から) をコンポーネント ID として使用します。
   - デプロイ YAML で `metadata.name` を確認 → それをコンポーネント ID として使用します (PascalCase 正規化)
   - 例: `templates/knowledge/devportal-deployment.yml` の `metadata.name: devportal` → コンポーネント ID は `DevPortal`
   - 例: `templates/knowledge/phi-deployment.yml` の `metadata.name: phi-model` → コンポーネント ID は `PhiModel`
   - **理由:** Helm テンプレートは頻繁に再編成されます (例: `templates/` から `templates/knowledge/` に移動) が、Kubernetes ワークロード名は変わりません。ワークロード名を使用すると、ディレクトリが再編成されてもコンポーネント ID が存続します。
   - `source_files` には、デプロイメント YAML パスとアプリケーションのソース コード パスを含める必要があります (例: `helmchart/myapp/templates/knowledge/devportal-deployment.yml` と `developer-portal/src/` の両方)
   - `source_directories` には Helm テンプレート ディレクトリとソース コード ディレクトリの両方を含める必要があります

   **外部サービス アンカー (リポジトリ ソース コードのないコンポーネントの場合):**
   外部サービス (クラウド API、マネージド データベース、SaaS エンドポイント) には、リポジトリ内にソース ファイルがありません。コードベースの**統合ポイント**にそれらを固定します。
   - `source_files` → 接続を定義するクライアント クラスまたは構成ファイル (例: Azure OpenAI 接続構成の場合は `src/MCP/appsettings.json`、Redis エンドポイント構成の場合は `helmchart/values.yaml`)
   - `source_directories` → 統合コードを含むディレクトリ (例: LLM クライアントの場合は `src/MCP/Core/Services/LLM/`)
   - `class_names` → ベンダーの SDK クラス (例: `OpenAIClient`) ではなく、サービスと通信するリポジトリ内の CLIENT クラス (例: `ResponsesAPIService`)。専用のクライアント クラスが存在しない場合は、空のままにしておきます。
   - `namespace` → 空のままにしておきます `""` (外部サービスにはリポジトリ名前空間がありません)
   - `config_keys` → サービス接続の環境変数/設定キー (例: `["AZURE_OPENAI_ENDPOINT", "RESPONSES_API_DEPLOYMENT"]`)。これらは、外部サービスにとって最も安定したアンカーです。
   - `api_routes` → 空のままにしておきます (外部サービスは、あなたのルートではなく独自のルートを公開します)
   - `dependencies` → 使用される SDK パッケージ (例: NuGet の場合は `["Azure.AI.OpenAI"]`、pip の場合は `["pymilvus"]`)
   
   **これが重要な理由:** 外部サービスは、LLM の実行間で表示名を頻繁に変更します (例: 「Azure OpenAI」、「GPT-4 エンドポイント」、「LLM バックエンド」)。 `config_keys` フィールドと `dependencies` フィールドにより、実行間で照合可能になります。**⛔ 禁止されている命名パターン — これらは決して使用しないでください。**
   - 実際のクラスに対応しない抽象名は絶対に作成しないでください: `ConfigurationStore`、`LocalFileSystem`、`DataLayer`、`IngestionPipeline`、`BackendServer`
   - クラス名は決して省略しないでください: `TerminalUserInterface` の場合は `TerminalUI`、`PowerShellCommandExecutor` の場合は `PSExecutor`
   - 同義語を決して置き換えないでください: `TaskProcessor` を `TaskServer`、`ResponsesAPIService` を `LLMService`
   - 2 つの別個のクラスを 1 つのコンポーネントに決してマージしないでください。`ResponsesAPIService` と `LLMService` は 2 つの異なるクラス → 2 つの異なるコンポーネントです。
   - コード内に存在しないコンポーネントは決して作成しないでください。Windows レジストリ アクセス コードがない場合は、`WindowsRegistry` コンポーネントを作成しないでください。
   - 実行間では決して名前を変更しないでください。実行 1 で `TaskProcessor` と名付けた場合、実行 2 では `TaskProcessor` でなければなりません。

   **⛔ コンポーネント アンカーの検証 (必須 - ステップ 2 の前に実行してください):**
   すべてのコンポーネントを特定したら、メンタル チェックリストを作成します。```
   For EACH component:
     Q: What is the EXACT filename or class that anchors this component?
     A: [must cite a real file path, e.g., "src/Core/TaskProcessor.cs"]
     If you cannot cite a real file → DELETE the component from your list
   ```この検証では、`WindowsRegistry` (レジストリ コードが存在しない)、`ConfigurationStore` (そのようなクラスは存在しない)、`LocalFileSystem` (クラスではなく抽象的な概念) などの発明されたコンポーネントを検出します。

   **⛔ コンポーネント選択の安定性 (複数の関連クラスが存在する場合):**
   多くのシステムには、関連するクラスのクラスターがあります (`CredentialManager`、`AzureCredentialProvider`、`AzureAuthenticationHandler` など)。決定的な選択を保証するには:
   - **セキュリティ関連の動作を所有するクラスを選択します** - 信頼の決定を行う、資格情報を保持する、またはデータを処理するクラスです。
   - **ヘルパー/ユーティリティよりも依存関係注入に登録されたクラスを優先します**
   - **内部実装クラスよりも上位レベルのオーケストレーターを優先**
   - **クラスを選択すると、その代替クラスはエイリアスになります** - 個別のコンポーネントとしてではなく、`aliases` 配列に追加します
   - **例**: `CredentialManager` が認証情報の検索を調整し、内部で `AzureCredentialProvider` を使用する場合、`CredentialManager` がコンポーネントで、`AzureCredentialProvider` がエイリアスになります。
   - **例**: `SessionStore` と `SessionFiles` の両方を含めないでください — `SessionStore` はクラス、`SessionFiles` は抽象概念です
   - **カウント ルール**: 同じコードを 2 回実行すると、同じ数のコンポーネントが生成されなければなりません (エッジ ケースの場合は ±1)。コンポーネントが 3 つ以上異なる場合は、選択ルールが守られていないことを示します。

   **⛔ 安定性アンカー (比較照合用):**
   `threat-inventory.json` に各コンポーネントを記録する場合、`fingerprint` フィールド `source_directories`、`class_names`、および `namespace` は **安定性アンカー** として機能します。これは、次の場合でも存続する不変の識別子です。
   - クラスの名前が変更されます (ディレクトリは同じままです)
   - ファイルは別のディレクトリに移動されます (クラス名は変わりません)
   - コンポーネント ID は分析実行ごとに変わります (名前空間は同じままです)
   比較照合アルゴリズムは、コンポーネント `id` フィールドよりもこれらのアンカーに依存します。したがって:
   - `source_directories` はすべてのプロセス タイプ コンポーネントに入力されなければなりません (`[]` を空にしないでください)
   - `class_names` には少なくともプライマリ クラス名を含める必要があります
   - `namespace` は、作成されたグループではなく、実際のコードの名前空間 (例: `MyApp.Core.Servers.Health`) でなければなりません。
   - これらのフィールドにより、2 つの LLM が異なる表示名を選択した場合でも、独立した解析実行全体でコンポーネントを識別できるようになります。**⛔ コンポーネントの適格性 — 脅威モデル コンポーネントとして適格なもの:**
   クラス/サービスは、次の基準をすべて満たす場合にのみ脅威モデル コンポーネントになります。
   1. **信頼境界を越えるか、セキュリティ上重要なデータを処理します** (認証情報、ユーザー入力、ネットワーク I/O、ファイル I/O、プロセス実行)
   2. **これはトップレベルのサービス**であり、内部ヘルパー (DI に登録されている、メイン エントリ ポイント、または独自の責任を持つエージェント) ではありません。
   3. **展開図に表示されます** - それを指して、「これはここで実行され、あれと通信します」と言うことができます。
   
   **次のコンポーネント タイプを必ず含めてください (コード内に存在する場合):**
   - すべてのエージェント クラス (HealthAgent、InfrastructorAgent、InvestigatorAgent、SupportabilityAgent など)
   - すべての MCP サーバー クラス (HealthServer、InfrastructorServer など)
   - メインホスト/オーケストレーター (MCPHost など)
   - すべての外部サービス接続 (AzureOpenAI、AzureAD など)
   - すべての資格情報/認証マネージャー
   - ユーザー インターフェイスのエントリ ポイント
   - すべてのツール実行サービス (PowerShellCommandExecutor など)
   - すべてのセッション/状態永続サービス
   - すべての LLM サービス クラス (ResponsesAPIService、LLMService - 別々のクラスの場合は、別々のコンポーネントになります)
   - 外部アクター (オペレーター、エンドユーザー)
   
   **これらを個別のコンポーネントとして決して含めないでください:**
   - ロガー (LocalFileLogger、TelemetryLogger) — これらは横断的な懸念事項であり、脅威モデルのコンポーネントではありません。
   - 静的ヘルパークラス
   - モデル/DTO クラス
   - 構成ビルダー (シークレットを処理しない場合)
   - 実行時に存在しないコードとしてのインフラストラクチャ クラス (AzureStackHCI クラスター リファレンス、デプロイ スクリプト)
   
   **目標:** 同じコードを実行するたびに、約 12 ～ 20 個のコンポーネントの同じセットを識別する必要があります。ロガーを含めたり、エージェントを除外したりしている場合、それは間違っています。**境界の命名規則:**
   - 境界 ID は PascalCase でなければなりません (`Layer`、`Zone`、`Group`、`Tier` 接尾辞は使用しないでください)
   - コード アーキテクチャ レイヤーからではなく、デプロイメント トポロジから派生します
   - **展開トポロジによって境界が決まります:**
     - 単一プロセス アプリ → **正確に 2 つの境界**: `Application` (プロセス) + `External` (外部サービス)。 1 つの境界は決して使用しないでください。 3 つ以上の境界は決して使用しないでください。これは単一プロセス アプリでは必須です。
     - マルチコンテナアプリ → コンテナ/ポッドごとの境界
     - K8s デプロイ → `K8sCluster` + 名前空間ごとの境界 (該当する場合)
     - クライアントサーバー → `Client` + `Server`
   - **K8s マルチサービス展開 (マイクロサービス アーキテクチャにとって重要):**
     K8s 名前空間に、異なるセキュリティ特性を持つ複数の Deployments/StatefulSet が含まれている場合は、ワークロード タイプに基づいてサブ境界を作成します。
     - `BackendServices` — ユーザーリクエストを処理する API サービス (FastAPI、Express など)
     - `DataStorage` — データベースと永続ストレージ (Redis、Milvus、PostgreSQL、NFS) — これらには、異なるアクセス制御、永続性、およびバックアップ ポリシーがあります
     - `MLModels` — GPU ノード上で実行される ML モデル サーバー — これらには、異なるコンピューティング リソース、攻撃対象領域 (敵対的な入力)、およびスケーリング特性があります
     - `Agentic` — エージェント ランタイム/マネージャー サービス (存在する場合)
     - 外側の `K8sCluster` にはこれらのサブ境界が含まれます
     - **これは「コード層」ではありません** - 各サブ境界は、独自のセキュリティ コンテキスト、リソース制限、およびネットワーク ポリシーを持つ異なる Kubernetes Deployment/StatefulSet を表します。
     - **テスト**: 2 つのコンポーネントが、異なるサービス アカウント、異なるネットワーク公開、または異なるリソース要件を持つ異なる Kubernetes デプロイメントにある場合 → それらは異なるサブ境界にあるべきです。
   - **FORBIDDEN 境界スキーム (SINGLE-PROCESS アプリのみ):**
     - コード レイヤーに基づいて境界を作成しないでください。`PresentationBoundary`、`OrchestrationBoundary`、`AgentBoundary`、`ServiceBoundary` はコード レイヤーであり、デプロイメント境界ではありません。これらはすべて同じプロセスで実行されます。
     - 1 つのプロセスを 4 つ以上の境界に分割しないでください。すべてのコンポーネントが 1 つの .exe で実行される場合、それらは 1 つの境界内にあります。
   - **例**: `TerminalUserInterface`、`MCPHost`、`HealthAgent`、`ResponsesAPIService` がすべて同じプロセスで実行されるアプリケーション → それらはすべて `Application` にあります。 `AzureOpenAI` のような外部サービスは `External` にあります。
   - 同じコードを 2 回実行すると、同じ数の境界 (±1) が生成されなければなりません。境界が 2 つ以上異なる場合は誤りです。
   - コード層 (プレゼンテーション/ビジネス/データ) に基づいて境界を作成しないでください。境界は、コード アーキテクチャではなく、展開の信頼境界を表します。**境界カウントのロック:**
   - 境界を特定した後、カウントを LOCK します。同じコードを 2 回実行すると、同じ数の境界が生成されなければなりません (一方の実行でエッジ境界が識別され、もう一方の実行でエッジ境界が識別されない場合は、±1 が許容されます)。
   - 同じコード上の 4 境界と 7 境界の違いは誤りであり、命名規則に従っていないことを示します。

   **追加の命名規則:**
   - どの LLM モデルが解析を実行するか、または実行回数に関係なく、同じコンポーネントは同じ `id` を取得する必要があります。
   - 外部アクター (`Operator`、`AzureDataStudio` など) は常に含まれます。決して削除しないでください。
   - 個別のストレージ (ファイル、データベース) を表すデータストアは常に別個のコンポーネントであり、決して結合しないでください。
   - ステップ 2 の前にコンポーネント リストをロックします。これらの正確な ID を後続のすべてのファイル (アーキテクチャ、DFD、STRIDE、所見、JSON) で使用します。
   - 2 つのクラスが別個のファイルとして存在する場合 (例: `ResponsesAPIService.cs` と `LLMService.cs`)、関連しているように見えても、それらは 2 つのコンポーネントです。**⛔ データ フローの完全性 (必須 - 実行間で一貫したフロー列挙を保証します):**
   データ フローは徹底的に列挙する必要があります。同じコードベースの 2 つの独立した分析は、同じフローのセットを生成しなければなりません (MUST)。これを達成するには:
   
   **⛔ リターン フロー モデリング ルール (フロー数の 24% の差異に対処):**
   - **個別のリターン フローをモデル化しないでください。** 要求と応答のペアは 1 つの双方向フローです (Mermaid では `<-->` を使用します)。
   - 例：`DF01: Operator <--> TUI` (入力と出力で 1 つのフロー)
   - 例: `DF03: MCPHost <--> HealthAgent` (委任と結果の 1 つのフロー)
   - **2 つの方向で異なるプロトコルまたはセマンティクスが使用される場合にのみ、別のフローをモデル化します** (HTTP リクエストと WebSocket プッシュバックなど)。
   - **理由:** インタラクションごとに 1 つのフローを作成するか 2 つのフローを作成するかを実行が独立して決定する場合、フロー数は 20 ～ 30% 変化します。このルールにより、その差異が排除されます。
   - **フローカウントの式:** `# flows ≈ # unique component-to-component interactions`。コンポーネント A がコンポーネント B と通信する場合、つまり 2 ではなく 1 フローになります。
   
   **フローの完全性チェックリスト (上記のリターン フロー ルールに従って `<-->` 双方向フローを使用します):**
   1. **イングレス/リバース プロキシ フロー**: `DF_EndUser_to_NginxIngress` (双方向 `<-->`)、`DF_NginxIngress_to_Backend` (双方向 `<-->`)。それぞれは 2 つのフローではなく 1 つのフローです。
   2. **データベース/データストア フロー**: `DF_Service_to_Redis` (双方向 `<-->`)。サービスとデータストアのペアごとに 1 つのフロー。
   3. **認証プロバイダー フロー**: `DF_Service_to_AzureAD` (双方向 `<-->`)。サービスと認証のペアごとに 1 つのフロー。
   4. **管理者アクセス フロー**: `DF_Operator_to_Service` (双方向 `<-->`)。管理者の操作ごとに 1 つ。
   5. **フローカウントのロック**: フローを列挙した後、カウントをロックします。同じコードを 2 回実行すると、同じ数のフローが生成されなければなりません (±3 は許容可能)。 >5 フローの差は、列挙が不完全であることを示します。
   
   **⛔ 外部エンティティ包含ルール (外部がモデル化されるアドレス差異):**
   - コードが Azure AD / Microsoft Entra ID からトークンを取得する場合は、**常に `AzureAD` (または `EntraID`) を外部エンティティとして含めてください** (`ChainedTokenCredential`、`ManagedIdentityCredential`、`AzureCliCredential`、MSAL、または任意の OAuth2/OIDC フローを探してください)。
   - コードが PowerShell、REST、または WMI 経由で外部インフラストラクチャにコマンドを送信する場合は、**常にインフラストラクチャ ターゲット** (例: `OnPremInfra`、`HCICluster`) を外部エンティティとして含めます。
   - **コードがクラウド LLM API を呼び出す場合は、**常に `AzureOpenAI`** (または同等の LLM エンドポイント) を含めてください。
   - **CLI/TUI ツール、管理ツール、またはオペレーター コンソールの外部アクターとして `Operator`** を常に含めてください。
   - **経験則:** コードにサービスのクライアント クラスまたは構成がある場合、そのサービスは外部エンティティです。
   
   **⛔ TMT カテゴリ ルール (実行間でのカテゴリの不一致に対処):**
   - エージェントが呼び出し可能な API を公開する **ツール サーバー** → `SE.P.TMCore.WebSvc` (`SE.P.TMCore.NetApp` ではありません)
   - 接続/ソケットを処理する **ネットワーク レベルのサービス** → `SE.P.TMCore.NetApp`
   - **OSコマンドを実行するサービス** (PowerShell、bash) → `SE.P.TMCore.OSProcess`
   - **データをディスクに保存するサービス** (SessionStore、FileLogger) → `SE.DS.TMCore.FS` (プロセスではなくデータ ストアとして分類)
   - **ルール:** クラスの主な目的がデータの永続化である場合、それはデータ ストアです。計算やオーケストレーションを行う場合、それはプロセスです。実行間で切り替えを行わないでください。
   
   **⛔ DFD 方向 (必須 — レイアウトの差異に対処):**
   - すべての DFD は `flowchart LR` (左から右) を使用する必要があります。 `flowchart TB` は決して使用しないでください。
   - すべてのサマリー DFD では `flowchart LR` も使用しなければなりません。
   - これは不変です。美学や図の形状に基づいて変更されません。**PascalCase の頭字語ルール:**
   - よく知られている頭字語をすべて大文字で保持します: `API`、`NFS`、`LLM`、`SQL`、`HCI`、`AD`、`UI`、`DB`
   - 例: `IngestionAPI` (`IngestionApi` ではない)、`NFSServer` (`NfsServer` ではない)、`AzureAD` (`AzureAd` ではない)、`VectorDBAPI` (`VectorDbApi` ではない)
   - シングルワードテクノロジでは標準的な大文字小文字が維持されます: `Redis`、`Milvus`、`PostgreSQL`、`Nginx`

   **一般的なテクノロジーの名前 (よく知られているインフラストラクチャにはこれらの ID を正確に使用してください):**
   - Redis キャッシュ/状態: `Redis` (`DaprStateStore`、`RedisCache`、`StateStore` は使用できません)
   - Milvus ベクター DB: `Milvus` (決して `MilvusVectorDb`、`VectorDB`)
   - NGINX イングレス: `NginxIngress` (決して `IngressNginx` ではありません)
   - Azure AD/Entra: `AzureAD` (`AzureAd`、`EntraID` は使用しないでください)
   - PostgreSQL: `PostgreSQL` (`PostgresDb`、`Postgres` は使用しないでください)
   - ユーザー/オペレーター: `Operator` (管理者ユーザーの場合)、`EndUser` (エンドユーザーの場合)
   - Azure OpenAI: `AzureOpenAI` (`OpenAIService`、`LLMEndpoint` は使用しないでください)
   - NFS: `NFSServer` (`NfsServer`、`FileShare` は使用しないでください)
   - 2 つの LLM モデルが別々のデプロイメントである場合は、それらを別々にしておきます (`MistralLLM` + `PhiLLM` を `LocalLlm` にマージしないでください)
   
   **ただし: アプリケーション固有のクラスの場合は、テクノロジ ラベルではなく、コードからの正確なクラス名を使用してください。**

   - `TaskProcessor.cs` → `TaskProcessor` (`LocalLLM` ではありません — クラスの名前は TaskProcessor です)
   - `SessionStore.cs` → `SessionStore` (`StatePersistence` ではありません。クラスの名前は SessionStore です)
   **コンポーネントの粒度ルール (安定性にとって重要):**
   - スクリプト/ファイル レベルではなく、**テクノロジー/サービス レベル**でコンポーネントをモデル化します。
   - Kusto を実行している Docker コンテナーは `KustoContainer` — `KustoService` + `IngestLogs` + `KustoDataDirectory` には分解されません
   - Moby Docker エンジンは `MobyDockerEngine` です — `InstallMoby` ではありません (インストーラー スクリプトは証拠であり、コンポーネントではありません)
   - ツールのインストーラーは `SetupInstaller` です — `InstallAzureEdgeDiagnosticTool` (スクリプト ファイル名) に名前は変更されません
   - ルール: コンポーネントに 1 つの主要な機能 (例: 「Kusto クエリの実行」) がある場合、それを実装するスクリプト/ファイルの数に関係なく、それを 1 つのコンポーネントとしてモデル化します。
   - スクリプトはコンポーネントの証拠であり、コンポーネント自体ではありません

   - カテゴリは 0、1、2、3、またはそれ以上の脅威を生成する可能性があります。その数はコンポーネントの実際の攻撃対象領域によって異なります。カテゴリごとに 1 つの脅威を上限にしないでください。豊富なセキュリティ面を備えたコンポーネント (API サービス、認証マネージャー、コマンド実行プログラム、LLM クライアント) には通常、関連する STRIDE カテゴリごとに 2 ～ 4 つの脅威が存在します。単純なコンポーネント (静的構成、読み取り専用データ ストア) のみがほとんど 0 ～ 1 を持つ必要があります。

   - N/A エントリは、概要テーブルの脅威の合計にはカウントされません。具体的な脅威の行のみがカウントされます。
   - 概要テーブルの S/T/R/I/D/E/A 列には、カテゴリごとの具体的な脅威の COUNT が表示されます (N/A が正当化された場合は 0 が有効です)。

      b. **Python 抽出スクリプト** — マークダウン ファイルを読み取り、正規表現を介して脅威/検出結果を抽出し、JSON を書き込む Python スクリプトを作成します。ターミナル経由でスクリプトを実行します。

   5. **カウントが一致しない状態でステップ 9 (評価) またはステップ 10 (検証) に決して進まないでください**
   
   ⛔ **大規模リポジトリ戦略 (脅威が 60 を超えるリポジトリには必須):**
   最大 60 を超える脅威を生成するリポジトリの場合、JSON ファイルが 1 回のパスで生成された場合、出力トークンの制限を超える可能性があります。このチャンク化アプローチを使用します。
   1. **メタデータ + コンポーネント + 境界 + フロー + メトリクスを最初に書き込みます** - これらは小さな配列です
   2. **脅威をバッチで追加** — 追加操作ごとに最大 20 個の脅威を含む脅威配列を書き込みます。 1 回の `create_file` 呼び出しで JSON 全体を書き込むのではなく、`replace_string_in_file` を使用して既存のファイルにバッチを追加します。
   3. **検出結果を追加** — 検出結果が 15 個を超える場合は同様にバッチ処理
   4. **最終検証** — 完成したファイルを読み取り、すべての配列の長さがメトリックと一致することを確認します。
   
   **代替アプローチ:** 分割して書き込むことが不可能な場合は、各脅威/検出エントリを最小限に抑えます。

   - `mitigation`フィールド：最大1文

   - JSON は読み取り用ではなくマッチング用です - 簡潔さが重要です9. **評価を書く** (`0-assessment.md`)

   - ⚠️ **7 つのセクションはすべて必須です:** レポート ファイル、エグゼクティブ サマリー、アクション サマリー (クイック ウィンを含む)、分析コンテキストと前提条件 (必要な検証 + オーバーライドの検索を含む)、参照した参考文献、レポート メタデータ、分類リファレンス

   1. 正確に 7 つのセクション: レポート ファイル、エグゼクティブ サマリー、アクション サマリー、分析コンテキストと前提条件 (`&` 付き)、参考にした参考文献、レポート メタデータ、分類リファレンス

   ⛔ **フェイルファスト ゲート:** 書き込み直後に、`verification-checklist.md` から `0-assessment.md` のインライン クイック チェックを実行します。続行する前に修正してください。

10. **最終検証** — 反復修正ループ

    このステップでは、すべてのチェックに合格するまでループで検証と修正を実行します。失敗が残ったままファイナライズしないでください。

    **パス 1 — 包括的な検証:**
    - `verification-checklist.md` + 出力フォルダー パスの内容を検証サブエージェントに委任します。
    - サブエージェントはフェーズ 0 ～ 5 のすべてのチェックを実行し、証拠とともに合否を報告します。
    - いずれかのチェックが失敗した場合:
      1. 利用可能なファイル編集ツールを使用して、失敗したファイルを修正します
      2. 修正されたファイルに対して失敗したチェックのみを再実行します。
      3. 失敗したチェックに合格するまで繰り返します

    **パス 2 — 回帰チェック (パス 1 に修正があった場合):**
    - フェーズ 3 (ファイル間の整合性) を再実行して、修正によって他のファイルが破損していないことを確認します
    - 新たな障害が発生した場合は、修正して再検証します

    **終了条件:** すべてのフェーズで失敗が 0 件報告されます。その後でのみ、分析を完了としてマークします。**サブエージェントコンテキスト管理:**
    - `verification-checklist.md` からの関連フェーズのコンテンツをサブエージェント プロンプトに含めます
    - サブエージェントがファイルを読み取れるように、出力フォルダーのパスを含めます。
    - サブエージェントの出力には、フェーズ名、合計チェック、合格、失敗、および各失敗のチェック ID、ファイル、証拠、正確な修正指示が含まれなければなりません。数えずに「良さそうです」を返さないでください。

## ツールの使用法

### 進捗状況の追跡 (todo)
- 各主要フェーズの開始時に Todo を作成する
- 各フェーズを開始する前に進行中をマークする
- 各フェーズが終了したらすぐに完了マークを付けます

### サブタスクの委任 (エージェント)
狭い読み取り専用タスクをサブエージェントに委任します (上記のサブエージェントのガバナンスを参照)。許可される委任:
- **コンテキスト収集:** 「これらのディレクトリで認証パターンを検索し、概要を返します」
- **コード分析:** 「これらのファイルを読み取り、セキュリティ関連の API、資格情報、および信頼境界を特定します」
- **検証:** 検証サブエージェントに `verification-checklist.md` の内容と出力フォルダーのパスを渡します。ファイルを読み取り、PASS/FAIL 結果を返します。 PARENT は障害を修正します。
- **JSON 生成 (例外):** 大規模なリポジトリの場合、正確なファイル パスと事前計算されたデータを使用した書き込み `threat-inventory.json` をデリゲートします。

**決して委任しないでください:** 「0.1-architecture.md を作成する」、「STRIDE 分析を生成する」、「脅威モデル分析を実行する」、またはサブエージェントが独自にレポート ファイルを作成するようなプロンプトは実行しないでください。

## 検証チェックリスト (最終ステップ)

完全な検証チェックリストは `verification-checklist.md` にあります。 9 つのフェーズが含まれています。

> **権限階層:** `orchestrator.md` は、AUTHORING ルール (レポート作成時に何を行うか) を定義します。 `verification-checklist.md` は、CHECKING ルール (書き込み後に何を確認するか) を定義します。一部のルールは可視化のために両方のファイルに表示されます。ルールが競合する場合、`orchestrator.md` ルールがオーサリングの決定に優先され、`verification-checklist.md` が合否基準に優先されます。すべての構造、図、一貫性チェックの完全なリストについては、常に `verification-checklist.md` を参照してください。これは、高品質なゲートの信頼できる唯一の情報源です。0. **フェーズ 0 — 一般的な偏差スキャン**: 間違っている→正しい例を含む既知の偏差パターン
1. **フェーズ 1 — ファイルごとの構造チェック**: セクションの順序、必要なコンテンツ、フォーマット
2. **フェーズ 2 — ダイアグラム レンダリング チェック**: Mermaid の初期化ブロック、classDef、スタイル、構文
3. **フェーズ 3 — ファイル間の整合性チェック**: コンポーネントの網羅性、DF マッピング、脅威から発見までのトレーサビリティ
4. **フェーズ 4 — 証拠の品質チェック**: 証拠の具体性、フラグを立てる前にコンプライアンスを検証する
5. **フェーズ 5 — JSON スキーマ検証**: スキーマ フィールド、配列の完全性、メトリクスの一貫性
6. **フェーズ 6 — 決定的アイデンティティ**: コンポーネント ID の安定性、境界の命名、フロー ID の一貫性
7. **フェーズ 7 — 証拠に基づく前提条件**: 導入の前提条件となる証拠、網羅性
8. **フェーズ 8 — HTML の比較** (増分のみ): HTML 構造、注釈、CSS の変更

**インライン クイック チェック:** `verification-checklist.md` には、各ファイルの書き込み直後 (ステップ 10 の前) に実行する必要があるインライン クイック チェックも含まれています。これらは、コンテンツがまだアクティブなコンテキストにあるときにエラーをキャッチします。

**2パス使用:**
- **作成前 (ワークフローの事前作業):** フェーズ 1 とフェーズ 2 をスキャンして、構造ゲートと図の品質ゲートを内部化します。これにより、やり直しが防止されます。
- **書き込み後 (ステップ 10):** 完了した出力に対して、フェーズ 0 ～ 4 のすべてのチェックを包括的に実行します。フェーズ 0 が最も重要です。これは、実行間で持続する偏差を捕捉します。完了する前に障害を修正してください。

**委任:** 検証サブエージェントに `verification-checklist.md` の内容と出力フォルダーを渡します。すべてのチェックが実行され、PASS/FAIL の概要が生成されます。完了する前に障害を修正してください。
