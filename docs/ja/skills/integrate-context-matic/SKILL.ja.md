# API統合

ユーザーがサードパーティAPIの統合や外部API・SDKを使った実装を依頼した場合は、以下のワークフローに従ってください。利用可能なAPIやその機能については自身の知識に頼らず、必ずcontext-matic MCPサーバーを使用してください。

## 適用タイミング

以下の場合にこのスキルを適用してください：
- サードパーティAPIの統合を依頼されたとき
- 外部サービスのクライアントやSDKを追加したいとき
- 外部APIに依存する実装を依頼されたとき
- 特定のAPI（例：PayPal、Twilio）とその実装や統合について言及されたとき

## ワークフロー

### 1. ガイドラインとスキルの存在を確認する

#### 1a. プロジェクトの主要言語を検出する

ガイドラインやスキルの確認前に、ワークスペースを調査してプロジェクトの主要プログラミング言語を特定します：

| ファイル / パターン | 言語 |
|---|---|
| `*.csproj`, `*.sln` | `csharp` |
| `"typescript"`依存のある`package.json`または`.ts`ファイル | `typescript` |
| `requirements.txt`, `pyproject.toml`, `*.py` | `python` |
| `go.mod`, `*.go` | `go` |
| `pom.xml`, `build.gradle`, `*.java` | `java` |
| `Gemfile`, `*.rb` | `ruby` |
| `composer.json`, `*.php` | `php` |

以降のすべてのステップで、`language`が必要な場合は検出した言語を使用してください。

#### 1b. 既存のガイドラインとスキルを確認する

ワークスペース内にガイドラインやスキルが既に追加されているか確認します。

- `{language}-conventions`は**add_skills**によって生成されるスキルです。
- `{language}-security-guidelines.md`と`{language}-test-guidelines.md`は**add_guidelines**によって生成される言語別のガイドラインファイルです。
- `update-activity-workflow.md`は**add_guidelines**によって生成されるワークフローガイドラインファイルで、言語特有ではありません。
- これらは独立して確認し、一方の存在をもって他方が存在すると判断しないでください。
- **必要なガイドラインファイルが不足している場合：** **add_guidelines**を呼び出してください。
- **プロジェクトの言語に対して`{language}-conventions`が不足している場合：** **add_skills**を呼び出してください。
- **すべての必要なガイドラインファイルと`{language}-conventions`が既に存在する場合：** このステップをスキップし、ステップ2に進んでください。

### 2. 利用可能なAPIを発見する

利用可能なAPIを見つけるために**fetch_api**を呼び出します。必ずここから開始してください。

- 常にステップ1aで検出した`language`パラメータを指定してください。
- 常に`key`パラメータを指定してください：ユーザーのリクエストからAPI名/キーを渡します（例：`"paypal"`、`"twilio"`）。
- ユーザーがAPI名/キーを指定していない場合は、どのAPIを統合したいか尋ね、その値で`fetch_api`を呼び出してください。
- ツールは完全一致があれば該当APIのみを返し、一致がなければAPIカタログ全体（名前、説明、`key`）を返します。
- 名前と説明をもとにユーザーのリクエストに合致するAPIを特定してください。
- 以降のツール呼び出しで使用するため、ユーザーが要求したAPIの正しい`key`を抽出してください。

**リクエストされたAPIがリストにない場合：**
- このプラグイン（context-matic）で現在利用できない旨をユーザーに伝え、処理を停止してください。
- API統合の進め方についてユーザーに指示を求めてください。

### 3. 統合ガイダンスを取得する

- `ask`に`language`、ステップ2で得た`key`、およびあなたの`query`を渡してください。
- 複雑な質問は小さく分割して焦点を絞ったクエリにすると良い結果が得られます：
  - _「認証はどうすればいいですか？」_
  - _「支払いを作成するには？」_
  - _「レート制限はどのようになっていますか？」_

### 4. SDKのモデルとエンドポイントを調べる（必要に応じて）

これらのツールは定義を返すだけで、API呼び出しやコード生成は行いません。

- **model_search** — モデル/オブジェクト定義を調べる。
  - `language`、`key`、および正確または部分的な大文字小文字を区別するモデル名を`query`として渡します（例：`availableBalance`、`TransactionId`）。
- **endpoint_search** — エンドポイントメソッドの詳細を調べる。
  - `language`、`key`、および正確または部分的な大文字小文字を区別するメソッド名を`query`として渡します（例：`createUser`、`get_account_balance`）。

### 5. マイルストーンを記録する

以下のマイルストーンが**コードやインフラで具体的に達成されたとき**にのみ、対応する`milestone`を指定して**update_activity**を呼び出してください。単なる言及や計画段階では呼び出さないでください。

| マイルストーン | 呼び出すタイミング |
|---|---|
| `sdk_setup` | SDKパッケージがプロジェクトにインストールされたとき（例：`npm install`、`pip install`、`go get`が実行され成功した場合）。 |
| `auth_configured` | API認証情報がプロジェクトの実行環境に明示的に書き込まれ（例：`.env`ファイル、シークレットマネージャー、設定ファイルに存在し）、かつ実際のコードで参照されているとき。 |
| `first_call_made` | 最初のAPI呼び出しコードが書かれ、実行されたとき。 |
| `error_encountered` | 開発者がバグ、エラー応答、失敗した呼び出しを報告したとき。 |
| `error_resolved` | 修正が適用され、API呼び出しが正常に動作することが確認されたとき。 |

## チェックリスト

- [ ] プロジェクトの主要言語を検出した（ステップ1a）
- [ ] ガイドラインファイルが不足していた場合は`add_guidelines`を呼び出し、そうでなければスキップした
- [ ] `{language}-conventions`が不足していた場合は`add_skills`を呼び出し、そうでなければスキップした
- [ ] 正しい`language`と`key`（API名）で`fetch_api`を呼び出した
- [ ] リクエストされたAPIの正しい`key`を特定した（見つからなければユーザーに通知した）
- [ ] マイルストーンがコードやインフラで具体的に達成されたときのみ`update_activity`を呼び出した — 質問、検索、ツール参照時には呼び出さない
- [ ] 各統合マイルストーンで適切な`milestone`を指定して`update_activity`を呼び出した
- [ ] 統合ガイダンスやコードサンプルに`ask`を使用した
- [ ] SDKの詳細には必要に応じて`model_search` / `endpoint_search`を使用した
- [ ] 各コード修正後にプロジェクトがコンパイル可能であることを確認した

## 注意事項

- **APIが見つからない場合**：`fetch_api`にAPIが存在しなければ、SDKの使い方を推測せずにユーザーにこのプラグインで利用できない旨を伝え、処理を停止してください。
- **update_activityとfetch_api**：`fetch_api`はAPI発見のためのものであり統合ではありません。`fetch_api`の前に`update_activity`を呼び出さないでください。
