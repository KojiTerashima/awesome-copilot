# オペレーティング・ケイデンス

30人で機能していた会議構造は、100人で崩壊します。100人で機能していたものは、300人で崩壊します。失敗パターンは常に同じです。会議が多すぎ、参加者が多すぎ、意思決定が少なすぎるのです。

## 使うべきタイミング

**トリガー:**
- 「会議で意思決定が出ない」
- 「成長しているのに足並みが悪くなっている」
- 「どの頻度で会議すべき？」
- 「部門横断で何が起きているか誰も分からない」
- 「意思決定にものすごく時間がかかる」
- 「経営陣が一日中会議に入っている」

**コンテキスト:**
- 20人から300人超へスケール中の企業
- PMF後〜成長ステージ
- 分散 / リモートチーム
- 「これについて話さないと」がデフォルト化したあらゆる段階

## コアフレームワーク

### 1. 5階層の会議アーキテクチャ

**パターン:**

会議ごとに目的は異なります。これを混同すると、非効率（時間の浪費）か混乱（意思決定の不明確さ）のどちらかが起こります。会議は、機能、頻度、決裁権限で分離してください。

**Level 1: Daily Standup（15分、チームのみ）**

- 昨日完了したこと、今日着手すること、ブロッカー
- 最大5〜10人。全社スタンドアップは見せ物
- アンチパターン: ステータス報告（会議ではなくSlackを使う）
- アンチパターン: 戦略議論（時間も場所も不適切）
- 成功基準: 15分で終わり、1〜2件のブロッカーが可視化される

**Level 2: Weekly Functional Reviews（60分、各部門リーダー）**

各部門は週次の固有リズムを持つ:
- Product team 金曜16時: 指標、ユーザーフィードバック、ロードマップのブロッカー
- GTM team 火曜16時: パイプライン、顧客アップデート、案件健全性
- Engineering 水曜16時: ベロシティ、バグバックログ、デプロイ

フォーマット: 指標レビュー（10分）→ 勝ち筋/ブロッカー（15分）→ 1テーマ深掘り（30分）→ 翌週優先事項（5分）

アンチパターン: 会議で全問題を解こうとすること。1〜2件に絞り、残りはフォローアップに委任する。

**Level 3: Weekly All-Hands（60分、全社）**

スケーリング企業における、最重要のアラインメント装置です。

- CEOアップデート（15分）: ノーススター進捗、週次フォーカス、変化点
- 指標ダッシュボード（10分）: 毎週同一フォーマット（継続性がパターン認識を可能にする）
- 深掘り（20分）: チーム入力が必要な戦略テーマを1つ — 発表ではなく議論
- Q&A（15分）: 本物の質問に、本物の回答

アンチパターン: 防御的トーン。All-handsは率直であるべきで、取り繕う場ではない。  
アンチパターン: 指標の不一致。ダッシュボードを変えると、チームは進捗追跡できない。

**Level 4: Bi-Weekly Leadership Alignment（90分）**

- ノーススター進捗（5分）
- 部門アップデート（30分、各5〜7分）
- 解決が必要な主要意思決定（30〜40分）: リソース競合、戦略転換、顧客/プロダクト判断
- 今後2週間の計画（15分）

ここで部門横断のブロッカーを解消します。部門が独立稼働したままなら、この会議は機能していません。

**Level 5: Quarterly Strategic Planning（半日〜1日）**

- 前四半期の振り返り（90分）: 何が機能し、何が機能せず、次にどう変えるか
- 次四半期の計画（120分）: 何を最適化するか？ロードマップは何か？
- 部門別ブレイクアウト（90分）: 各部門が四半期計画を策定
- 統合（60分）: 部門ごとのコミット共有と競合解消

アンチパターン: 「楽しいアクティビティ」が多すぎて中身が薄い。  
アンチパターン: 明確な意思決定が出ない。

**スケーリング時の調整:**

- **<30人**: Level 2-3のみ。日次スタンドアップは不要（全体が見える）。隔週リーダー会議も不要（あなた自身がリーダー層）。
- **30-100人**: 5レベルすべて追加。月次レビューで、日々見えなくなったものを補足。
- **100-300人**: Skip-levelレビューを追加。実行現場から2階層以上離れる。
- **300+人**: 部門別サブケイデンスを追加。CEOの会議数は50人時点より**少なく**あるべきで、増やすべきではない。

**これを機能させるルール:**

すべての会議は意思決定を生むか、キャンセルする。ステータス更新は非同期。会議中に誰も意思決定していないなら、退出する。

### 2. 週次メトリクス報告（問題を早期検知するダッシュボード）

**パターン:**

月次報告では問題発見が30日遅れます。その時点では悪い月は確定済みです。週次報告なら第2週で問題を掴めるため、まだ月を救えます。

**フォーマット（毎週同じ構造）:**

```
[DATE] の週

North Star: [Metric]
今週: [Value] | 先週: [Value] | 変化: [+/-] [↑↓]
コンテキスト: [1文 — このトレンドが重要な理由]

部門指標:
  Product:  7-Day Retention: 34% | Last: 33% | +1% ↑
            Feature Adoption: 18% | Last: 16% | +2% ↑
            Context: Onboarding improvements showing impact

  GTM:      Pipeline: $8.2M | Last: $7.8M | +$400K ↑
            New POCs: 3 | Last: 2
            Context: Partner pipeline adding deals

  Health:   Team Morale: 7.2/10 (down from 7.5)
            Context: Org restructure causing uncertainty
```

**運用ルール:**

1. **毎週同じ指標。** 継続性がパターン認識を可能にする。指標追加はOK、削除はしない。
2. **指標ごとに1文のコンテキスト。** 数字だけでなく、なぜ重要か？計画比は？前期間比は？
3. **全指標にトレンド方向。** 上昇/下降/横ばいの矢印。大きく動いたなら一時要因か構造要因かを明示。
4. **信号色を使う。** GREEN（順調）、YELLOW（要注意）、RED（対応必要）。REDには必ず、担当者・具体アクション・期限を付与。

**エスカレーションルール:**

同じアクションプランで2週連続REDならエスカレーションする — そのアクションプランは機能していない。

**指標数の目安:**

合計8〜12個。動いても行動が変わらない指標は削除。40指標のダッシュボードは意思決定ツールではなく装飾。

**よくあるミス:**

見栄えは良いが事業成果を予測しないバニティ指標。利用文脈なしの総ダウンロード数。裏付け指標のないCEO向け見出し。

### 3. 四半期計画（戦略ドリフトを防ぐプロセス）

**パターン:**

四半期計画がないと企業は漂流します。各部門が局所最適化し、SalesはICP外の案件を追い、Productは単一顧客向け機能を作り、Marketingはパイプラインにつながらない施策を回します。

**3週間の計画サイクル:**

**Week 1: 振り返り + データ収集**
- 前四半期実績 vs 計画（リーダーシップが準備）
- 各部門が1ページの振り返り作成: 何が機能し、何が機能せず、どう変えるか
- Finance準備: 売上実績、支出実績、予測
- 市場データ: 競合の動き、顧客フィードバックのテーマ、勝敗分析

**Week 2: 優先順位設定（リーダーシップ半日）**
- 振り返りレビュー（30分 — 事前読了、会議で発表しない）
- 会社レベルの優先事項を3〜5件合意
- 各項目に対し: オーナー、成功指標、必要リソース
- **やらないこと**を特定（やることと同じくらい重要）
- 部門横断依存関係を解消
- ノーススターをタイブレーカーとして使用: 「これは目標達成に寄与するか？寄与するなら優先。あれば嬉しい程度なら後回し。」

**Week 3: OKR展開 + リソース配分**
- 各部門が会社優先事項をチームOKRに落とし込む
- リーダーシップが整合性をレビュー
- リソース配分を確定（人員、予算、ツール）
- 最終計画を全社共有

**四半期コミットメントの形式:**

```
Q2 2026 Roadmap
North Star: [What we're optimizing for]

Pillar 1: Product (25% team effort)
  Initiative: [Name]
    Problem: [What we're solving]
    Success: [Specific metric]
    Owner: [Name]
    Timeline: [When]

Pillar 2: GTM (50% team effort)
  Initiative: [Name]
    ...

Pillar 3: People (10% effort)
  Initiative: [Name]
    ...

Pillar 4: Tech Debt (15% effort)
  Initiative: [Name]
    ...
```

**「やらないこと」リスト:**

優先事項を1つ追加するごとに、1つ止めるものを特定する。**やらないこと**を言語化できないなら、優先事項が多すぎる。

**よくあるミス:**

誰も読まない30ページ文書を生む四半期計画。成果物は、オーナーと指標付きの3〜5優先事項を1ページにまとめること。それだけ。

### 4. 意思決定スピードと権限

**パターン:**

20人ではCEOがほぼ全判断をリアルタイムで下せる。速い。100人では判断にアラインメントが必要。遅い。300人ではアラインメント、承認、文書化が必要。氷河並みに遅い。

**解決策は会議増ではない。明確な決裁権限だ。**

**意思決定権限マトリクス:**

| Decision | Who Decides | Timeline | Escalation |
|----------|------------|----------|------------|
| Company strategy | CEO | 1 week | Board if strategic |
| Feature priority | Product lead | 1 week | CEO if >3 eng weeks |
| Customer support issue | CSM | Immediately | CS lead if escalated |
| Marketing campaign | Marketing lead | 2 weeks | CMO if >$10K budget |
| Hiring | Function leader | 2 weeks | CEO if role not approved |
| New partnership | CEO | 2 weeks | Board if strategic |
| Vendor selection | Function leader | 1 week | CEO if >$50K/year |

**問題:**

スケーリング企業は、可逆で低リスクな判断を、不可逆で高リスクの判断のように扱い始める。すべて承認が必要。すべて会議が必要。すべて合意形成が必要。

**修正:**

**Type 1（不可逆・高リスク）:** 価格モデル、市場参入、大型提携 → CEO/経営が1回の会議で議論し決定。期限: 最大1〜2週間。

**Type 2（可逆・低リスク）:** クリエイティブ案、機能優先順位、単発採用 → 部門オーナーが決定し、共有し、改善。期限: 当日または翌日。

**100%ではなく70%の情報で決める。** スピードはすべての段階で競争優位。

**よくあるミス:**

協業を装った合意主義。「全員の足並みをそろえよう」はしばしば「誰も決めたくない」の言い換え。決裁者を明示し、決めてもらい、次へ進む。

### 5. Async-Firstコミュニケーション

**パターン:**

同期会議はスケールしない。デフォルトを非同期にし、必要時のみ同期へエスカレーションする。

**Async First（会議不要）:**
- 意思決定文書（重要案件でも同様 — 提案を文書化し、コメントを募り、48〜72時間フィードバックを取り、合意または重大異論なしで決定）
- 進捗共有（会議ではなく週次レポート）
- プロセス変更とSOP
- すでに決まった決定事項（議論ではなく周知）

**Syncが必要なとき:**
- リアルタイムのブレインストーミングが必要
- 大きな対立を解く必要がある
- ホワイトボードが要る複雑テーマ
- チームビルディング / 関係構築

**ドキュメント規律:**

すべての意思決定を文書化: 何を決めたか？なぜか？誰が決めたか？いつ発効するか？誰が知るべきか？

検索可能な形式（wiki、共有ドライブ）で保管。新入社員のオンボーディングが速くなり、過去の決定を蒸し返さなくなる。

**よくあるミス:**

「クイック同期」会議が週10時間を食いつぶす。Slackで過剰共有（流れやすくノイジー）し、永続形式（ドキュメント、メール）での共有が不足。重要事項は6か月後も検索可能であるべき。

### 6. CEO週次アップデート

**パターン:**

スケーリング企業で最もレバレッジの高いコミュニケーション手段。作成5〜10分。全員が読む。文脈設定、成果称賛、優先事項明示、共通認識形成を実現する。

**形式（日曜夜または月曜朝に送信）:**

**1. Week Focus（1段落）:**
今週の優先事項は何か？チームは何に集中すべきか？

**2. North Star Progress（1〜2箇条）:**
主要指標はどこにいるか？上昇/下降/横ばいか？なぜ重要か？

**3. Wins This Week（3〜5箇条）:**
何をリリースしたか？顧客/パートナーの成果は？大局的な意味は？

**4. Blockers Getting Resolved（1〜2箇条）:**
今週何をアンブロックするか？誰が把握すべきか？

**5. Ask（1箇条、任意）:**
チームが必要とする支援は？紹介、フィードバック、顧客紹介など？

**ルール:**

毎週同じ曜日。継続性はオペレーション規律のシグナル。1週でも飛ばすとチームは気づき、「何を隠しているのか」と考え始める。

**よくあるミス:**

長すぎる（読まれない）、詳細すぎる（部門会議に回す）、良いニュースだけ（信頼を失う）、不定期（読まれなくなる）。

### 7. 役割明確化 > タイトル

**パターン:**

スピードの最強ツールは階層ではなく、明示的な役割明確化。自分の責任範囲が明確で、他に委譲できないと、意思決定は速くなる。

**実行方法:**

- すべての施策に、オーナーを必ず1人だけ設定（サポートメンバーは可）
- 指標はそのオーナーに紐づける
- 成功はタスク完了でなくKPIの変化で測る
- 明確なオーナー不在の施策は48時間以内に整理する

**テスト:**

この成果を所有する「たった1人」を言えるか？「チーム」ではなく個人。言えないなら施策は漂流する。

**よくあるミス:**

複数人へのプロジェクト割当（「全員がオーナー」= 誰もオーナーでない）。インパクトではなく活動量を測る。施策ごとの明確なROI追跡なしにバーンレートだけ上がる。

## 意思決定ツリー

### どの会議レベルが必要か？

```
Company size <30?
├─ Yes → Levels 2-3 only (weekly functional + all-hands)
└─ No → Continue...
    │
    30-100 people?
    ├─ Yes → All 5 levels
    └─ No → All 5 + skip-level reviews + function sub-cadences
```

### この会議は残す価値があるか？

```
Does it produce decisions?
├─ No → Can it be async?
│   ├─ Yes → Make it async, cancel the meeting
│   └─ No → Redesign with decision agenda
└─ Yes → Are the right people in the room?
    ├─ No → Fix attendee list (fewer > more)
    └─ Yes → Keep it
```

## よくあるミス

**1. 成長とともに会議を追加する**  
置き換えるべき。200人時点でCEOの会議数は50人時点より少ないべき。

**2. ステータス更新会議**  
メールで済むならメールにすべき。会議は意思決定のために使う。

**3. 四半期ごとに指標を変える**  
継続性がトレンド識別を可能にする。毎回同じダッシュボードで。

**4. 合意主義カルチャー**  
決裁者を明示し、決めてもらい、他は周知する。

**5. すべての情報がSlackにある**  
流れやすく、ノイジーで、検索しづらい。重要決定はドキュメントへ。

**6. 30ページ文書を生む四半期計画**  
1ページに3〜5優先事項。それが成果物。

## クイックリファレンス

**会議アーキテクチャ:**  
Daily standup（15分）→ Weekly functional（60分）→ Weekly all-hands（60分）→ Bi-weekly leadership（90分）→ Quarterly planning（半日）

**週次メトリクスダッシュボード:**  
8〜12指標、毎週同形式、信号色、指標ごとに1文コンテキスト、すべてのREDに owner + action + deadline

**四半期計画サイクル:**  
Week 1: Retro + data → Week 2: Priority setting（最大3〜5）→ Week 3: OKR cascade + resources

**意思決定権限:**  
Type 1（不可逆）: CEO/leadership、1〜2週間 → Type 2（可逆）: Function owner、当日

**CEO週次アップデート:**  
Week focus → North star progress → Wins → Blockers → Ask

**情報フロー:**  
日次: Slack wins/customer-voice → 週次: CEO email + function updates → 月次: All-hands + skip-levels → 四半期: Planning share + demos
