# オンボーディング：ContextMatic MCP

このスキルは `context-matic` MCPサーバーのガイド付きインタラクティブツアーを提供します。  
すべてのフェーズを順番に進めてください。各インタラクションポイントの後はユーザーの返答を待ってから続行してください。

> **エージェントの行動ルール — スキル全体を通して守ること：**  
> - **スキルの構造を説明しないこと。** フェーズ名やステップ番号、指示を読んでいるような言い方（例：「フェーズ1では…」「ステップ1a：」「スキルに従って…」）はしないでください。自然な会話としてツアーを進めてください。  
> - **ツール呼び出しは必ず事前に宣言すること。** 一文で十分です。何を調べるのか、なぜ調べるのかをユーザーに伝えてからツールを呼び出してください。例：「プロジェクト言語で利用可能なAPI一覧を取得しますね。」これによりユーザーは状況を把握でき、無言の間が生じるのを防げます。

## フェーズ0 — オープニングとツール紹介

まず、サーバーが何をするものかを簡単にわかりやすく説明してください。以下の内容をもとに自分の言葉で伝えてください。

> **context-matic** MCPサーバーは、AI支援コーディングの根本的な問題を解決します。一般的なモデルは公開コードで学習されていますが、それはしばしば古く誤りがあったり、新しいSDKバージョンには対応していなかったりします。このサーバーは**ライブでバージョンを認識する基盤レイヤー**として機能します。エージェントがトレーニングデータからSDKの使い方を推測する代わりに、現在のAPIバージョンとプロジェクトのプログラミング言語に合致する正確なSDKモデル、エンドポイント、認証パターン、実行可能なコードサンプルをサーバーに問い合わせます。

問題の説明が終わったら、初めて使う人に紹介するように4つのツールを順に説明してください。各ツールについて以下を伝えます：  
- **何をするものか** — 覚えやすい一行説明  
- **いつ使うか** — 具体的で身近なシナリオ  
- **何が返ってくるか** — ユーザーが見る出力の種類

以下の内容を参考にしつつ、会話調で説明してください。表はそのまま提示しないでください。

> | ツール | 機能 | 使う場面 | 返り値 |
> |---|---|---|---|
> | `fetch_api` | APIの`key`/識別子と言語に完全一致するAPIを返すか、言語ごとのAPI一覧を返す。`key`は`fetch_api`が返す機械可読識別子（例：`paypal`）で、人間向け表示名（例：「PayPal Server SDK」）ではない。 | 「どんなAPIが使える？」／新規プロジェクト開始時／「PayPal SDKはある？」 | 利用可能なAPIの名前付きリスト（短い説明付きの全カタログ）または指定した識別子と言語に完全一致するAPI |
> | `ask` | 統合に関する質問にバージョン正確なガイダンスとコードサンプルで回答 | 「認証はどうする？」「クイックスタートを見せて」「Xの正しいやり方は？」 | 実際のSDKバージョンに基づくステップバイステップの案内と実行可能なコードサンプル |
> | `model_search` | SDKのモデル/オブジェクト定義と型付きプロパティを検索 | 「Orderにはどんなフィールドがある？」「このプロパティは必須？」 | モデル名、説明、完全な型付きプロパティリスト（必須・任意、ネスト型） |
> | `endpoint_search` | エンドポイントメソッド、パラメータ、レスポンス型、実行可能なコードサンプルを検索 | 「createOrderの呼び出し方を教えて」「getTrackは何を返す？」 | メソッドシグネチャ、パラメータ型、レスポンス型、コピペ可能なコードサンプル |

このセクションの最後に、ツアー中にこれら4つのコアな探索・統合ツールをライブで実演することを伝え、今すぐ`fetch_api`から始めることを明示してください。  
このツアーはContextMaticサーバーのコアツールに焦点を当てており、広範なワークフローのすべてのヘルパーを扱うわけではないことも伝えてください。

## フェーズ1 — 利用可能なAPIを表示

### 1a. プロジェクト言語の検出

`fetch_api`を呼び出す前に、ワークスペースのファイルを調べてプロジェクトの主要言語を判別します：

- `package.json` + `.ts`/`.tsx` → `typescript`
- `*.csproj` または `*.sln` → `csharp`
- `requirements.txt`、`pyproject.toml`、または `*.py` → `python`
- `pom.xml` または `build.gradle` → `java`
- `go.mod` → `go`
- `Gemfile` または `*.rb` → `ruby`
- `composer.json` または `*.php` → `php`
- プロジェクトファイルが見つからなければ、静かに`typescript`にフォールバック

検出した言語は以降のすべてのツール呼び出しに渡します。

### 1b. 利用可能なAPIを取得

検出した言語をユーザーに伝え、利用可能なAPIを取得することを伝えます。例：  
*"これはTypeScriptプロジェクトですね。TypeScript向けの利用可能なAPIを取得しますね。"*

`fetch_api`を`language`に検出言語、`key`に空文字を渡して呼び出し、利用可能なAPIの全リストを取得します。

結果は整形したリストで表示し、各APIの**名前**と一文の**説明**を示してください。省略やスキップはしないでください。

例（実際の結果に合わせて調整してください）：

```
このサーバーで現在利用可能なAPIは以下の通りです：

1. PayPal Server SDK   — PayPal REST APIを使った支払い、注文、サブスクリプション、保管。
2. Spotify Web API     — 音楽・ポッドキャストの探索、再生制御、ライブラリ管理。
....
```

## フェーズ2 — API選択（対話）

ユーザーに尋ねます：

> 「どのAPIを調べたいですか？名前か番号を言ってください。」

**ユーザーの返答を待ってから続行してください。**

選択されたAPIの`fetch_api`レスポンスの`key`を保存し、以降のツール呼び出しに渡します。説明文で使うためAPIの名前も控えておきます。

## フェーズ3 — 選択したAPIの説明

呼び出す前に、例えば次のように言います：  
*"いい選択ですね。では[API名]の概要を取得します。"*

`ask`を以下のパラメータで呼び出します：  
- `key` = 選択したAPIのキー  
- `language` = 検出した言語  
- `query` = `"このAPIの概要を教えてください：何ができるか、主なコントローラーやモジュール、認証方法、使い始めの手順について"`

返答は会話調で提示し、以下を強調してください：  
- APIの機能（ユースケース）  
- 認証方法（認証情報、OAuthフローなど）  
- 主なSDKコントローラーや名前空間  
- インストールするNPM/pip/NuGetなどのパッケージ名

## フェーズ4 — プロジェクト言語での統合（対話）

ユーザーに尋ねます：

> 「[API名]の特定の機能を知りたいですか？例えば注文作成、トラック検索、サブスクリプション管理など。それとも統合のクイックスタートを見ますか？」

**ユーザーの返答を待ってください。**

呼び出す前に、例えば次のように言います：  
*"了解です。調べますね。" または "わかりました。クイックスタートを表示しますね。"*

`ask`を以下のパラメータで呼び出します：  
- `key` = 選択したAPIのキー  
- `language` = 検出言語  
- `query` = ユーザーの要望、または「SDKのインストール、認証情報設定、最初のAPI呼び出しを含む完全な統合クイックスタートを見せて」といった全体ガイド

返答はコードサンプルも含めてそのまま提示してください。

## フェーズ5 — `model_search`の実演

ユーザーに伝えます：

> 「次に`model_search`の使い方をお見せします。このツールはSDKのモデルやオブジェクト定義を調べられます。型付きプロパティ、必須か任意か、使われている型もわかります。部分一致や大文字小文字も区別します。」

呼び出す前に、例えば次のように言います：  
*"`[モデル名]`モデルを検索して結果を見てみましょう。"*

選択したAPIから**代表的なモデル**を選び、`model_search`を呼び出します：  
- `key` = 選択したAPIキー（例：`paypal`や`spotify`）  
- `language` = 検出言語  
- `query` = 選んだ代表モデル名

| APIキー | デモ用クエリ例 |
|---|---|
| `paypal` | `Order` |
| `spotify` | `TrackObject` |

結果を表示し、以下を説明してください：  
- 正確なモデル名と説明  
- 興味深い型付きプロパティ（必須・任意を強調）  
- ネストしたモデル参照（例：`PurchaseUnit[] | undefined`）

ユーザーに伝えます：

> 「モデル名で検索できます。部分一致も使えます。[API名]のモデルの形状を知りたいときはいつでも聞いてください。」

## フェーズ6 — `endpoint_search`の実演

ユーザーに伝えます：

> 「同様に`endpoint_search`はSDKのメソッドを調べられます。正確なパラメータ、その型、レスポンス型、実行可能なコードサンプルが得られます。」

呼び出す前に、例えば次のように言います：  
*"`[エンドポイント名]`エンドポイントを取得してパラメータとコードサンプルを見てみましょう。"*

選択したAPIの**代表的なエンドポイント**を選び、`endpoint_search`を呼び出します：  
- `key` = 選択したAPIキー（例：`paypal`や`spotify`）  
- `query` = 調べたいエンドポイント/SDKメソッド名（例：`createOrder`や`getTrack`）  
- `language` = ユーザーのプロジェクト言語（例：`typescript`や`python`）

例：

| APIキー (`key`) | エンドポイント名 (`query`) | 言語例 |
|---|---|---|
| `paypal` | `createOrder` | ユーザーのプロジェクト言語 |
| `spotify` | `getTrack` | ユーザーのプロジェクト言語 |

結果を表示し、以下を説明してください：  
- メソッド名と説明  
- リクエストパラメータと型  
- レスポンス型  
- 完全なコードサンプル（返されたまま提示）

ユーザーに伝えます：

> 「コードサンプルはすぐ使えます。正しいSDKからインポートし、クライアントを初期化し、エンドポイントを呼び出し、エラー処理も含まれています。メソッド名や部分一致の大文字小文字を区別して検索できます。」

## エージェント向けメモ

- ユーザーが`fetch_api`結果にないAPIを選んだ場合は、現在利用できない旨を伝え、利用可能なAPIでツアーを続けるか提案してください。  
- このスキルのすべてのツール呼び出しは**読み取り専用**です。プロジェクトの変更、パッケージのインストール、ファイルの書き込みはユーザーが統合を明示的に依頼しない限り行いません。  
- `endpoint_search`や`ask`のコードサンプルは、適切な言語タグ付きのコードブロックでそのまま提示してください。
