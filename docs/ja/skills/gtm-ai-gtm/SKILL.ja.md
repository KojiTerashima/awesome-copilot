# AI Product GTM

AI製品のGo-to-market戦略。これは一般的なAI原則ではなく、「autonomous」という言葉に買い手が警戒し、「teammate」という表現で転換した、エンタープライズ向け自律型AIエージェント販売の実パターンです。

## 使うべきタイミング

**トリガー:**
- 「このAI製品をどうポジショニングすべき？」
- 「買い手が『AIが本番を壊すのが怖い』と言っている」
- 「autonomous と copilot、どちらで呼ぶべき？」
- 「顧客ごとに利用量が10倍違うAIをどう価格設定する？」
- 「エンタープライズのセキュリティ審査は通ったのに運用部門に却下された。なぜ？」

**コンテキスト:**
- AIエージェントプラットフォーム（コーディング、サポート、運用）
- LLMベースのアプリケーション
- *実際に* 何かを実行する自律ツール（提案だけではない）
- AIインフラ
- AIが意思決定を行うあらゆる領域

## コアフレームワーク

### 1. エンタープライズAIの本当の反論（思っているものとは違う）

**自律型AIエージェントを売って学んだこと:**

3か月目、エンタープライズのセキュリティレビューは素早く通過していました。良い兆候ですよね？ しかし、あるパターンが見えてきました。セキュリティは承認するのに、**運用部門が却下する**のです。

反論は「AIが本番を壊すか？」ではありませんでした。彼らは「いずれ壊す」と*前提*していたのです。本当の問いはこうでした。

**「エージェントが誤った動作をしたとき、誰が責任を負うのか？」**

「エージェントを信頼できるか？」ではなく、「これに対処する*自分たちのチーム*を信頼できるか？」です。

**なぜこれが重要か:**

自律エージェントは新しい運用負荷を生みます。売っているのはAIの能力ではなく、組織としての受け入れ準備です。午前2時にあなたのエージェントが本番を止めたら、誰が呼び出されるのか？ 誰が修正するのか？ 誰がVPに説明するのか？

**フレームワーク: 責任のカスケード**

AIエージェントを導入する前に、企業は明確な答えを必要とします。

1. **L1対応**: 誰がエージェントを監視するか？（24/7運用チームか、開発チームのオンコールか）
2. **L2エスカレーション**: エージェントのアクションが失敗したとき、誰がデバッグするか？（エージェントチームか、プロダクトチームか）
3. **L3オーナーシップ**: 深刻な障害時、誰が顧客コミュニケーションを担当するか？

この3つすべてに答えられなければ、**買ってもらえません**。AIの出来がどれだけ良くても関係ありません。

**これが営業プロセスをどう変えるか:**

**従来のアプローチ:**
- AIをデモする
- 精度指標を示す
- ROIを語る

**新しいアプローチ:**
- AIをデモする
- *失敗モード*を明示的に示す
- 「このシナリオは御社の誰が対応しますか？」と聞く
- 先方のインシデント対応プロセスを一緒に確認する
- AIの失敗を既存のrunbookにマッピングする

**見極めの質問:**

「エージェントのアクションでワークフローが壊れたとき、何が起きるかを教えてください。誰にアラートが飛び、誰が調査し、ロールバックするか修正継続するかを誰が判断しますか？」

答えられないなら、まだ準備ができていません。商談を一時停止し、先にプロセス構築を支援すべきです。

**よくあるミス:**

これを*製品*の反論として扱うこと（「AIの精度を上げます」）。これは*組織*の反論です。精度向上では「午前2時に誰が持つのか」は解決しません。

**うまくいくと見てきたパターン:**

AIエージェント導入に成功する企業は、すでに次を持っています。
- 本番システムのオンコールローテーション
- インシデント対応プレイブック
- 非難しないポストモーテム文化
- 明確なエスカレーション経路

苦戦する企業は次の傾向があります。
- 手動デプロイプロセス
- ヒーロー文化（「全部Steveが直す」）
- 正式なインシデント対応なし
- 非難中心の文化

**判断基準:**

エンタープライズに自律AIをデモする前に自問してください。「これが先方の本番を壊したら、先方チームの誰が修正責任を持つのか？」。答えられないなら、先方も買えません。

### 2. Copilot vs Agent vs Teammate（3つの異なるGTMモーション）

**ポジショニングの罠:**

初期のエンタープライズ商談では「autonomous AI agent」と位置づけていました。買い手は身構えました。たった1語、「autonomous」→「AI teammate」に変えただけで、商談進行は目に見えて改善しました。

なぜか？ **言葉の選び方が買い手心理を形作るからです。**

**3つのフレーミング:**

**1. Copilot（最も安全、価値は最も低い）**
- **意味**: AIは提案し、意思決定は毎回人間
- **買い手心理**: 安全で脅威が少ない
- **GTMモーション**: 開発者導入、ボトムアップ
- **ユースケース**: コード補完、文章作成支援、検索
- **反論**: 「これにお金を払う価値はある？」（知覚価値が低い）

**2. Agent（最も怖い、価値は最も高い）**
- **意味**: AIが自律的に行動し、人間は定期的にレビュー
- **買い手心理**: 怖い、人間の置き換えを想起させる
- **GTMモーション**: エンタープライズ営業、トップダウン
- **ユースケース**: バッチ処理、自動化ワークフロー、運用
- **反論**: 「本番を壊したらどうする？」（責任不安）

**3. Teammate（最適解）**
- **意味**: AIと人間が協働し、作業を分担
- **買い手心理**: 置き換えではなくパートナーシップ
- **GTMモーション**: ハイブリッド（開発者導入 + マネージャー承認）
- **ユースケース**: 多くのAIエージェントプラットフォーム
- **反論**: 「これをどうワークフローに統合する？」（プロセスの問い）

**ポジショニングの転換:**

**Before:** 「複雑なワークフローをエンドツーエンドで処理する自律AIエージェント」
- 開発者: 「クールだけど怖い」
- マネージャー: 「うちのチームを置き換えるのか？」
- 商談進行: 遅い

**After:** 「複雑なタスクでエンジニアと組むAI teammate」
- 開発者: 「これは助かる」
- マネージャー: 「チームの生産性が上がる」
- 商談進行: 4か月以上停滞していた3件のエンタープライズ案件が、転換から8週間以内に成約

**効いた具体的な言葉選び:**

❌ **言わない:**
- 「Autonomous」（怖い）
- 「Replaces」（脅威）
- 「Fully automated」（制御不能）
- 「AI-first」（結局どういう意味？）

✅ **言う:**
- 「Teammate」（協働）
- 「Augments」または「Accelerates」（置き換えではなく支援）
- 「You stay in control」（安心感）
- 「Handles the repetitive work」（具体的価値）

**フレーミングの選び方:**

```
Does your AI make decisions without human approval?
├─ Yes → Are you selling to developers or enterprises?
│   ├─ Developers → "Agent" framing (they want autonomous)
│   └─ Enterprises → "Teammate" framing (they want control)
└─ No → "Copilot" framing (augmentation, not automation)
```

**厳しい現実:**

Agentを作ってcopilotとして位置づけることはできます。copilotを作ってagentとして位置づけることはできません。**製品能力が上限を決め、ポジショニングはその下のどこに着地するかを決めます。**

**よくあるミス:**

印象が良いからと「autonomous」を使うこと。印象が強いことと信頼されることは別です。ポジショニングで買い手が身構えた時点で負けです。

### 3. AI価格設定の問題（利用量が10倍違うとき）

**パターン:**

私が関わったすべてのAI企業が直面します。顧客Aは月1,000 APIコール、顧客Bは10,000。Bに10倍請求するべきか？ すれば解約される。しなければ粗利が崩れる。

**3つのモデル:**

**1. Seat-Based（$X / user / month）**
- **機能する場面**: AIが人間の作業を予測可能に補強する
- **例**: コード補完、文章アシスタント
- **問題**: AI価値のスケーリングを取り込めない
- **実際のリスク**: 高利用顧客が最良顧客なのに、低利用顧客を実質補助する構造になる

**2. Usage-Based（$X / API call / prediction / hour）**
- **機能する場面**: AI作業量が変動し、顧客が単位を理解できる
- **例**: 画像生成、文字起こし、バッチML
- **問題**: 高利用顧客に価格ショック
- **実際のリスク**: 顧客が製品利用を*減らす*最適化に走る

**3. Outcome-Based（達成アウトカムごとに$X）**
- **機能する場面**: アウトカムを信頼性高く測定できる
- **例**: 「修正バグごとに課金」「解決サポートチケットごとに課金」
- **問題**: 測定が難しく、ゲーム化されやすい
- **実際のリスク**: AIの成果が出なければリスクを全て売り手が負う

**実際に機能するもの（ハイブリッド）:**

基本料金（固定費をカバー） + 変動料金（価値に連動）。

**構成例:**
- Base: チームあたり $X/月（プラットフォーム利用料）
- Variable: 成功アクション/アウトカムごとに $Y
- これが機能する理由:
  - Baseがインフラ/サポート固定費をカバー
  - Variableが顧客価値と整合
  - 高利用顧客を罰しない（より大きな価値を得ている）

**もっと早くしておきたかった価格会話:**

利用量課金AIを価格設定するときは、

**顧客にこう聞く:**
「これを手作業でやると、いくらかかりますか？」

APIコール$0.10で、顧客の人件費$2節約なら安すぎます。1コール$0.50で節約が$0.40なら、十分使われません。

**価格設定ルール:**

あなたの変動料金は、**顧客の代替コストの20-30%**にすべきです。価値を取れるだけ高く、同時に十分使ってもらえるだけ低く。

**よくあるミス:**

「みんなそうしてるから」とOpenAIの価格（1Kトークン$0.01）をコピーすること。あなたのコスト構造はOpenAIではありません。あなたの提供価値もOpenAIではありません。*自社*の事業に合わせて価格を決めてください。

### 4. AI信頼ラダー（実際に登ってきた立場から）

**パターン:**

「信じてください、動きます」ではAIは売れません。信頼は段階的に築くものです。

**第一段階: 透明性（初回デモ前）**

聞かれる前に次の3つを送る:
- Model card（どのモデルか、何で学習したか、どのベンチマークでどの精度か）
- Security whitepaper（データの行き先、処理方法）
- Explainability doc（AI判断の解釈方法）

**これが効く理由:**
買い手はデューデリジェンスを行う前提です。*聞かれる前に*資料を出すと、自信と信頼性が伝わります。

**第二段階: コントロール（デモ内）**

安全機構を見せる:
- ユーザーによるAI提案の承認/却下方法
- Kill switchとrollback機構
- Confidence scoreと、AIが「不確か」と言う条件

**これが効く理由:**
「暴走AI」への恐れは現実です。制御機構を示すことで、失敗モードを真剣に設計していると証明できます。

**第三段階: パフォーマンス（4〜8週目）**

有効性を証明する:
- ベースライン（人間または従来ツール）との比較ベンチマーク
- 類似企業のケーススタディ
- 可能なら先方データでのライブデモ

**これが効く理由:**
約束より証拠。顧客1社の「週X時間削減」は、マーケティング文言100個より強い。

**第四段階: スケール（本気になった段階）**

エンタープライズ対応力を示す:
- エンタープライズ導入事例
- スケール時性能（レイテンシ、スループット、エラー率）
- コンプライアンス資料（SOC 2、GDPRなど）

**これが効く理由:**
エンタープライズはMVPを本番投入しません。1000ユーザーで倒れない証明が必要です。

**私がした失敗:**

AIの仕組みを説明する前に性能証明をしようとしたこと。買い手はシステムを理解していないため、ベンチマークを信頼しませんでした。**順序が重要です。**

**判断基準:**

デモ前に買い手から「どう動くの？」と聞かれたら、透明性ステップを飛ばしています。戻って資料を送りましょう。

### 5. エンタープライズAIデモ（成功だけでなく失敗を見せる）

**うまくいかないもの:**

AIが魔法のように全解決する作り込みデモ。買い手は「うちの汚いデータでは動かない」と思います。

**うまくいくもの:**

AIがミスして回復する様子を見せる。真剣に、これが効きます。

**機能するデモ構成:**

**1. 問題提示（30秒）**
「御社のエンジニアは[具体タスク]に何時間も使っています。実態はこうです。」
- 見せる: 現在の手動ワークフロー
- 定量化: 時間 × エンジニア数 × 週数 = 総コスト

**2. AIの試行（60秒）**
「同じタスクをAIで処理します。」
- 見せる: AIが分析し、実行する様子
- **重要な動き**: AIがエラーや不確実性に遭遇する場面を入れる
- 見せる: AIが再分析して回復する、または支援を求める
- **語る**: 「最初から完璧ではありません。不確実性への対処は人間のように行います。」

**3. 人間のレビュー（30秒）**
「ここでエンジニアがレビューして承認します。」
- 見せる: エンジニアがAIの結果を確認
- **重要な動き**: エンジニアが上書き・調整する場面を見せる
- **語る**: 「主導権は人間にあります。AIは反復作業を担い、人間は判断を担います。」

**4. 結果（30秒）**
「[X時間] → [Y分]。成果責任はエンジニアが持ち、AIが実行を加速します。」
- 定量化: 時間短縮、コスト削減、創出された余力

**これが効く理由:**

- 失敗を見せる → 信頼が高まる（隠していない）
- 回復を見せる → AIの堅牢性を示せる
- 人間の上書きを見せる → 制御権を渡せる
- 削減効果を定量化 → ROIが具体化する

**見てきたパターン:**

完璧AIデモ → 買い手は懐疑的  
不完全でも回復するAIデモ → 買い手は前のめり

**よくあるミス:**

AIが100%正確な例だけを選ぶこと。買い手は現実データが汚いと知っています。汚さを見せないと、何か隠していると受け取られます。

### 6. 「誰が責任を持つのか？」への反論ハンドラー

**反論:**

「すごく良さそうだけど、AIが何か間違えたらどうなるの？」

**悪い回答:**
「うちのAIは95%の精度で、毎週改善しています。」
（翻訳すると「5%で本番を壊すかも。頑張ってください」）

**良い回答:**
「良い質問です。失敗シナリオを一緒に見ましょう。」

**そして聞く:**

1. 「AIのアクションがエラーを起こしたとき、御社の誰が調査しますか？」
2. 「ツール障害に対するインシデント対応プロセスはありますか？」
3. 「ロールバックの判断責任は、承認したエンジニアですか？ それとも運用チームですか？」

**これで起きること:**

- 論点が「失敗するか？」（はい、します）から「失敗をどう扱うか？」へ移る
- 運用準備度を具体的に考えてもらえる
- AIエージェント導入準備ができているか判別できる

**フォローアップ:**

「推奨はこうです。まず低リスク環境から始め、2〜4週間は非クリティカルなワークフローをAIに任せる。チームがミスをどう扱うかを観察し、プロセスに自信が持てたら適用範囲を広げる。」

**これが効く理由:**

売っているのは完璧さではありません。運用成熟度を要するツールです。**未成熟な買い手を説得するより、成熟した買い手を見極めるほうが良い。**

**パターン:**

成熟した買い手: 「ツール障害のrunbookは既にある。AIもそこに追加する。」  
未成熟な買い手: 「絶対に失敗しないようにできる？」

**判断基準:**

買い手が100%精度を要求するなら、いったん離れるべきです。準備ができていません。インシデント対応プロセスが整ってから再訪してください。

### 7. AIポジショニングの罠（非対称戦を戦う）

**パターン:**

AIエージェント領域で競合していると、どの競合サイトも同じことを言います。「AIで[workflow]を自動化」。差別化しようとすると、買い手が理解しにくい複雑な技術ベンチマーク説明が必要になります。

これがポジショニングの罠です。**資金力で勝る企業の土俵で、機能競争をしてしまうこと。**

**診断方法:**

1. 直接競合5〜7社のホームページメッセージを集める
2. 共通主張を特定する（ここはコモディティ化。勝てない）
3. 自社の構造的優位をマップする（単なる機能差ではない）
4. 競合が容易に真似できないポジションを見つける

**AIポジショニングで機能する構造的優位:**
- 固有のデータまたはワークフロー所有（競合が再現できない制御点）
- 配備柔軟性（on-prem、private cloud、顧客管理インフラ）
- 価格モデル革新（成果連動、競合がseat-basedの中でのusage-basedなど）
- コミュニティ/エコシステム（時間で複利するネットワーク効果）

長続きしない機能優位:
- 「精度が高い」（競合は1スプリントで追いつく）
- 「推論が速い」（インフラはコモディティ化する）
- 「連携が多い」（コピーしやすい）

**テスト:**

各ポジショニング主張について問う。「競合は1回のプロダクトスプリントでこれをコピーできるか？」。Yesなら防御力がありません。そこにGTMを乗せてはいけません。

**よくあるミス:**

誰もがやっていることに対して「うちのほうが上」と主張すること。AIではベンチマークが毎月変わります。一時的に優れているモデル性能ではなく、アプローチの構造的な違いでポジションを取りましょう。

### 8. Ceiling Moment Qualification（高意欲AI買い手を見つける）

**パターン:**

AIエージェントにおける最も意欲の高いエンタープライズ買い手は、すでに類似ツールを導入し、限界にぶつかった人たちです。学習コストを既に払っており、課題空間を理解し、アップグレードの明確な事業根拠を持っています。

**Ceiling Momentの見分け方:**

見込み客が次を満たす:
- copilot/assistant系ツールを6か月以上利用
- 限界に到達（複雑タスクを扱えない、自社スタックに合わない、自律性が足りない）
- 乗り換えコストが低い（メンタルモデルが移植可能）
- 明確な事業ケース（「現行ツールがあってもこれを手作業でX時間使っている」）

**狙い方:**

1. 自社AI製品が補完または置換するツールを特定
2. それらツールの利用が確認できる企業リストを作成
3. 自社機能ではなく「限界」に寄せてアウトリーチ文面を作る:
   - 「[incumbent]を使うチームは、[あなたの製品が提供する能力]が必要になると天井に当たりがちです」
   - incumbentの価値は認める（悪口を言わない）
   - 「置換」ではなく「次のレベル」として位置づける

**なぜ高く転換するか:**

Ceiling-moment会話はコールドアウトリーチ比で3〜5倍転換しやすい。理由は:
- 見込み客がすでに課題を理解している
- すでにカテゴリに投資済み
- 社内予算が既に割り当てられている
- 何が足りないかを言語化できる

**見極めの質問:**

「現行ツールで自動化しようとした最も複雑なタスクは何で、どこで破綻しましたか？」

具体的な痛みを具体的に語れるならceiling-moment買い手です。「問題なく動いている」と言うなら、まだ準備ができていません。

**よくあるミス:**

ツール未経験の見込み客にAIエージェント導入を説得しようとすること。転換率が悪く、教育サイクルが長く、比較対象が「より良くやる」ではなく「何もしない」になります。既にカテゴリを信じている買い手を狙いましょう。

## 意思決定ツリー

### どのポジショニングを使うべきか？

```
Does your AI act autonomously (no approval per action)?
├─ Yes → Who are you selling to?
│   ├─ Developers → "Agent" framing
│   └─ Enterprises → "Teammate" framing
└─ No → "Copilot" framing
```

### どの価格モデルを使うべきか？

```
Can you measure customer outcomes reliably?
├─ Yes → Outcome-based (or hybrid with outcome component)
└─ No → Continue...
    │
    Does usage vary 5x+ by customer?
    ├─ Yes → Hybrid (base + usage)
    └─ No → Seat-based
```

### この買い手はAIエージェント導入準備ができているか？

```
Do they have incident response processes for tool failures?
├─ Yes → Continue...
│   │
│   Do they have on-call rotations for production systems?
│   ├─ Yes → Qualified buyer
│   └─ No → Help them build it first
└─ No → Not ready (come back in 6 months)
```

## よくあるミス

**1. 印象が強いから「autonomous」を使う**
   - これで商談が遅くなるのを何度も見ました。「autonomous」はエンタープライズを怖がらせます。「teammate」のほうが進みます。

**2. AIの失敗モードを隠す**
   - 買い手は現実データが汚いと知っています。失敗を見せないと、隠していると受け取られます。

**3. 「本番を壊すか？」を反論本体と捉える**
   - 本当の反論は「壊れたとき誰が責任を持つのか？」。精度ではなく組織準備度の問題です。

**4. OpenAIのように利用量課金AIを価格設定する**
   - あなたのコスト構造は彼らとは違います。顧客代替コストの20-30%で価格を設計しましょう。

**5. デモ前の透明性資料を飛ばす**
   - 順序が重要です。Transparency → Control → Performance → Scale。段階を飛ばさない。

**6. 完璧なAIをデモする**
   - ミス + 回復を見せる。作られた完璧さより信頼を得られます。

**7. 100%精度を求める買い手に売ろうとする**
   - その段階では準備不足です。インシデント対応プロセスを持つ成熟した買い手を絞り込むべきです。

## クイックリファレンス

**エンタープライズ反論チェックリスト:**
- [ ] 「AIが本番を壊したら誰にページが飛ぶ？」→ 先方のオンコールローテーションにマップ
- [ ] 「AI障害は誰がデバッグする？」→ 先方のインシデント対応にマップ
- [ ] 「顧客コミュニケーションは誰の責任？」→ 先方のエスカレーション経路にマップ

**ポジショニングの語彙選択:**
- ✅ Teammate, augments, accelerates, you stay in control
- ❌ Autonomous, replaces, fully automated, AI-first

**デモ構成:**
1. 問題と定量コスト（30秒）
2. 失敗/不確実性を含むAI試行（60秒）
3. 人間のレビューと上書き（30秒）
4. ROIを含む成果（30秒）

**信頼ラダー:**
1. Transparency（model card、security、explainability）
2. Control（承認ワークフロー、kill switch、confidence score）
3. Performance（ベンチマーク、事例、ライブデモ）
4. Scale（エンタープライズ導入、コンプライアンス、SLA）

**ハイブリッド価格式:**
- Base: $X/month（固定費をカバー）
- Variable: 単位あたり$Y（顧客代替コストの20-30%）
