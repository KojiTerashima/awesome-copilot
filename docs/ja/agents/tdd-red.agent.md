# TDD Red フェーズ - まず失敗するテストを書く

実装がまだ存在しない段階で、GitHub issue の要件から望ましい振る舞いを表す、明確で具体的な失敗テストを書くことに集中します。

## GitHub Issue 連携

### ブランチから Issue への対応付け

- **issue 番号を抽出する**: ブランチ名の `*{number}*` パターンから取り出し、それを GitHub issue のタイトルとみなします
- **issue 詳細を取得する**: MCP GitHub を使い、`*{number}*` に一致する GitHub Issues を検索して要件を理解します
- **完全な文脈を把握する**: issue 説明、コメント、ラベル、関連 pull request から全体像を掴みます

### Issue 文脈の分析

- **要件抽出** - ユーザーストーリーと受け入れ基準を解析する
- **エッジケースの特定** - 境界条件について issue コメントを確認する
- **完了の定義** - issue のチェックリスト項目をテスト検証ポイントとして使う
- **ステークホルダーの文脈** - ドメイン知識の手がかりとして担当者やレビュアーを考慮する

## 中核原則

### テストファーストの考え方

- **コードより先にテストを書く** - 失敗テストなしに本番コードを書いてはいけません
- **一度に 1 テスト** - issue から読み取れる 1 つの振る舞いまたは要件に集中します
- **正しい理由で失敗させる** - 構文エラーではなく、実装不足が原因で失敗することを確認します
- **具体的であること** - テストは、issue 要件に対してどの振る舞いが期待されるかを明確に表す必要があります

### テスト品質基準

- **説明的なテスト名** - `returnsValidationError_whenEmailIsInvalid_issue{number}` のように、振る舞い中心で明確な名前を使います（言語の慣習に合わせて大文字小文字は調整してください）
- **AAA パターン** - Arrange、Act、Assert を明確に分けて構成します
- **単一アサーション重視** - 各テストは issue 条件の 1 つの結果だけを検証します
- **まずエッジケース** - issue 議論で触れられた境界条件を考慮します

### テストパターン（ポリグロット）

- **JavaScript/TypeScript**: **Jest** または **Vitest** を使い、`describe`/`it` ブロックと `expect` アサーションで書く
- **Python**: **pytest** を使い、説明的な関数名と `assert` 文を使う
- **Java/Kotlin**: **JUnit 5** と **AssertJ** を使って流れるようなアサーションを書く
- **C#/.NET**: **xUnit** または **NUnit** と **FluentAssertions** を使う
- issue の例に複数の入力シナリオがある場合は、パラメータ化テストやデータ駆動テストを適用する
- issue で示されたドメイン固有の検証向けに、共通のテストユーティリティを作る

## 実行ガイドライン

1. **GitHub issue を取得する** - ブランチから issue 番号を抽出し、完全な文脈を取得する
2. **要件を分析する** - issue をテスト可能な振る舞いに分解する
3. **計画をユーザーに確認する** - 要件とエッジケースの理解を確認する。ユーザーの確認なしに変更を始めてはいけません
4. **最も単純な失敗テストを書く** - issue の最も基本的なシナリオから始める。一度に複数のテストを書いてはいけません。RED、GREEN、REFACTOR のサイクルを 1 テストずつ反復します
5. **テストが失敗することを確認する** - 期待した理由で失敗することを確認するためにテストを実行する
6. **テストを issue に結び付ける** - テスト名やコメントに issue 番号を含める

## Red フェーズのチェックリスト

- [ ] GitHub issue の文脈を取得し、分析済みである
- [ ] テストが issue 要件から期待される振る舞いを明確に表している
- [ ] テストが正しい理由で失敗している（実装不足）
- [ ] テスト名が issue 番号を参照し、振る舞いを説明している
- [ ] テストが AAA パターンに従っている
- [ ] issue 議論のエッジケースを考慮している
- [ ] まだ本番コードを書いていない
