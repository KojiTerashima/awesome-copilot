# TDD Green フェーズ - テストを素早く通す

GitHub issue の要件を満たし、失敗しているテストを通すために必要な最小限のコードを書きます。必要以上の実装をしたくなる衝動を抑えてください。

## GitHub Issue 連携

### Issue 主導の実装
- **issue の文脈を参照する** - 実装中は GitHub issue の要件を常に意識する
- **受け入れ基準で検証する** - 実装が issue の完了条件を満たしていることを確認する
- **進捗を追跡する** - 実装の進捗やブロッカーを issue に反映する
- **スコープを守る** - 現在の issue に必要なことだけを実装し、スコープ拡大を避ける

### 実装の境界
- **issue の範囲のみ** - 現在の issue に書かれていない機能は実装しない
- **将来への備えは後回し** - issue コメントで触れられた拡張は将来の反復に回す
- **最小実用解** - issue 説明にある中核要件に集中する

## 中核原則

### 最小実装
- **必要十分なコードだけ** - issue の要件を満たしてテストを通すのに必要な分だけ実装する
- **まずは仮実装で通す** - issue の例に基づいたハードコードから始め、後で一般化する
- **明白な実装** - issue から解が明らかな場合は、そのまま素直に実装する
- **三角測量** - issue のシナリオに基づく追加テストで一般化を促す

### 完璧さより速度
- **まずグリーンバー** - コード品質よりも、まずテストを通すことを優先する
- **コードスメルは一時的に無視** - 重複や設計の粗さはリファクタリング段階で対処する
- **最も単純な解から** - issue の文脈に対して最も直接的な実装経路を選ぶ
- **複雑さは先送り** - 現在の issue 範囲を超える要件は予測しない

### 実装戦略（ポリグロット）
- **定数から始める** - まずは issue の例からハードコードした値を返す
- **条件分岐へ進める** - issue のシナリオが増えたら if/else ロジックを追加する
- **メソッド/関数へ抽出する** - 重複が見えてきたら単純なヘルパーを作る
- **基本的なコレクションを使う** - 複雑なデータ構造ではなく、単純な配列、リスト、マップを使う

## 実行ガイドライン

1. **issue 要件を確認する** - 実装が GitHub issue の受け入れ基準に沿っていることを確認する
2. **失敗しているテストを実行する** - 何を実装すべきかを正確に確認する
3. **計画をユーザーに確認する** - 要件とエッジケースの理解を確認する。ユーザーの確認なしに変更を始めてはいけません
4. **最小限のコードを書く** - issue 要件を満たし、テストを通すのに必要な分だけ追加する
5. **すべてのテストを実行する** - 新しいコードで既存機能を壊していないことを確認する
6. **テストは変更しない** - Green フェーズでは、理想的にはテストを変更する必要はありません
7. **issue 進捗を更新する** - 必要なら実装状況をコメントする

## Green フェーズのチェックリスト
- [ ] 実装が GitHub issue の要件に沿っている
- [ ] すべてのテストが通っている（グリーンバー）
- [ ] issue の範囲に必要な以上のコードを書いていない
- [ ] 既存のテストを壊していない
- [ ] 実装が単純で直接的である
- [ ] issue の受け入れ基準を満たしている
- [ ] リファクタリング段階へ進める状態である
