# TDD Refactor フェーズ - 品質とセキュリティを改善する

すべてのテストをグリーンのまま保ち、GitHub issue への準拠を維持しながら、コードを整理し、セキュリティのベストプラクティスを適用し、設計を改善します。

## GitHub Issue 連携

### Issue 完了の検証

- **受け入れ基準がすべて満たされているか確認する** - 実装を GitHub issue の要件と突き合わせて確認する
- **issue 状態を更新する** - issue を完了として扱うか、残作業を特定する
- **設計判断を記録する** - リファクタリング時に行ったアーキテクチャ上の選択を issue にコメントする
- **関連 issue を結び付ける** - リファクタリング中に見つかった技術的負債や follow-up issue を特定する

### 品質ゲート

- **完了の定義への準拠** - issue のチェックリスト項目がすべて満たされていることを確認する
- **セキュリティ要件** - issue で触れられたセキュリティ考慮事項に対応する
- **性能基準** - issue で指定された性能要件を満たす
- **ドキュメント更新** - issue で参照されたドキュメントを更新する

## 中核原則

### コード品質の改善

- **重複を除去する** - 共通コードを再利用可能なメソッドやクラスへ抽出する
- **可読性を改善する** - issue のドメインに沿った、意図が伝わる名前と明確な構造を使う
- **SOLID 原則を適用する** - 単一責任、依存性逆転など
- **複雑さを単純化する** - 大きなメソッドを分割し、循環的複雑度を下げる

### セキュリティ強化

- **入力検証** - issue のセキュリティ要件に従って、外部入力をすべてサニタイズ・検証する
- **認証/認可** - issue に指定がある場合は適切なアクセス制御を実装する
- **データ保護** - 機密データを暗号化し、安全な接続文字列を使う
- **エラー処理** - 例外詳細から情報漏えいを起こさない
- **依存関係スキャン** - 脆弱なパッケージを確認する（`npm audit`, `pip audit`, `dotnet list package --vulnerable` など）
- **シークレット管理** - 環境変数または secrets manager を使い、資格情報をハードコードしない
- **OWASP 準拠** - issue や関連セキュリティチケットで挙がった懸念に対応する

### 設計の洗練

- **設計パターン** - 適切なパターン（Repository、Factory、Strategy など）を適用する
- **依存性注入** - 疎結合のために DI コンテナまたはコンストラクタインジェクションを使う
- **設定管理** - 環境変数または設定ファイルへ外出しする
- **ログと監視** - issue の切り分けに適した構造化ログをスタックに応じて追加する
- **性能最適化** - async/await や同等の並行処理プリミティブ、効率的なコレクション、キャッシュを使う

### 言語別ベストプラクティス（ポリグロット）

- **Null 安全性** - strict null checks（TypeScript）、nullable reference types（C#）、Optional types（Java/Kotlin）を有効にする
- **モダン言語機能** - パターンマッチング、分割代入、その言語らしい構文を使う
- **メモリと性能** - ボトルネックがプロファイリングで判明した場合にのみ、言語固有の最適化を適用する
- **エラー処理** - 具体的なエラー/例外型を使い、黙って飲み込まない

## セキュリティチェックリスト

- [ ] すべての公開メソッドで入力検証を行っている
- [ ] SQL インジェクションを防いでいる（パラメータ化クエリ）
- [ ] Web アプリケーションで XSS 対策をしている
- [ ] 機密操作に認可チェックがある
- [ ] 安全な設定になっている（コードにシークレットがない）
- [ ] 情報漏えいしないエラー処理になっている
- [ ] 依存関係の脆弱性スキャンを行っている
- [ ] OWASP Top 10 の観点に対応している

## 実行ガイドライン

1. **issue 完了状況を確認する** - GitHub issue の受け入れ基準が完全に満たされていることを確認する
2. **テストがグリーンであることを確認する** - リファクタリング前にすべてのテストが通っていなければなりません
3. **計画をユーザーに確認する** - 要件とエッジケースの理解を確認する。ユーザーの確認なしに変更を始めてはいけません
4. **小さな増分変更** - 細かいステップでリファクタリングし、頻繁にテストを実行する
5. **一度に 1 つの改善** - 1 つのリファクタリング技法に集中する
6. **セキュリティ分析を実行する** - 静的解析ツール（SonarQube、Checkmarx）を使う
7. **セキュリティ判断を記録する** - セキュリティ上重要なコードにはコメントを加える
8. **issue を更新する** - 最終実装をコメントし、完了していれば issue を閉じる

## Refactor フェーズのチェックリスト

- [ ] GitHub issue の受け入れ基準を完全に満たしている
- [ ] コード重複を取り除いている
- [ ] 名前が issue のドメインに沿って意図を明確に表している
- [ ] メソッドが単一責任になっている
- [ ] issue 要件に沿ってセキュリティ脆弱性へ対応している
- [ ] 性能面の考慮を適用している
- [ ] すべてのテストが引き続きグリーンである
- [ ] コードカバレッジを維持または改善している
- [ ] issue を完了扱いにするか、follow-up issue を作成している
- [ ] issue 指定どおりにドキュメントを更新している
